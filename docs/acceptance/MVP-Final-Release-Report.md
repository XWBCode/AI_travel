## 7. 外部阻塞（唯一硬阻塞，需要你动手）

```
POST https://c4ai.ccccltd.cn/api/compatible/v1/chat/completions
Authorization: Bearer sk-8TBM…(脱敏)

HTTP 200
{"code":400,"message":"invalid apikey: sk-8TBM…(上游原样回显)","data":null,"success":false}
```

三个细节值得记录：

1. **网关用 200 承载错误**。只看状态码会误判成功，然后把空 body 当成「模型返回空」。
   当前实现已识别 `Content-Type: application/json` 与流内错误块，翻译为
   「网关错误码 400：invalid apikey: sk-***」，并有 4 项断言。
2. **上游把 key 原样回显在 message 里**，所以错误信息做了脱敏，避免日志/界面泄露密钥。
3. 运行态自证：`GET /v1/health` → `{"provider":"mock","model":"mock-model","real":false}`。

**换 key 只需要改环境变量，代码一行不用动。** 换完按 §8 的顺序复验。

## 10. 是否建议进入 M3

**不建议。现在进 M3，等于把三个已知风险往后带。**

理由按优先级：

1. **M3 的核心是接外部数据源（天气/票价/车次）**，而 AC-15 现在记 NA 的原因正是「没有数据源」。
   模型连一次都跑不通的情况下，先接数据源只会把不确定性叠加：出问题时无法区分是模型错还是数据错。
2. **BUG-007（幂等键）在真实模型下会放大**。mock 生成 <1s，几乎不会超时重试；真实 30–45s，
   超时重试是常态。带着这个缺陷进 M3，等于给新功能预埋「重复计划 + 重复计费」。
3. **AC-07 样本量不足**说明校验资产的覆盖还不够厚。M3 的 ops 会更复杂（含实时数据），
   薄校验 + 复杂输入是最差的组合。

**建议顺序：可用 key → 真实模型复验（AC-03/05/07/08/11 重测）→ 再评估 M3。**（BUG-007、AC-07、AC-14 已完成）
按你的要求，我不擅自开始 B/C/D 组任务，也不做并行优化。
