# 和风天气凭据准备与联调

> 适用：D-03 落地。**只能由账号主体操作**——注册要邮箱/手机号与实名，公钥要上传到控制台。
> 开发侧已经把代码、单测、联调脚本准备好，你按本文做完，10 分钟内能拿到真实验证结果。
> 最后更新：2026-11-23

---

## 0. 先说清楚：为什么这一步不能代做

和风天气的 JWT 认证是**非对称密钥**：私钥在你这（本地文件），公钥在它那（控制台上传）。
注册账号需要邮箱/手机号验证，上传公钥是一次网页操作。这两件事都绑定账号主体，
不属于"写代码"能覆盖的范围。我能做的是：把步骤压到最少、把失败排查顺序写清楚。

---

## 1. 生成 Ed25519 密钥对（1 分钟）

```bash
cd backend-ai                      # 放在 backend-ai 下即可，不必再套子目录
openssl genpkey -algorithm ED25519 -out ed25519-private.pem
openssl pkey -pubout -in ed25519-private.pem > ed25519-public.pem
```

- `ed25519-private.pem`：**私钥**，签名用。留在本地，永远不要提交、不要发给任何人（包括我）。
- `ed25519-public.pem`：**公钥**，下一步粘贴到控制台。

> 已经生成过就跳过这一步，**不要重新生成**：控制台绑的是旧公钥，
> 重新生成会让私钥与公钥不配对，表现为接口一直 401 且官方不告诉你原因。
>
> 判断配对是否正确的唯一办法：控制台凭据页显示的 SHA-256，
> 等于「PEM 全文去掉结尾换行」的 SHA-256。复算（`$(...)` 会自动去掉尾部换行）：
>
> ```bash
> printf '%s' "$(openssl pkey -in ed25519-private.pem -pubout)" | openssl dgst -sha256
> ```
>
> 输出的 64 位十六进制应与控制台凭据页那串逐字相同。不同 = 拿错私钥，
> 此时去调 API 只会得到 401，而且官方出于安全不会告诉你原因。
> 详细过程见 `docs/acceptance/D-03-QWeather-接入报告.md` §5。

> `backend-ai/.gitignore` 的上级 `.gitignore` 已含 `*.pem` / `*.key`，所以这两个文件不会入库。
> 但**不要**把它们放进 `backend-ai/secrets/` 之外随便哪个目录然后 `git add -f` ——那会绕过忽略规则。

Windows 没有 `openssl` 时的替代方案：Chrome 137+ 打开控制台（F12）执行官方脚本
（`dev.qweather.com/docs/configuration/authentication/` 的「使用浏览器」一节），
它会直接打印一对 PEM。

## 2. 注册并创建凭据（3 分钟）

1. 注册并登录 <https://console.qweather.com>
2. **设置页**（`console.qweather.com/setting`）抄下两项：
   - **API Host**：形如 `abcxyz.qweatherapi.com`，是**你的专属域名**。
     用公共域名或别人的 host 一律 `403 INVALID HOST`，这是最常见的第一个坑。
   - **开发者 ID**：`Q` 开头的 10 位。
3. **项目管理**（`console.qweather.com/project`）：新建项目 → 添加凭据
   - 凭据名称随便写，比如 `ai-travel-dev`
   - 身份认证方式选 **JSON Web Token**（不要选 API KEY：2027 起会被限流，SDK 5+ 已不支持）
   - 公钥文本框粘贴 `ed25519-public.pem` 的**全部内容**（含 BEGIN/END 两行）
   - 保存后抄下 **项目 ID** 和 **凭据 ID（kid）**

> 控制台保存后不会再显示公钥，只给一个 SHA256。可以用它核对上传的是不是本地这对：
> 去掉首尾空白与换行后再算 SHA256，与控制台显示的一致即可。

## 3. 配环境变量（1 分钟）

写进 `.env`（已在 `.gitignore` 内），或直接 export：

```bash
WEATHER_PROVIDER=qweather
QWEATHER_API_HOST=abcxyz.qweatherapi.com
QWEATHER_DEVELOPER_ID=Q12345ABCD
QWEATHER_PROJECT_ID=ABCDE23456
QWEATHER_KEY_ID=ABCDE12345
QWEATHER_PRIVATE_KEY_PATH=./ed25519-private.pem
```

> 路径相对 `backend-ai/`（服务在该目录下启动）。本项目实际配置已写入
> `backend-ai/.env`（已忽略入库）。`app/config.py` **不自动加载** `.env`，启动前先：
> `set -a; . ./.env; set +a`

Java 侧同样要 `WEATHER_PROVIDER=qweather`（它只做开关与超时，不碰凭据）。

> 私钥也可以用 `QWEATHER_PRIVATE_KEY_PEM` 直接给内容（给 CI 用）。
> **不要**把它写进 `config/config.yaml`——那个文件是入库的，代码里也只从环境变量读 PEM。

## 4. 跑真实联调（2 分钟）

```bash
cd backend-ai
./.venv/Scripts/python.exe scripts/verify_weather_qweather.py     # Windows
# ./.venv/bin/python scripts/verify_weather_qweather.py           # macOS / Linux
```

脚本 7 项检查，逐项打印 PASS / FAIL / SKIP：

| # | 检查 | 失败时先去查 |
|---|---|---|
| 1 | JWT 签发（alg/kid/iss/sub/exp 逐字） | 开发者 ID 与项目 ID 是否填反；kid 是不是**凭据** ID 而不是项目 ID |
| 2 | 真实调用 200 且能归一化 | 403 → 看 §5 的 403 分支；401 → 公钥没上传成功或时钟偏差 |
| 3 | 降水概率落在 0–100 | 若全是 0–1，说明上游口径变了，改 `qweather._probability` |
| 4 | 日期连续且首日正确 | 报「疑似时区错位一天」→ `localTime=true` 没生效 |
| 5 | 10 天边界 / 越窗口降级 | 见 `FORECAST_WINDOW_DAYS` 与路由 `le=10` 是否同步 |
| 6 | 归因含「和风天气」 | 前端署名与链接是否展示 |
| 7a | 403 → hard：只发 1 次请求、立即熔断 | 若请求发了 2 次以上 → hard 判定失效；若 breaker 还 closed → 熔断器没接上 |
| 7b | 熔断打开后不再发请求 | 新增请求数必须为 0。不为 0 说明「重试」绕过了熔断 |
| 7c | DNS 失败 → soft，**不许**熔断 | 若这里熔断，说明把网络抖动误判成 hard，会把偶发问题放大成功能全挂 |

**退出码**：`0` 全通过；`1` 有 FAIL；`2` 一项都没真跑（缺凭据）。
`2` 不能当通过看——这一点是刻意设计的，防止"跳过"被读成"绿了"。

## 5. 失败排查顺序（按出现概率排）

### 403 INVALID HOST

API Host 填错。必须是从**你自己的**控制台-设置复制的那个域名，不是 `api.qweather.com`，
也不是文档示例里的 `abcxyz.qweatherapi.com`（那只是占位）。

> **实测形态**：2026-11-24 新注册账号拿到的 host 是 `kg6x8bg34e.re.qweatherapi.com`，
> **中间多一段 `.re.`**。所以不要按 `xxxxx.qweatherapi.com` 的固定形状去校验或拼装，
> 原样照抄最稳——代码里也只做 `https://{host}` 拼接，不做格式断言。

> **同样别用「错 host」去测 403**：域名不存在时请求死在 DNS，拿不到 403，只会得到
> `UPSTREAM_ERROR` + `hard=False`。要测 403 就用注入响应（脚本第 7a 项就是这么做的）。

### 401 UNAUTHORIZED

官方出于安全不返回具体原因，所以按顺序排：

1. **kid 是不是凭据 ID**（不是项目 ID）；
2. **iss 是不是开发者 ID**（`Q` 开头），**sub 是不是项目 ID**（两者填反是最常见原因）；
3. **公钥有没有真的上传成功**——用控制台的 JWT 验证工具（`console.qweather.com/support/jwt-validation`）
   粘一个 token 进去，它会明确告诉你签名对不对；
4. **本机时钟**偏差超过 30 秒。官方建议 `iat = now - 30s`，我们已经这么做了，
   但如果机器时间整体偏了，还是会 401。

### 403 NO CREDIT / OVERDUE / ACCOUNT SUSPENSION

账号额度、账单、冻结问题。这类错误**不要重试**——重试只会加速被判定为攻击。
代码里已把它们当 hard 错误处理（立刻熔断，冷却到上限）。

### 429 TOO MANY REQUESTS

QPM 超限。同样不重试，直接熔断。等冷却结束后的半开试探会自动恢复。
若频繁 429，先看是不是有人绕过了缓存（单飞合并 + 60 分钟 TTL 正常情况下不该触发）。

## 7. 成本口径（别被第三方文章吓到）

来源：<https://dev.qweather.com/docs/finance/pricing/>（按量计费定价）、
<https://dev.qweather.com/docs/finance/billing-and-payment/>（计费与支付）、
<https://blog.qweather.com/post/update-pricing-253/>（2025-03-01 降价公告）。核验日期 2026-11-24。

### 7.1 官方阶梯价（"天气和基础服务"分组，我们只用这一组）

| 每月请求量 | 每次请求价格 |
|---|---|
| 0 – 50,000 | **CNY 0** |
| 之后 950,000（至 100 万） | CNY 0.0007 |
| 之后 4,000,000（至 500 万） | CNY 0.0005 |
| 之后 5,000,000（至 1000 万） | CNY 0.00035 |
| 之后 40,000,000（至 5000 万） | CNY 0.00015 |
| 之后 50,000,000（至 1 亿） | CNY 0.0001 |
| 超过 1 亿 | 联系 sales@qweather.com |

该分组包含：天气预报、分钟预报、预警、天气指数、空气质量、时光机、**GeoAPI**、
天文、控制台API。即"天气 + 地理编码 + 空气质量"的请求量**合并累进**，不是各算各的。

> 我们只调 `/weather/v1/daily`，且城市坐标用自带 `city_coords.json`（不调 GeoAPI），
> 所以**一次天气查询 = 1 次请求**，不是 2 次。这是自带坐标表除了合规之外的第二份收益。

### 7.2 计费规则（官方原文口径）

- **后付费**，不用预付、不用买断；停止调用就不再产生费用。
- 账单周期 = 一个自然月，每月 1 号出账；应计费用按小时累计。
- 阶梯价累进周期 = 一个自然月，**每月 1 号从第一档重新开始**（不是全年累计）。
- 最小计费金额 **0.01 元**，不足按 0.01 元计。
- 官方算例：100 万次 = 5 万×0 + 95 万×0.0007 = **665 元/月**。
- 节省计划（一年期系数 0.7）可再打折，属预付承诺，**我们用不到，别开**。

### 7.3 我们项目的实际成本

按现有实现（60 分钟 TTL + 单飞合并，一个计划一小时最多 1 次）估算：

| 日活 | 估算月请求量 | 月费用 |
|---|---|---|
| 100 | ~1.8 万 | **0 元**（免费额度内） |
| 500 | ~9 万 | ~28 元 |
| 1,000 | ~18 万 | ~91 元 |
| 10,000 | ~180 万 | ~1,065 元 |

结论：这个量级**天气不是成本项**。真正要盯的是 **QPM** 和错误率——错误率高会先撞上
风控（持续错误请求可能被判定为攻击），那比账单麻烦得多。

### 7.4 三个别踩的坑

1. **逾期 30 天冻结账号**：账单未付 → 服务暂停；持续 30 天 → 账号冻结，且欠款仍要付。
   没有绑定支付方式的号，一旦超额就会走到这条路。
2. **最小计费 0.01 元**：超额后哪怕只有 3 次请求，也是 0.01 元起，不是 0.0021 元。
3. **免费额度可商用**：官方条款没有"非商用"限制，只要求注明来源
   （「天气服务由和风天气驱动」+ 链接 <https://www.qweather.com>）。
   这一点与 Open-Meteo（免费端点明确禁商用）本质不同，是选它的核心理由。
