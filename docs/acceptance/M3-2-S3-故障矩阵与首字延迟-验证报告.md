### 3.2 AC-9 首字延迟实测（S3 重点）

**测法**：本机起真 uvicorn（临时端口）+ httpx 真 HTTP 流式读 `/v1/plan/stream`；
三组同输入、同 provider（回声）、同进程、同环回；每组预热 2 次后丢弃（消除建连接偏差）。

| 组 | 条件 | `t_intent` P50 / P95 | `t_draft` P50 / P95 | 天气耗时 P50 / P95 |
|---|---|---|---|---|
| A 对照 | 注入关闭 | 8.7 / 29.0 ms | 8.7 / 29.0 ms | 0.0 / 0.0 ms |
| B 实验 | 注入开启，上游正常 | 9.1 / 33.8 ms | 9.7 / 33.8 ms | 0.0 / 0.0 ms |
| C 超时 | 注入开启，上游 5s | 2.2 / 26.2 ms | **2021.1 / 2043.2 ms** | 2009.0 / 2016.0 ms |

| 判据 | 结果 |
|---|---|
| AC-9.1 实验组 `t_draft` P95 增量 ≤ 2500ms | **PASS，+4.8ms**（两次独立运行分别为 −1.7ms 与 +4.8ms，即落在 ±5ms 噪声内） |
| AC-9.2 超时组 `t_draft` P95 增量 ≤ 2500ms | **PASS，+2014.2ms**（≈ 2s 预算 + 序列化开销） |
| AC-9.3 超时组天气耗时上界 | **PASS，P95 = 2016ms**（预算 2000ms） |
| AC-9.4 注入不推迟第一个 SSE 事件 | **PASS，+4.8ms** —— `intent` 事件在注入**之前**发出 |
| AC-9.6 测量本身有效 | **PASS，C 组 `draft-intent` P50 = 2017.6ms**，A 组同口径 0.0ms（证明 SSE 真的逐条到达、注入真的卡在 intent 之后） |
| AC-9.7 上游正常时注入开销可忽略 | **PASS，天气耗时 P95 = 0.0ms** |
| AC-9.5 三组 100% 出计划 | **PASS，15/15/10** |

**一个必须讲清楚的结构性事实**：`run_generation` 先 `yield intent` 再查天气，所以注入
推迟的不是"第一个 SSE 事件"，而是"**用户看到行程内容**的时点"。如果只测首字节，会得出
"注入不影响首字延迟"的错误结论 —— 用户明明多等了 2 秒。这也是 `t_intent` 与 `t_draft`
分开记的原因。

## 6. 已知限制与踩过的坑（诚实记录）

1. **模型是回声 provider**：A/B/C 三组用同一个 provider，模型与网络被固定住，
   所以测出来的是**注入带来的增量**，不是"真实模型下的首字延迟"。
   真实模型首字延迟取决于上游（DeepSeek 等），与本次改动无关，不在此报告的结论范围内。
2. **本机环回网络**：绝对值（8~30ms）不代表生产；有意义的是**组间差值**与**天气耗时**。
3. **坑 1（测量方法）**：第一版用 `TestClient.stream()`，三组 `t_intent / t_draft / t_done`
   三个数字一模一样（差 0.1ms）——整段 SSE 被攒成一块才交过来，测的根本不是首字延迟。
   改成真 uvicorn + 真 HTTP 后才看到 C 组 `draft-intent ≈ 2s`。为此加了 AC-9.6 这条自检，
   以后再有人换回 TestClient，这条会立刻变红。
4. **坑 2（预热偏差）**：不预热时第一次请求要建连接（66ms），算进 P95 会让"对照组"看起来更慢，
   差值变成负数（−31ms）。现在每组预热 2 次并丢弃。
5. **熔断是进程级单例**：矩阵每一场开头 `reset_all()`，否则上一场把熔断打开后，
   后面几场会"假跳过"。这也是本次 **SKIP = 0** 的原因，不是没跑。
6. **超时场景只跑 10 次**：每次固定消耗 2s 预算，10 次≈20s；A/B 各 15 次。
   P95 用 nearest-rank（样本少时不造没出现过的数）。
