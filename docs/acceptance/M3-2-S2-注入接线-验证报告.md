| 附加-1 | **天气功能默认关闭，关闭时生成链路与原版行为一致** | `A.1` dataclass 默认 `False`；`A.2` 上游调用 **0 次**；`A.3` prompt 无注入块；`A.4` **prompt 与 `build_plan_messages(history)` 全等**（逐字比对，不是"看起来类似"）。单测 `test_switch_off_prompt_is_byte_identical_to_baseline` / `test_switch_off_generation_matches_baseline_prompt` |

### 3.3 查询范围：PM 四条规则逐条落地

| 规则 | 实现 | 测试 |
|---|---|---|
| ① 有 `days` 按行程天数 | `days = min(wanted_days, remaining)` | `test_days_rule_takes_itinerary_length`、端到端 `B.1`（3 天窗口） |
| ② 有 `endDate` 不超过 `endDate` | `_last_day()` = `min(窗口末日, endDate)` | `test_end_date_caps_the_range_below_days`（7 天行程 + 11-26 结束 → 只查 3 天）、`test_end_date_used_when_days_missing` |
| ③ 都没有则查满剩余窗口 | `days = remaining` | `test_unknown_days_fills_the_remaining_window`（10 天） |
| ④ 无论如何不超过 10 天 | `window_end = today + 9` 兜底 | `test_end_date_beyond_window_is_clamped_by_window`、`test_too_many_days_does_not_exceed_window` |

`endDate` 解析不了或早于 `startDate` 时**忽略**而不是判成"不能注入"：前者是槽位抽取问题（不该连带否掉整次注入），后者拿去当上限会算出零天甚至负数天。测试 `test_unusable_end_date_is_ignored_not_fatal`。

### 3.4 两个埋点

```
weather_injected trace=B-inject-ok cities=1 covered=1 uncovered=0 days=3 upstream=1 elapsedMs=0
weather_skipped  trace=A-default-off reason=INJECT_DISABLED cities=0 upstream=0 elapsedMs=0
weather_skipped  trace=E-circuit-open reason=UPSTREAM_ERROR cities=1 upstream=0 elapsedMs=0 detail=成都:CIRCUIT_OPEN
```

`reason` 取值：`INJECT_DISABLED` / `PROVIDER_DISABLED` / `NO_CITY` / `NO_START_DATE` /
`BAD_START_DATE` / `DATE_OUT_OF_RANGE` / `NO_DATA`。
`NO_DATA` 带 `detail=`，逐城写具体原因 —— 否则"熔断（本地拦下、没出网）"和"真 500（出网了、被拒）"
在埋点里长得一模一样，那正是前面花一整轮才在展示层修掉的那种混淆。
日志**不记**对话原文、不记天气包（只记 traceId / 城市数 / 天数 / 耗时 / 上游次数）。

## 4. 回滚方式

| 层次 | 动作 | 效果 |
|---|---|---|
| **① 配置（首选，秒级）** | 不设或设 `WEATHER_INJECT_ON_GENERATION=false` | 生成链路回到 M3-2 之前，**零上游调用**（`A.2`/`A.4` 已证明 prompt 逐字一致） |
| ② 配置（软关） | `WEATHER_PROVIDER=none` | 即使开关打开也不查（`test_disabled_provider_skips_without_querying`） |
| ③ 代码回滚点 | `git revert` 单个提交（S2 是一个提交） | 新增文件整体消失；4 个改动文件的 diff 全部撤回 |
| ④ 局部关 | `WEATHER_INJECT_MAX_CITIES=1` / `WEATHER_INJECT_TIMEOUT_MS=0` | 缩到单城 / 不吃预算（立刻按"没天气"处理） |

三条互不依赖：①不需要重启代码回滚，②③④任意组合都不影响既有功能。

## 5. 是否影响既有生成链路

**不影响，且有三层结构性证据，不是"跑了一遍没报错"。**

1. **默认关闭 + 逐字比对**：开关关闭时 `build_plan_messages` 在拼接之前就返回，
   端到端断言 `A.4` 用的是 `==` 全等（messages 列表逐条逐字比对）。
2. **mock 分支完全不走这条路**：`run_generation` 里天气查询写在 `if not real: ... return`
   **之后**，所以本地/CI 的 mock 生成（也是契约回归基准）连配置都不读。
   这也是单测能保持"零出网"的原因。
3. **外部契约零变化**：Java、Vue、`contracts/travel-plan/`、`/plan/adjust` 全零改动，
   `plan_draft` / `plan_rejected` / `done` 事件字段一个没变（`git status` 可查）。

另外两处刻意的"不做"，避免把小功能做成大改动：

- **不让模型写 `aiNote` 附注**：那句话由 `brief_ai_note()` 用真实元数据拼，
  并自带 freeText 自检（禁"数字+单位"、≤ 500 字），不合规就**不加这句话**，
  而不是把一份本来合格的计划判成不合格。
- **不在注入侧预先解析城市**：坐标表只在 `fetch_forecast` 里用一次。
  在这儿再解析一遍，等于把「坐标未知就不出网」这条保证放进两个地方，改一处就会漏一处。

## 6. 已知限制（留给 S3 / M3-3，不在本切片范围）

1. **首字延迟**：注入发生在第一次 token 之前，最坏 +2s（`inject_timeout_ms`）。
   真实网络下的增量还没有测量，属 AC-9 / S3。
2. **快照不一致**：生成时用的天气与用户几分钟后在详情页看到的可能不同（TTL 60 分钟 + 上游更新）。
   设计稿 §7.3 已声明不试图消除。
3. **`/plan/adjust` 不注入**（D3 留 M3-3）：调整时计划已落库、`basic` 齐全，适用面比生成更大。
4. **适用面窄**：需要 `startDate` 且首日在 10 天窗口内。`startDate` 大面积为 null 是已知现实（09 §4.3），
   所以基调是"有则用、无则不提"。
