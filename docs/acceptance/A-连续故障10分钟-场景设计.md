## 1. 为什么要单独做这一场

之前证明的是**单次失败**：一次 500 会降级、一次 403 会立刻熔断。
但用户真正会遇到的是**持续故障**——上游挂 10 分钟，期间页面被刷新十几次。

持续故障和单次失败是两类问题：

| 单次失败的关注点 | 持续故障的关注点 |
|---|---|
| 这次请求有没有降级 | 第 4 次、第 40 次请求还会不会继续打上游 |
| 熔断会不会开 | 冷却到了会不会半开、半开失败会不会加长冷却 |
| 报错文案对不对 | 用户这 10 分钟里到底看到什么 |
| — | 缓存能扛多久，扛不住时是"旧数据"还是"错日期" |
| — | 恢复后能不能自己回来（而不是要重启） |

一句话：**单次失败证明"坏了不会崩"，持续故障才证明"坏了不会越搞越坏"。**

## 2. 故障注入方式（为什么不用真实账号）

PM 明确要求不通过真实账号制造 429/403。做法是在 Python 侧替换**唯一的出网点**
（`app/tools/weather_providers/qweather.py::_get`），由控制文件切换行为：

| 控制值 | 等价上游行为 | 归类（见 03 §4） |
|---|---|---|
| `ok` | 200 + 合法响应 | 正常 |
| `http_500` | 5xx | **soft**：可自愈，连续 3 次才熔断 |
| `timeout` | 连接/读超时 | **soft** |
| `http_403` | 403（INVALID HOST 之类） | **hard**：立刻熔断，且一次都不重试 |

- 这是**进程内替身**，不是"改了产品代码加开关"：替身脚本在启动时 monkeypatch，产品代码零改动。
- 每次调用都追加一行到 JSONL（时间、URL、结果）。**上游调用次数是本场的核心证据**：
  "没有请求风暴"只能靠计数证明，不能靠"看起来很快"。
- 绝不发真实请求：连 host 都不解析，纯内存返回。

## 3. 测试拓扑

```
驱动脚本 (verify_weather_outage.py)
   ├─ 写控制文件 ──────────────► 故障开关 (ok / http_500 / timeout / http_403)
   ├─ HTTP ─► Java :8080  (AI_SERVICE_URL=http://127.0.0.1:8100)
   │              └─► Python 故障实例 :8100  ──[替身]──► 内存响应
   └─ HTTP ─► Python 故障实例 :8100（直连，单独驱动熔断状态机）
```

两条轨分开跑，因为它们的关注点不同：

- **J 轨（Java）**：用户视角。看页面/接口在这 10 分钟里返回什么、多快。
- **P 轨（Python 直连）**：机制视角。逐个请求把熔断器推到 open → half-open → 冷却翻倍。

若只跑 J 轨，Java 的进程内缓存会把请求挡在外面，熔断器根本不会被推动；
若只跑 P 轨，无法回答"用户看到什么"。**必须两条同时跑。**

## 4. 时间轴与每阶段预期

### 4.1 主场景：10 分钟持续 500（生产参数）

参数全部取生产默认：`failure_threshold=3`、`cooldown=300s`、Java `cacheTtl=60min`、Java 天气超时 5s。
**唯一偏离生产的**：Python 实例的 `WEATHER_CACHE_TTL_MINUTES=1`（见 §4.4 说明）。

| 时刻 | 阶段 | 动作 | 预期（可断言） |
|---|---|---|---|
| T+0:00 | P0 基线 | 故障=ok，请求 Java 天气接口 | 200；`available=true`、`source=QWEATHER`、`stale=false`；记录 `fetchedAt` 与 3 天日期作为基准 |
| T+0:05 | P0 预热 | 同一接口再请求一次 | 200 且**上游调用数不增加**（缓存命中）；耗时显著低于首次 |
| T+0:10 | P1 故障开始 | 控制=500 | — |
| T+0:10–T+1:10 | P1 缓存仍有效 | J 轨每 30s 一次 | 200；`available=true`、`stale=false`、日期与基线**逐字相同**；上游调用数**不增长**（Java 缓存还在有效期内）→ 证明"有效旧缓存继续可用" |
| T+1:10 起 | P2 缓存过期 | J 轨继续每 30s | 200；`available=true`、**`stale=true`**、`note` 含"本次刷新失败"；日期仍是基线那 3 天（**不得前移/后移**）→ 证明"过期缓存降级为旧值而不是消失" |
| T+0:10–T+2:00 | P3 熔断建立 | P 轨每 20s 一次直连 | 前 3 次计入 soft 失败；第 4 次起 `breaker=open`，**上游调用数冻结**；返回 `ok=false` + `UPSTREAM_ERROR`，耗时 < 200ms（没打上游） |
| T+5:10 之后 | P4 半开探测 | P 轨在冷却结束后的首次请求 | 恰好放行 **1 次**探测（上游调用数 +1）；探测失败 → 冷却翻倍至 600s；之后请求再次被拦（调用数不再增） |
| T+10:10 | P5 故障结束 | 控制=ok | — |
| T+10:10–T+16:10 | P6 恢复等待 | P 轨继续探 | 冷却期内仍被拦（调用数不增）。**预期：默认参数下 10 分钟故障后，恢复最长要再等 10 分钟**（半开失败后 600s 冷却），这是设计使然，不是缺陷 |

**P6 的结论要照实写**：如果在这一场里始终没等到电路自行恢复，结论就是"默认冷却下，恢复时间可能超过故障时长本身"。这比"测出恢复很快"更值得写进报告——因为它决定了运维该不该有手动兜底。

### 4.2 补场景：空缓存 + 故障中首次访问

10 分钟窗口内 Java 缓存不会自然过期到"无缓存"状态，所以单独做：

| 动作 | 预期 |
|---|---|
| 故障=500 期间重启 Java（进程内缓存清空），请求天气接口 | 200（**不是 5xx**）；`available=false`、`reason=UPSTREAM_ERROR`、`days` 为空 |
| 同一时刻请求计划详情 `GET /api/plans/{id}` | **200 且耗时 < 2s**：天气失败不得拖慢核心链路 |
| 页面打开该计划 | 页面正常渲染，天气条**不塌缩**，显示一行降级原因 |

### 4.3 恢复场景（压缩冷却，只为证明能回来）

主场景的 600s 冷却会让"恢复"这一步要等到 15 分钟以后。为了在可接受时间内证明恢复路径本身正确，
单独跑一次**把冷却压到 20s** 的实例，并明确标注这是参数压缩，不是生产时序：

| 步骤 | 预期 |
|---|---|
| 故障=500，连续请求至 `breaker=open` | 调用数停止增长 |
| 控制切回 ok，等 20s 冷却 | — |
| 下一次请求 | 放行 1 次探测 → 成功 → `breaker=closed`；返回 `available=true`、`stale=false`、新 `fetchedAt` |
| 再请求一次 | 走缓存（调用数不增），`stale=false` |
| Java 侧同一时刻 | 从 `stale=true` 恢复为 `stale=false` |

### 4.4 一处刻意的参数偏离（必须写明，不能藏）

主场景把 Python 实例的 `WEATHER_CACHE_TTL_MINUTES` 设为 **1 分钟**（生产 60）。
原因：Java 的缓存有效期由 Python 响应里的 `expiresAt` 决定，60 分钟意味着
10 分钟故障期间 Java 永远命中缓存、`stale` 分支一次都触发不到——那这场就只能证明"缓存很好"，
证明不了"缓存过期后怎么降级"。

这个偏离只影响**缓存存活时长**，不影响降级逻辑本身；且 1 分钟是"更快到达同一个状态"，
不是"换了一条代码路径"。报告里会与主场景分开标注。

## 5. 判定与记录规则

- 每条断言输出 PASS / FAIL / SKIP 与实测值；**SKIP 不计入通过**。
- 只有全部 PASS 且退出码 0 才算这一场通过。
- 三条附加硬指标（贯穿全程）：
  1. `GET /api/health`（Java）与 `/v1/health`（Python）在整场中始终 200；
  2. 上游调用总数在熔断后**不再增长**（这是"没有请求风暴"的唯一证据）；
  3. 天气接口最坏耗时 < Java 侧 5s 超时 + 1s 余量。
- 明确不声称：真实 429/403（用替身注入）、真实网络抖动（用固定 500）、
  多实例部署下的熔断（本项目是进程内熔断，单机语义）。

## 6. 预期可能暴露的问题（先写下来，避免事后找补）

> 执行后回填（2026-11-24）：三条全部被证实，另加一条脚本层面的教训。

1. **熔断返回的原因太笼统 —— 已证实**：熔断期间与上游真 500 返回同一个
   `UPSTREAM_ERROR`，耗时也相近（都是毫秒级），**从外部完全无法区分**。
   证据：主场景 30 次请求里，真失败 3 次、熔断拦截 21 次，用户看到的文案一模一样。
   这可能值得改成独立 reason，但本轮不改（PM：不扩功能）。
   > **2026-11-24 已修**：PM 批准后新增 `CIRCUIT_OPEN`，熔断期不再复用 `UPSTREAM_ERROR`。
   > 跨层验证见 `CIRCUIT_OPEN-跨层验证报告.md`。上面这段保留原样，因为它记录的是**当时的实测状态**。
2. **Java 与 Python 两层缓存 + 两层超时 —— 已证实且比预想更明显**：
   故障期 18 次响应是"Java 用旧值 + Python 已熔断"的组合，
   `note` 里能看到"本次刷新失败：UPSTREAM_ERROR"，但用户无法知道是熔断还是上游挂了。
   > **2026-11-24 部分已修**：新产生的 `note` 会写 `CIRCUIT_OPEN`，原因不再被折叠。
   > 但 `note` 里仍是英文枚举（Java 刻意不翻译，只透传），前端在 `stale=true` 时不展示 `note`——
   > 也就是说"旧值 + 熔断"这个组合下，用户依然只看到一句"数据为上次成功获取的结果"。
   > 这一格留作后续（不在 PM 本轮批准范围内）。
3. **恢复期没有手动兜底 —— 已证实，且比预想更慢**：半开探测失败后冷却从 300s 翻倍到 600s，
   10 分钟故障结束后最长还要再等约 10 分钟。是否需要运维手工重置入口，需 PM 决定。
4. **（新增）断言比产品更容易出错**：第一版脚本有 4 条断言口径写错，
   产生 2 个假红 + 2 个假绿。详见报告 §6。这条教训写进文档不是自我批评，
   而是提醒下一次做同类验证的人：**先想清楚"这个数字说明什么"，再去写比较**。
