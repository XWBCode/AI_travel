## 2. 外部阻塞的证据

```
POST https://c4ai.ccccltd.cn/api/compatible/v1/chat/completions
Authorization: Bearer sk-8TBM…(已脱敏)

HTTP 200
{"code":400,"message":"invalid apikey: sk-8TBM…(上游原样回显，已脱敏)","data":null,"success":false}
```

两点值得记下来：

1. **网关用 HTTP 200 承载错误**。如果只看状态码会以为成功，随后把空 body 当作「模型返回空内容」，
   排查方向会完全跑偏。当前实现已识别 `Content-Type: application/json` 与流内错误块，
   并翻译为「网关错误码 400：invalid apikey: sk-***」（见 `verify_provider_errors` 4 项断言）。
2. **上游会把 key 原样回显在 message 里**，所以错误信息做了脱敏，避免日志/界面泄露密钥。

当前运行态：`GET /v1/health` → `{"provider":"mock","model":"mock-model","real":false}`。

## 3. Mock 层实测（能证明什么、不能证明什么）

| 指标 | 实测 | 能证明 | **不能**证明 |
|---|---|---|---|
| 意图识别准确率（目的地+天数） | 20/20 = 100% | 规则版解析在常见句式上可靠 | 模型对模糊表达的理解力（规则版本来就不用模型） |
| 计划生成结构完整性 | 3 份计划，3 天/9 项，天数与 `days` 自洽 | 契约→校验→落库链路闭合 | 真实模型能否产出合法结构 |
| FactField 合规 | 124 个 FactField，`verified=false` 带值 0 处 | 校验器拦得住「编造数值」 | 真实模型是否会尝试编造 |
| 流式首字延迟 | P50 30ms / P95 38ms（n=30） | 流式链路本身没有额外延迟 | 真实模型 30–45s 的响应体验 |
| 调整建议 ops 合规 | 六种 op 全部通过 `AdjustmentOps.normalize` | 增量写库机制正确 | 模型产出的 ops 是否「合理」 |

### 3.1 一个必须写清楚的限制：mock 的「聪明」是假的

`mock_adjust` 的策略是「找第一个备注为空的行程项补一句备注，找不到就新增一项」。
它能保证每次调用都产生**非空且合法**的 ops，从而让端到端脚本可以稳定回归；
但它和「用户说下午不去了」没有任何关系。

所以**「调整建议的端到端 21 项全通过」只证明流程正确，不证明建议有用**。这一条必须和
真实模型的验收结论分开读。

### 3.2 Mock 也暴露了一个真实问题（已修）

Mock 第一次跑验收时，AC-04（断连落库）直接 FAIL，而这不是 mock 的锅——
是 `runPlan` 的断连分支把整轮回答吞了（BUG-001）。**这些问题恰恰只有跑真实链路才看得见**，
Mock 生成速度快反而让断连窗口更容易被抓到。

## 4. 真实模型层：要验什么、怎么验

Key 换好后按下面这套口径跑，才能得出「模型行不行」的结论。建议一次跑 20 次生成 + 10 次调整。

### 4.1 计划生成

| 指标 | 口径 | 门槛建议 |
|---|---|---|
| 一次通过率 | `plan_draft` 事件出现次数 / 发起次数 | ≥ 90% |
| 失败原因分布 | `plan_rejected.reason`（SCHEMA_VIOLATION / NEED_MORE_INFO / 50201） | 记录，不设门槛 |
| 端到端耗时 | `meta` → `done` 的 P50/P95 | P95 ≤ 60s（.env 已按 240s 兜底） |
| 输出长度是否被截断 | 检查 `days` 最后一天是否有内容、`aiNote` 是否收尾 | 0 次截断（4096 token 会截断，已调至 8192） |
| FactField 编造 | `verified=false` 且 `value != null` 的数量 | 0 |

### 4.2 调整建议

| 指标 | 口径 | 门槛建议 |
|---|---|---|
| ops 合规率 | `30109` 次数 / 发起次数 | ≤ 10% |
| 空操作率 | `30110` 次数 / 发起次数 | ≤ 10%（说明模型会「改了个寂寞」） |
| 指令遵循 | 人工抽检 10 条：「删掉下午那项」是否真的只删那项 | 主观，但必须有人看 |
| 越界尝试 | ops 里出现天数/日期/预算字段的次数 | 0（校验器会拒，但要统计模型是否老想越界） |

### 4.3 判定口径

- 上述任一硬门槛（一次通过率、编造数、越界数）不达标 → 不发布，先调 prompt / 加约束；
- 全达标 → 补一份本报告的「真实模型」章节，并重跑 `verify_acceptance.py` 全量。

## 5. 已做的防护（不依赖模型是否听话）

| 防护 | 位置 | 作用 |
|---|---|---|
| 契约校验（Schema + 语义 S-1~S-8） | `PlanSchemaValidator` | 模型胡写直接拒，不落库（AC-07） |
| `unverifiedFieldCount` 服务端重算 | `PlanService` | 模型自报的数字不作数（S-5 修订） |
| ops 规范化 + 白名单 | `AdjustmentOps` | 越界字段、非法时间、跨计划 itemId 全部拒 |
| `before` 服务端回填 | `AdjustmentOps` | 不让模型编造「原值」 |
| 网关错误识别与脱敏 | `provider.py` | 200 带错误体能被看穿，key 不外泄 |
| 待确认强制 | `PlanAdjustmentService` | 模型永远不能直接写正式计划（AC-11） |

**这六条的价值在于：模型再差，最坏结果也只是「生成失败」，不会变成「数据被写坏」。**
