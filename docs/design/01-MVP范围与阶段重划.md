# 01 · MVP 范围与阶段重划

> 状态：草案，待 D-01 确认 ｜ 上位文档：总纲 V1.0 第 7、12、13 章

## 1. 现状问题

总纲第 7 章划分了 Phase 0–6，但存在三个结构性问题：

1. **总量过大**：6 大业务模块、13 个页面、7 个 Agent、17 类实体、若干外部数据源，全部落在"阶段规划"里，没有一条明确的交付主线。
2. **Phase 之间没有"可用产品"**：Phase 1 结束只有聊天，Phase 2 结束只有计划草稿，直到 Phase 3 才形成第一条用户价值闭环。中间任何一个 Phase 暂停，交付物都不能独立演示。
3. **验收项与阶段不对齐**：第 12 章 17 条最终验收标准没有映射回各 Phase，无法判断"做到第几步算完成"。

同时，总纲第 13 章自己给出了答案：

> **先完成闭环，再扩展功能。** 优先完成用户登录 → AI 对话 → 旅行计划生成 → 用户确认 → 旅行执行的完整闭环。

但这条原则没有落到第 7 章的 Phase 划分里。**本文件就是把这条原则落实为可执行范围。**

## 2. MVP 定义

### 2.1 一句话

> 一个用户能登录、用自然语言生成一份结构化旅行计划、修改并确认它、开始旅行、查看当天行程与进度、结束旅行并留下记录。

### 2.2 MVP 必须有（In Scope）

| # | 能力 | 对应总纲章节 | 对应验收项 |
|---|---|---|---|
| 1 | 注册 / 登录 / JWT / 个人资料查看 | 2.1、Phase 1 | 12-1 |
| 2 | AI 多轮对话、独立会话、历史持久化、SSE 流式、停止生成 | 2.2.1、Phase 1 | 12-2、12-16 |
| 3 | 旅行需求识别与必要信息追问 | 2.2.2、Phase 2 | 12-3 |
| 4 | 结构化旅行计划生成（含每日行程、景点、预算框架） | 2.2.2、Phase 2 | 12-4 |
| 5 | 计划修改、用户明确确认、状态机 DRAFT→CONFIRMED | 2.2.3、Phase 2 | 12-5 |
| 6 | 开始旅行 / 每日行程展示 / 进度勾选 / 完成旅行 | 2.2.4、Phase 3 | 12-6、12-7 |
| 7 | 行程调整建议（AI 出方案，**用户确认后**才改正式计划） | 2.2.4、4.2 | 12-8 |
| 8 | 站内通知（行程提醒、计划状态变更） | 2.6 | 补充项 |

> **第 8 项是总纲遗漏**：总纲 2.6 定义了 7 类通知，但第 7 章没有任何 Phase 包含通知系统。而「行程提醒」「计划状态变更」在 Phase 3 就必须存在，否则闭环断裂。本文件把它提进 MVP。

### 2.3 MVP 明确不做（Out of Scope）

| 不做 | 原因 | 计划归属 |
|---|---|---|
| 旅行社区（文章、点赞、评论、搜索、RAG） | 与核心闭环无关，且引入 UGC 审核与合规成本 | Phase 4（后置） |
| 分享链接 / 多人协作 / 编辑锁 / 投票 / 版本回滚 | 并发控制与权限模型复杂度高，独立于单人闭环 | Phase 5（后置） |
| 实时天气 / 火车票 / 地图距离优化 | 依赖外部数据源与商用授权，当前无 key | L1 增强层（见 03） |
| GPS 定位与进度自动判断 | 敏感个人信息，需隐私政策与合规评估 | 后置 |
| 多 Agent 完整编排（7 个 Agent 全上） | 简单任务直连主 Agent 即可，总纲 4.1 明确反对为多 Agent 而多 Agent | Phase 6 |
| Elasticsearch / RabbitMQ / Qdrant | 第一阶段模块化单体即可承载，见总纲 3.4 | 按需引入 |
| 邮件 / 移动端推送 | 站内消息已满足 MVP | 后置 |

### 2.4 范围红线

- **不得**为了"看起来完整"而把 Out of Scope 项做成静态假页面冒充已完成功能（总纲 9.3）。当前前端的占位页（`/placeholder/*`）明确标注「待开发」，这个做法正确，保持。
- **不得**把 Mock 天气数据当作真实天气展示。L0 阶段所有实时字段标记「未核实」（见 03）。
- 新增范围必须走变更记录，说明对工期与依赖的影响，由项目负责人确认。

## 3. 重划后的里程碑

按「每个里程碑结束都有一条可演示的用户路径」重划。工期与人力**留空待 D-10 确认**。

| 里程碑 | 目标（可演示的用户路径） | 主要内容 | 对应原 Phase | 工期 |
|---|---|---|---|---|
| **M0** 基线 | 三端能启动、能注册登录、能发一条消息并收到流式回复 | Phase 0 + 1 骨架（**已完成**）、SQL、启动脚本、Git | 0 / 1 | 已完成 |
| **M1** 计划生成 | 用户说一句话 → 得到一份结构化计划卡片 → 能修改 → 能确认 → 刷新后还在 | 需求解析、计划 Schema、计划详情/编辑页、状态机、L0 降级标注 | 2 | 待确认 |
| **M2** 旅行执行 | 用户确认的计划能「开始旅行」，看当天行程、勾进度、要求 AI 调整、结束旅行 | 执行页、进度记录、调整建议 + 用户确认、站内通知、COMPLETED 状态 | 3 + 2.6 | 待确认 |
| **M3** 增强层 | 有真实天气时行程卡片显示带来源与更新时间的天气，无数据时明确降级 | 天气 Tool、FactField 契约、来源展示、缓存与限流 | 2.2.4 部分 | 待确认 |
| **M4+** 扩展 | 社区 / 分享 / 协作 / RAG / 深度 Agent | 沿用总纲 Phase 4–6，届时另行细化 | 4 / 5 / 6 | 待确认 |

**关键差异**：原 Phase 2 只做"生成计划"，M1 要求一直做到"确认并持久化"；原 Phase 3 才形成闭环，现在 M1 结束就有可演示交付物。

## 5. 与最终验收标准的映射

总纲第 12 章 17 条，映射到重划后的里程碑：

| 验收项 | 里程碑 | 验收项 | 里程碑 |
|---|---|---|---|
| 1 注册登录管理个人信息 | M0（部分）/ M1 | 10 浏览社区内容 | M4+ |
| 2 持续多轮对话 | M0 | 11 分享旅行计划 | M4+ |
| 3 AI 理解旅行需求 | M1 | 12 多人加入同一计划 | M4+ |
| 4 生成结构化计划 | M1 | 13 多人讨论和投票 | M4+ |
| 5 修改和确认计划 | M1 | 14 查看历史版本 | M4+ |
| 6 开始和结束旅行 | M2 | 15 AI 检索有权限知识 | M4+ |
| 7 查看天气和旅行进度 | M2（进度）/ M3（天气） | 16 核心数据持久化 | M0 / M1 |
| 8 要求 AI 调整行程 | M2 | 17 安全、异常、部署 | 全里程碑 |
| 9 发布旅行文章 | M4+ | | |

**结论**：M2 结束时 MVP 闭环完成（验收项 1–8、16、17），M3 补齐天气，M4+ 覆盖 9–15。可在 M2 做一次正式的产品验收，而不必等全部 17 条。

## 6. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 大模型 key 未取得 | M1 计划生成无法真实验证 | 沿用现有 `mock` Provider 打通链路，显式标注 `[MOCK]`；拿到 key 只改 `.env`（总纲 9.3） |
| 天气/地图数据源与商用授权未定 | M3 阻塞；若强行上线会违反总纲「不编造」红线 | L0/L1 分层（03），商务流程尽早启动（D-03/D-04） |
| 范围膨胀（中途想加社区/协作） | M1/M2 延期 | 任何新增范围走 D-01 变更确认 |
| 计划 Schema 未冻结就前后端并行开发 | 大面积返工 | D-06 评审冻结后再联调 |
