# 12 · M3-3 设计方案：给 `/plan/adjust` 增加可选天气上下文

- 状态：**设计中，待项目经理审批实施范围**（本稿不含任何代码改动）
- 上游依据：[11-M3-2](./11-M3-2-天气进入生成链路-设计方案.md)（已关闭）、[03 §4.1](./03-外部数据源选型与降级规范.md)（生成期使用外部数据的六条规矩）、[M3-2 关闭记录](../acceptance/M3-2-关闭记录与运行验证清单.md)
- 暂定边界（PM 批复）：**只给 `/plan/adjust` 增加可选天气上下文；不修改计划契约；不改变原有调整规则和状态机。**

---

## 0. 一句话

生成链路在回答「**帮我排一份行程**」时可以看一眼天气；调整链路在回答「**这份行程里某一项要不要改**」时同样需要看一眼天气——但它是另一条业务链路，**输入形状、窗口语义、延迟形态、留痕能力**四处都与生成链路不同，所以 M3-3 是"另写一条"，不是"照抄一遍接线"。

---

## 1. 目标场景与要解决的问题

### 1.1 四个真实请求，两类需求

| 用户原话（发生在行程进行中） | 需要天气吗 | 为什么 |
|---|---|---|
| 「今天下午下雨的话，把爬山换成室内的」 | **需要** | 模型不知道今天下雨，只能给一个与天气无关的替换 |
| 「明天要是还下雨，第 3 天就改去博物馆」 | **需要** | 条件句的主体是天气，模型完全没有这个变量 |
| 「第 2 天太赶了，删掉一个景点」 | 不需要 | 纯强度问题 |
| 「把第 4 天标题改成『慢下来的一天』」 | 不需要 | 纯文案 |

**四分之二需要。** 而现在的行为是：模型对这四个请求的处理方式完全一样——它看不到任何天气，于是对前两个只能给出"看似合理但可能正好相反"的建议（下雨天建议去爬山）。这不是延迟问题，是**建议正确性**问题。

### 1.2 M3-3 要解决什么

让 `/plan/adjust` 在**能拿到天气**时，把一份已核实的天气预报交给模型，使它给出的增量修改建议与当天的实际天气不冲突；拿不到时，行为与现在**逐字相同**。

### 1.3 不解决的问题（明确非目标）

- **不让天气出现在界面上。** `/plan/adjust` 的响应不新增任何天气字段。用户端今天看不到"这次建议参考了天气"，M3-3 之后也看不到。
- **不让天气写进计划。** 调整产出的是 ops，不是完整计划；M3-3 **不**在计划里留任何痕（无 `aiNote`、无备注、无新增 op）。理由见 §4.6。
- **不改调整规则。** 六种 op 类型、字段白名单、`MAX_OPS=20`、HH:mm 校验、同天增删与重排不混用——一条都不动。
- **不做"按用户意图决定要不要查天气"的分类器。** 理由见 §4.1。
- **不动 Java。** 视图构造、`AdjustmentOps` 校验、乐观锁、状态机全部保持原样。

## 2. 为什么不能照搬生成链路

这是本设计最重要的一节。M3-2 的接线方式（`prepare_weather_block(slots)` → `build_plan_messages(history, block)`）**不能**平移到调整链路，原因有五个，每一个都会导致错误行为而不是"稍微不准"。

| 维度 | 生成链路（M3-2，已关闭） | 调整链路（M3-3） | 照搬会怎样 |
|---|---|---|---|
| 输入 | 槽位 `{destination, destinations, startDate, days}`，`startDate` 大面积为 null | 计划视图，**每天自带 `date` 和 `city`** | — |
| 日期来源 | 单一 `startDate` + `days` | 逐天 `date`，缺失时可由 `startDate + dayIndex - 1` 推算 | — |
| 城市来源 | `destinations` 列表，可能模糊/多城无对应关系 | **每天绑定一个确定城市** | 用 `destinations` 会丢掉"哪天在哪个城"的对应 |
| 窗口判定 | `startDate` 必须落在 `[今天, 今天+9]` | 行程**可能已经开始**（`IN_PROGRESS`） | **直接否掉最需要天气的场景** |
| 输出 | 完整计划，有 `verify()` 与 `aiNote` 可留痕 | 增量 ops，**无留痕处** | 无处记录"用了天气" |
| 自由文本机检 | `contract.verify()` 检查 `freeText` 禁止"数字+单位" | **两侧都没有这项检查**（见 §2.4） | 天气数值可被直接写进 `note` 且无人拦截 |
| 延迟形态 | SSE：先发 `intent`，再查天气，只推迟"内容出现" | **同步 JSON**：天气耗时 100% 叠加到用户等待 | 2s 预算会把"改个备注"变成 2s+ |
| 失败代价 | 无天气的计划仍是完整计划 | 若走校验闸门拒绝，用户要**重说一遍** | 闸门设计必须极度保守 |

### 2.1 输入更全，这反而是好消息

Java 侧 `PlanAdjustmentService#build()` 构造的 `aiView` 是：

```
{ title, totalDays, startDate, status,
  days: [ { dayIndex, date, city, theme, items: [ {itemId, order, title, startTime, endTime, note} ] } ] }
```

它同时有 `startDate` **和**逐天 `date`/`city`。这意味着 M3-3 **不需要**像 M3-2 那样依赖槽位抽取质量：城市与日期的准确率取决于数据库里的计划本身，而不取决于模型听没听懂用户说的话。11 号文档 §2.3 里那句"调整时计划已落库、`basic` 齐全，适用面比生成更大"，指的正是这一点。

### 2.2 窗口必须是"交集"，这是与 M3-2 的必要偏离

M3-2 的 `can_inject()` 有一句硬判定：

```python
if start < today or start > window_end:
    return InjectDecision(False, SKIP_OUT_OF_RANGE)
```

放到调整链路上就是灾难：**`IN_PROGRESS` 的行程 `startDate` 必然早于今天**，于是"今天下午下雨要不要改行程"这个最典型的请求会被判成 `DATE_OUT_OF_RANGE`，一次都不查。

所以 M3-3 用自己的窗口函数：**行程日期区间 ∩ 预报窗口**，交集非空就查交集部分。这保证了：

- `startDate` 在过去、行程还在继续 → 能拿到今天起的天气（正确）
- 行程全部在过去（`COMPLETED`，实际到不了这里）→ 交集为空，零查询
- 行程全部在 10 天之外 → 交集为空，零查询（与 M3-2 一致）

**10 天上限本身沿用**——那是数据源能力，不是业务选择，没有重新讨论的余地。

### 2.3 没有流式输出，延迟是全额叠加

生成链路的 `run_generation` 是 async generator，先 `yield intent` 再查天气，所以天气耗时推迟的是"用户看到行程内容"的时点，不是"第一个 SSE 事件"（PM 已就此定过性：**不能描述成"天气不影响首字延迟"**）。

调整链路没有这个问题，因为**它没有流**：`await run_adjust(...)` 一次性返回 JSON。天气耗时 100% 落在用户的白屏时间里。

结论：**M3-3 的预算必须比 M3-2 小**，见 §4.5。

### 2.4 最后一道机械网，在调整链路上是缺的

生成链路里"自由文本禁止数字+单位"有代码兜底：`contract.verify()` 用 `NUMERIC_UNIT_PATTERN` 扫全份计划。

调整链路**没有**：

- `validate_ops()`（Python）只校验 op 类型、itemId 归属、HH:mm 格式、字段白名单、重排完整性——**不校验自由文本里的数值**；
- `AdjustmentOps`（Java）只校验长度上限（`title ≤ 60`、`note ≤ 200`）与结构——**同样不校验数值**。

也就是说，`ADJUST_SYSTEM_PROMPT` 规则 6（"自由文本禁止「数字 + 单位」"）**目前只靠模型自觉**。今天这不算漏洞，因为模型手里没有真实数字可抄；M3-3 一注入天气，它手里就有了。所以 M3-3 必须自己补这一道网（§4.3），**且只在注入过天气时生效**，否则等于顺便收紧了已验收的调整行为。

### 2.5 结论

M3-3 = **新的窗口函数** + **复用 M3-2 的摘要/渲染/查询/缓存** + **一条新的、仅在注入期生效的数值闸门**。不是给 `run_adjust` 加两行 `await`。

## 3. 功能范围

### 3.1 做

1. 从计划视图推导「城市 × 日期」查询范围（纯函数，可单测）。
2. 复用 M3-1 的 `fetch_forecast`（只读，不改缓存/熔断），并发查 ≤3 个城市。
3. 复用 `build_brief` / `render_brief_block` 生成注入块，追加一段**调整场景专用**的使用约束。
4. `build_adjust_messages(plan_view, instruction, weather_block=None)` 增加可选参数。
5. 两个配置项（开关默认关闭、独立预算）+ 两条埋点。
6. 注入过天气时，给 `validate_ops` 追加一条**数值检查**（扩展了 `%`/`级`/`毫米` 的正则）。
7. 端到端故障矩阵与延迟实测。

### 3.2 不做

- 不做意图分类器（§4.1 有论证）。
- 不在响应里返回天气，不写 `aiNote`，不新增 op 类型或字段（§4.6）。
- 不把 `_weather` 之类字段塞进 `plan_view`（那会污染输入契约，也会让模型以为天气是计划的一部分）。
- 不改 `NUMERIC_UNIT_PATTERN`（它服务于已冻结的契约校验，改它会改变生成侧行为）。
- 不改"按天缓存键"（那属于 M3-1 缓存语义，PM 明确不为此重构）。
- 不做"校验失败自动重试一次"（§4.3 有取舍说明）。
- 不动任何 Java 代码、不动 `contracts/`。

## 4. 六个问题的回答

### 4.1 Q1：调整请求如何判断是否需要天气，哪些情况不注入？

**答：不做"是否需要"的意图判断；只做"能不能拿到"的能力判断。**

#### 为什么不做意图判断

关键在于**时点**：调整链路的产出（ops）是模型算出来的，所以在注入时点，"这次要改什么"**结构上未知**。想判断"是否需要天气"，只剩三条路，每条都不成立：

1. **关键词分类**（"下雨""天气""热"→ 需要）——用户说「今天下午不想爬山了」时没有一个天气词，但那正是最需要天气的一句。漏判代价是"建议又错了"，而这正是 M3-3 要修的东西。
2. **先让模型判断**——多一次调用、多一份延迟与成本，且判断本身也不可靠。
3. **两段式**（先出 ops 再看要不要天气）——已经生成完了，天气没有用处。

更根本的理由：**判错的代价不对称**。漏注入 = 少一条参考（等于今天的行为）；误注入 = prompt 长几百 token、多几十毫秒。为了省这点成本去引入一个会误判的规则，违反本项目"判据只能有一个且可机检"的一贯做法。

所以沿用 M3-2 的原则：**有则用、无则不提**，用不用交给模型——注入块自带使用约束，system prompt 里已有"只做用户要求的改动，不要顺手优化"（规则 5），这两条合起来就是"给了也可以不用"。

#### 注入的排除清单（全部是"能不能拿到"，不是"要不要"）

| # | 条件 | reason | 上游调用 | 说明 |
|---|---|---|---|---|
| 1 | `WEATHER_INJECT_ON_ADJUST=false`（**默认**） | `INJECT_DISABLED` | 0 | 在**第一次读配置**就返回，连窗口都不算 |
| 2 | 数据源未启用（`provider=none`） | `PROVIDER_DISABLED` | 0 | 语义同 M3-1 |
| 3 | 计划里没有可解析的日期（`date` 全 null 且 `startDate` 为 null/非法） | `NO_START_DATE` | 0 | 不兜底成"今天"——兜底等于编造 |
| 4 | 行程日期区间与 `[今天, 今天+9]` **无交集** | `DATE_OUT_OF_RANGE` | 0 | 含"全部在 10 天之外"与"全部已过去" |
| 5 | 计划里没有城市（`days[].city` 全空） | `NO_CITY` | 0 | |
| 6 | 城市名无法解析出坐标 | 逐城 `CITY_UNKNOWN` | 0 | 由 `resolve_city` 在出网前拦下 |
| 7 | 查询成功但一个 `verified=true` 字段都没有 | `NO_DATA` + 逐城 detail | 已发生 | 渲染空表会诱导模型自行补全 |

**关于计划状态：不重复判断。** Java 侧 `PlanAdjustmentService` 已经限定只有 `CONFIRMED` / `IN_PROGRESS` 能进调整链路，`COMPLETED` / `CANCELLED` 到不了这里。Python 侧再判一遍等于把同一条规则放在两个地方，改一处漏一处（§2.1 同款理由，M3-2 在 `_fetch_city` 里已经用过一次这个论证）。若将来调整对 `DRAFT` 开放，天气照常注入——那不是错误。

### 4.2 Q2：城市与日期从哪来，是否沿用 10 天窗口？

**答：城市与日期都从计划视图逐天读；10 天上限沿用，但判定方式改为"交集"。**

#### 日期：`day.date` 优先，`startDate + dayIndex - 1` 兜底

```python
def _day_date(day, start):
    raw = str(day.get("date") or "").strip()
    if raw:
        try:
            return date.fromisoformat(raw)
        except ValueError:
            pass                      # 格式错就退到推算，不因此否掉整次注入
    index = day.get("dayIndex")
    if start and isinstance(index, int) and index >= 1:
        return start + timedelta(days=index - 1)
    return None                       # 这一天无法定位，排除
```

为什么允许推算：`day.date` 在库里是可空列，而 `startDate` 是计划级字段。两者都不缺时以逐天值为准（它是用户实际改过的值）；`day.date` 缺失但 `startDate` 在时，用 `dayIndex` 推出来的日期与生成时写入的规则完全一致。这条兜底能把"日期齐全率"从"看数据质量"变成"看 `startDate` 在不在"。

#### 城市：逐天绑定，不顺带查"计划里没出现的城市"

```python
pairs = []                            # (date, city)
for day in plan_view.get("days") or []:
    d = _day_date(day, start)
    city = str(day.get("city") or "").strip()
    if d and city:
        pairs.append((d, city))
```

去重保序后截断到 `inject_max_cities`（默认 3）。**截断要按"与窗口有交集的天数"排序**——先保留交集天数多的城市，而不是按出现顺序无脑切前 3 个，否则一个 5 城行程可能只剩下 3 个只有 1 天的城市，把主城市丢掉。

#### 窗口：交集，不是包含

```python
lo = min(d for d, _ in pairs); hi = max(d for d, _ in pairs)
win_lo, win_hi = today, today + timedelta(days=FORECAST_WINDOW_DAYS - 1)
q_lo, q_hi = max(lo, win_lo), min(hi, win_hi)
if q_lo > q_hi:
    return 不注入(DATE_OUT_OF_RANGE)
# 只保留落在交集内的 (日期, 城市)
pairs = [(d, c) for d, c in pairs if q_lo <= d <= q_hi]
```

| 场景 | M3-2 的 `can_inject` | M3-3 的交集 | 哪个对 |
|---|---|---|---|
| `startDate=今天-2`，共 5 天 | `DATE_OUT_OF_RANGE`，不查 | 查今天到 `start+4` | **交集** |
| `startDate=今天+3`，共 2 天 | 通过，查 2 天 | 同 | 一致 |
| 全部 `startDate=今天-10` | 不查 | 不查 | 一致 |
| `startDate=今天+20` | 不查 | 不查 | 一致 |

#### 查询范围：全局一个区间，不是每城一个

每城的 `(最小日期, 最大日期)` 可能不同，理论上可以按城市各查各的（更省额度）。**第一版刻意不这么做**：

- `weather_inject._query()` 的超时/取消/排序语义是 M3-2 用一整轮修出来的（超时不能丢已完成结果、被取消的城市必须补进"没有预报"），按城市分区间就要写第二套；
- 上限本来就是 3 城 × 10 天，额度浪费有限；
- 少一条分支 = 少一个出错的地方。

代价写清楚：成都只有 1 天、昆明有 4 天时，成都会多查 3 天（拿到但渲染时被 `(date, city)` 白名单过滤掉，不进 prompt）。

#### 渲染：按 `(date, city)` 白名单过滤

`build_brief()` 会把"查到的"全渲染出来，而多查的日期必须挡掉——否则表里出现计划外的日期，模型可能把"第 6 天"的天气用进一份 4 天的行程。所以渲染后按 `pairs` 过滤 `BriefDay`，未覆盖的日期在块内明写"表中没有列出的日期没有预报"。

### 4.3 Q3：天气如何进 Prompt，如何防止编造或复制数值？

**答：进 user 消息最前面，与【当前计划】分段；防编造靠三层，其中唯一可机检的是"注入期数值闸门"。**

#### 进入位置

`build_adjust_messages` 现在输出 2 条消息：`system` + 一段 `user`（`【当前计划】\n{json}\n\n【用户要求】\n{原话}`）。改成：

```
【已核实的天气预报】
（元信息 + 覆盖范围 + 表格 + 通用使用约束 + 调整场景附加约束）

【当前计划】
{json}

【用户要求】
{原话}
```

三个刻意的选择：

1. **独立参数，不塞进 `plan_view`。** 塞进视图有两个后果：输入契约被污染（Java 不认识那个键），以及模型会把天气当成"计划的一部分"从而试图修改它。签名与 M3-2 对齐：`weather_block: str | None = None`。
2. **放最前面，而不是夹在【当前计划】和【用户要求】之间。** 后者会切断"计划—要求"这对相邻关系，而这两段的相邻性正是规则 1（itemId 必须照抄）能生效的原因。放最前面也与生成链路一致：环境 → 对象 → 指令。
3. **不进 system prompt。** system 是"规则"，天气是"数据"。M3-2 已经把这条守住（`build_plan_messages` 只改 user 消息），M3-3 沿用。

#### 调整场景的附加约束

`render_brief_block()` 输出的尾部约束是**生成场景**写的（"你可以据此调整每日安排""表中没有的日期不得编造"）。调整场景还多一条风险：**模型可能因为看到天气，顺手改动用户没提到的行程项**。所以注入块尾部追加一段（**不改 M3-2 的 `_USAGE_RULES`**，只在调整侧拼接）：

```
【本次是调整，不是重排】
- 只在用户这次的要求与天气有关时才参考上表；不要因为天气去改用户没有提到的行程项。
- 上表只用来说明「这样改是否更合理」，不要把它写进任何字段。
```

#### 三层防线

| 层 | 手段 | 可机检 | 挡什么 |
|---|---|---|---|
| 1 | Prompt：`_USAGE_RULES` + 附加约束 + system 规则 3/5/6 | 否 | 大部分"顺手写数字"的冲动 |
| 2 | **结构**：op 类型与字段白名单不变 | **是** | 模型无法"修改天气字段"——根本没有这个字段可改 |
| 3 | **校验**：注入期数值闸门 | **是** | 写进 `title`/`note`/`theme`/`summary` 的阿拉伯数字+单位 |

**闸门的具体形态**（M3-3 唯一改变"建议是否被接受"的地方）：

```python
# 只用于 M3-3 的注入期检查。刻意不复用、也不修改 contract.NUMERIC_UNIT_PATTERN：
# 那个正则服务于已冻结契约的 freeText 校验，加 "%" 会改变生成侧行为。
WEATHER_VALUE_PATTERN = re.compile(
    r"[0-9０-９]+\s*(%|％|℃|°C|摄氏度|度|级|毫米|mm|MM|厘米|cm|米/秒|m/s)"
)

_FREE_TEXT_FIELDS = ("summary",)          # + 每个 op 的 title/note/theme
```

触发条件：**本次注入过天气**。命中即 `AdjustError("建议内容里出现了天气数值，请重试")`，与现有"模型输出不合规就在本地拒绝，让用户马上重说一遍"的处置方式一致（`adjust.py` 模块文档第一段就是这个理由）。

**为什么用"拒绝"而不是"自动重试一次"**：重试会让延迟翻倍且不确定（模型可能再犯），而这条规则在 system prompt 里本来就写着，模型违反属于"输出不合规"，与它输出非法 JSON 是同一类问题，处置应当一致。若后续实测发现触发率偏高，再单独评估重试——那是 PM 要批的另一件事。

**已知限制（必须写清楚，不能装作挡住了）**：

- **中文数字漏网**：「十几度」「三十来度」「三四级风」不命中正则（`十`/`三` 不是 `[0-9]`）。扩展到中文数字会误伤正常文案（「一起」「十分」），在调整链路上误伤代价是**合法建议被拒**，比漏网更糟。
- **因此这一层是"提高成本"而不是"绝对防止"**。补它的是 §9 的 AC-A10：人工/模型抽样检查 20 条注入过天气的建议，确认没有数值转述。
- **未来一天的天气也算数值**：`note` 里写"明天有雨"是允许的（不含数字），这正是我们要的行为——约束的是数值，不是"提到天气"。

### 4.4 Q4：天气失败时，如何保证原有调整行为不变？

**答：把"注入"做成一个绝不抛异常的单点，失败即 `block=None`，并保证此时 messages 与改造前逐字相同。**

四条保证，每条都有对应的机检（§9）：

1. **绝不抛。** `prepare_adjust_weather_block()` 内部把 `fetch_forecast` 的异常、`asyncio` 的超时、`build_brief` 的空结果全部消化为"不注入"。理由与 M3-2 相同：调用方是 `run_adjust`，一旦异常穿透，用户看到的是"调整建议生成失败"——**一个纯辅助功能绝不能把主功能弄坏**。
2. **不注入时 messages 逐字相同。** `build_adjust_messages(plan_view, instruction)` 与改造后 `build_adjust_messages(plan_view, instruction, None)` 的输出用 `==` 全等断言（不是"看起来一样"）。这是 M3-2 用过的同一手法。
3. **失败不影响后续步骤。** 拿不到天气 → 照常调模型 → 照常 `validate_ops` → 照常返回。**不做**"没天气就不调模型"这类降级，也不做"天气失败时降级成 mock"。
4. **闸门只在注入过时生效。** 没有天气就没有数值可抄，此时拒绝一条不含天气数值的建议是纯粹的误伤。所以 `validate_ops` 的追加检查以 `weather_injected` 为前置条件 —— **关闭开关时，`validate_ops` 的行为与今天逐字相同**。

### 4.5 Q5：延迟预算、缓存、埋点

**答：预算 1200ms（比生成链路小 40%）；复用 M3-2 的 60 秒短缓存且两链路共享同一份；两条新埋点，字段比 M3-2 多一个 `cached`。**

#### 预算：1200ms，理由是三段加法

调整链路没有流式输出（§2.3），用户等待 = `天气耗时 + 模型耗时`。以实测口径估算：

| 段 | 现状（无天气） | 注入后 | 说明 |
|---|---|---|---|
| 天气查询 | 0 | 缓存命中 <5ms / 未命中 100–300ms（3 城并发） | M3-2 实测冷启动建连接约 66ms |
| 模型（JSON 模式，非流式） | 主耗时 | 不变 | 注入只增加 prompt 长度 |
| 合计增量 | — | 典型 ~300ms，上限 1200ms | |

M3-2 的 2000ms 是按"SSE 已先给出 intent，用户有东西可看"定的。调整链路没有这个前提，2s 会把"改个备注"这种秒级操作变成 2s+，感知劣化明显。1200ms 覆盖 3 城并发的正常耗时（3×300ms 的串行最坏情况是 900ms，并发下远小于此），超出即视为上游异常、不注入。

配置上**独立**一个 `inject_adjust_timeout_ms`，而不是复用 `inject_timeout_ms`：两条链路的延迟形态不同，将来单独调一条不该影响另一条。

#### 缓存：共享 M3-2 的那一份

同一场行程的典型操作序列是「生成 → 确认 → 调整第 2 天 → 再调整第 4 天」。如果调整链路自带一套缓存，第二次调整就要把刚查过的城市重查一遍——既费额度，又让延迟不可预测（用户不知道这次会不会等 300ms）。

所以**两链路共用 `weather_inject` 里的 `_cache`（键结构不变：`(provider, city, start, days)`）**。代价是最多 3 城 × 10 天的小字典，收益是"连续调整几乎全是命中"。

**明确不保证的**：跨链路命中率不保证。生成时用的是 `[startDate, startDate+days)`，调整时用的是交集区间，键不同就命中不了。要提升得把键从"区间"改成"按天"，那属于 M3-1 缓存语义，本阶段不做（列为 §8 的可选项）。

#### 埋点：两条，日志级，不进任何对外契约

| 埋点 | 字段 |
|---|---|
| `weather_adjust_injected` | `trace` / `cities` / `covered` / `uncovered` / `days` / `pairs` / `upstream` / `cached` / `elapsedMs` |
| `weather_adjust_skipped` | 同上 + `reason` + `detail`（逐城原因，如 `成都:CIRCUIT_OPEN`） |

- 与 M3-2 的 `weather_injected` / `weather_skipped` **分成四个名字**：日志分析时必须能区分链路，否则"今天天气调用了多少次"会被重复计数。
- `cached` 是 M3-3 新增字段，也是唯一能验证"缓存真的省了"的数字（对应 AC-A9）。
- **不记对话原文、不记完整天气包、不记 plan_view**（03 §4.2 出境原则）。
- 另加一条 `adjust_done trace=... weatherMs=... totalMs=...`，把 §4.5 的三段加法变成可监控的数字。这条同时补上了 V-3 里登记的"调整链路没有分段耗时"的空白。

### 4.6 Q6：如何保证契约、校验器、状态机不被污染？

**答：四个"零"加一条"仅注入期生效"，全部可机检。**

#### ① 契约：零新增字段

- `contracts/travel-plan/` **一行不改**。天气不进计划，调整产出也不是计划。
- `/plan/adjust` 的**响应体字段集不变**：仍是 `{summary, ops, mock}`。AC 用"键集合相等断言"，多一个键就红。
- **不在计划里留痕。** 生成链路靠 `attach_ai_note()` 在 `aiNote` 里写"参考了哪份预报"；调整链路**不能**这么做，因为 ① 调整产出的是 ops，写 `aiNote` 需要一个新 op 或改 Java；② 那是修改用户可见的计划内容，超出"只加可选上下文"的边界。代价是用户看不到"这次用了天气"，接受。

#### ② 校验器：白名单不动，只加一条前置条件检查

- `OP_TYPES`（6 种）、`ITEM_FIELDS`（4 个）、`DAY_FIELDS`（2 个）、`MAX_OPS=20`、`HH_MM` —— **全部不动**。
- 模型如果想"把第 2 天的天气改成小雨"，它需要 `field="weather"`，白名单里没有 → 直接拒绝。这是结构级的防线，不依赖 prompt。
- 唯一新增：注入过天气时，`summary`/`title`/`note`/`theme` 不得含天气数值（§4.3）。**未注入时该检查不执行**，所以"关闭开关 → 校验器行为逐字相同"。

#### ③ 状态机与乐观锁：不动，但要承认一个副作用

`/plan/adjust` 是"读视图 → （新增：查天气）→ 调模型 → 回 Java 用 `base_version` 确认"。状态迁移、版本号、`PLAN_VERSION_CONFLICT` 的处理全在 Java，M3-3 一行不碰。

**但必须承认**：注入把"确认前的窗口"拉长了最多 1200ms，同一计划在这段时间内被别人改动时，冲突概率上升。缓解与现状：

- 预算小（1200ms），且缓存命中时接近 0；
- 冲突已有确定的用户提示（`PLAN_VERSION_CONFLICT`），不是静默失败；
- **不做自动重试**（重试会掩盖真实的并发冲突，也会让天气再查一次）。

这是一个**已知影响**，不是"没问题"。若实测冲突率上升明显，第一选择是关掉开关，而不是加补偿逻辑。

#### ④ 输入契约：`plan_view` 结构不变

天气**不**写进 `plan_view`（§4.3 第 1 点）。所以 Java 侧的 `build()` 一行不改，`AdjustRequest` 的字段也不变。

#### ⑤ 机检：递归扫描

复用 M3-2 的 B.8 手法：对 `/plan/adjust` 的完整响应做递归扫描，出现 `weather` / `temperature` / `precipitation` / `wind` / `humidity` 任一键即 FAIL。同时正着扫一遍 ops 的 JSON 文本，确认没有 `℃` / `%` / `级`。

### 6.2 新增配置（`WeatherSettings`，全部默认关闭/保守）

### 6.3 内部数据结构

```python
@dataclass(frozen=True)
class AdjustWindow:
    allowed: bool
    reason: str | None
    pairs: tuple[tuple[str, str], ...]   # (ISO 日期, 城市)，已按交集过滤、已截断
```

刻意**不复用** `InjectDecision`：它的 `cities`/`days` 是"多城共用一个区间"的形状，而调整场景需要 `(日期, 城市)` 的逐天对应。硬套会让"哪天在哪个城"这个关键信息在类型上就丢了。

#### S4 的 12 个场景（逐条对应 AC）

每场都必须断言三件事：**① `code=0` 且 `ops` 通过 `validate_ops`（任何天气故障都不能让调整失败）；② 上游调用次数符合预期；③ 响应键集合不变**。每场前后 `weather_circuit.reset_all()`。

| # | 场景 | 期望 reason | 上游调用 | 关键断言 |
|---|---|---|---|---|
| 1 | 开关关闭（默认） | `INJECT_DISABLED` | 0 | messages 与改造前 `==` 全等 |
| 2 | 数据源未启用 | `PROVIDER_DISABLED` | 0 | 同上 |
| 3 | 计划日期全缺（`date` 全 null 且 `startDate` null） | `NO_START_DATE` | 0 | 不兜底成今天 |
| 4 | 行程全在 10 天外（`startDate=今天+20`） | `DATE_OUT_OF_RANGE` | 0 | — |
| 5 | 行程全已过去（`startDate=今天-10`，共 3 天） | `DATE_OUT_OF_RANGE` | 0 | — |
| 6 | **行程跨今天**（`startDate=今天-2`，共 5 天） | 注入 | 1–3 | 只查今天起的天；AC-A6 |
| 7 | 城市无坐标（`CITY_UNKNOWN`） | `NO_CITY`/逐城 `CITY_UNKNOWN` | **0** | 坐标未知不得出网 |
| 8 | 全部城市查询成功 | 注入 | 城市数 | 每城只绑自己的日期 |
| 9 | 部分城市失败（成都 ok / 乐山 500） | 注入（部分） | 城市数 | 乐山进 `uncovered`，不写进成都行；AC-A7 |
| 10 | 全部城市失败（500） | `NO_DATA` + `detail=…:UPSTREAM_ERROR` | 城市数 | 块不注入，仍出建议 |
| 11 | 一慢多快（乐山 5s / 成都正常，预算 600ms） | 注入（部分） | 城市数 | 整请求 ≈ 预算 + 模型耗时；被取消城市进 `uncovered` |
| 12 | 连续两次相同请求（缓存命中 / 过期） | 注入 | 第二次 0 | 第二次 `weather_ms ≤ 5`；AC-A9 |

第 11 场是唯一能同时验证"超时用已完成的部分"和"被取消的城市不能沉默"的一场——这两条正是 M3-2 用一整轮才修对的语义，M3-3 复用同一份实现（D-A5）就是为了不重犯。

## 13. 实施回填：实测数据与偏离（2026-11-24）

S1~S4 已落地（默认关闭）。这一节只记**与设计稿不一致的地方**和**只有真跑才知道的数字**；
验收明细见 [`M3-3-S4-故障矩阵与延迟-验证报告`](../acceptance/M3-3-S4-故障矩阵与延迟-验证报告.md)。

### 13.1 与设计稿的偏离

| 项 | 设计稿 | 实际 | 原因 |
|---|---|---|---|
| 数值闸门位置 | 写在 S3 标题下，容易被读成"给 `validate_ops` 加参数" | **独立函数 `validate_weather_values`，由调用点在注入时为真才调用** | 只有这样才能让"`validate_ops` 一个字符没改"成为 `git diff` 可证的事实，而不是靠测试论证 |
| 闸门单位表 | "数字 + 天气单位" | 只认 `% ℃ ° 度 级 毫米 mm cm 米/秒 m/s`，**不认**分钟/小时/元/公里 | 后者是行程本身的单位，拦它们等于顺手改了调整规则 |
| 覆盖范围断言 | 断言"乐山进 `uncovered`" | 另加断言"乐山**不出现在表里**"、"成都的行只挂自己的日期" | "写进未覆盖"与"没有串到别人头上"是两件事，验收要分别钉 |
| S4 的 12 场景 | 12 行全部是上游/配置故障 | 落成 **20 段 / 63 项**：PM 点名的 12 类 + 设计稿里 4 类本地判定（未启用/无坐标/越窗/跨今天）+ 白名单、并发、缓存、响应结构、闸门触发率 | 设计稿那 12 行的口径混了"上游怎么坏"和"挡在出网之前"，拆开后判据更单一：后者统一断言"上游调用 = 0" |

### 13.2 实测数字

- **故障矩阵**（`verify_adjust_weather_matrix.py`）：20 段 **63 项断言，PASS 63 / FAIL 0 / SKIP 0**。
  `code=0` + `ops` 合法出现在 15 个不同故障下；7 种"不该查"的情形上游调用 **全为 0**。
- **延迟**（`measure_adjust_latency.py`，每组预热 2 次）：A 关闭 `total P50 124ms`；
  B 缓存热 **+0ms**；C 上游 5s、预算 1200ms → `total P50 1339ms`、天气耗时
  `P50 1211 / P95 1213ms`，**增量 +1215ms ≈ 预算（101%）**。三组 `code` 全为 0。
- **闸门触发率**：未注入 + 违规文本 0/20 拦截；注入 + 违规文本 20/20；
  注入 + 干净文本 **0/20 误伤**（目标 <5%）。
- **测试基线**：Python **350**（288 + 24 + 18 + 20）/ Java **192 run 0 fail 0 error（65 skipped，零改动）** / 前端 **12 脚本**（零改动）。

### 13.3 三个只有真跑才知道的事实

1. **"第二次 weather_ms ≤ 5"不能用墙钟量。** 客户端墙钟里混着模型与 HTTP 开销，
   第二次命中缓存时总耗时仍有 125ms 左右。只有埋点的 `elapsedMs` 才是天气占的时间（实测 0ms）。
   验证脚本因此挂了一个日志 handler 去读埋点，而不是改产品代码加返回值。
2. **响应键集合的比对必须排除被闸门拒绝的那批。** 拒绝响应是既有的 `AdjustError` 形状
   （`{code,message,data:null,traceId}`），与成功响应的 `{summary,ops,mock}` 天然不同。
   第一次把两类混在一起比，20 个"不一致"全是真阳拦截，假红一次。
3. **超时断言不能卡 1.0 倍预算。** 300ms 预算下 320ms 也会出现，CI 上必然假红；
   真正钉死"预算是整请求的、不是每城一份"的是 C 组的 +1215ms，不是单请求的墙钟。

### 13.4 剩余未做

- 真实上游（和风）在调整链路上的耗时分布：本切片全程用替身，量的是"注入增量"。
- 真实模型对天气数值的转述率（AC-A10 的抽样是构造用例，只能证明闸门对中文数字不生效）。
- 生产环境多实例下的版本冲突概率（属 Java 侧 CAS，本次未动）。
- 开关的生产开启决策：`WEATHER_INJECT_ON_ADJUST` 仍默认 `false`，等 PM 决定灰度范围。
