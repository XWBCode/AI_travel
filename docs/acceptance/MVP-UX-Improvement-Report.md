# MVP 体验走查与改进建议

> 基线：`main` @ `2e27428`（修复后 `06b2b55`）
> 方式：Edge + 内置浏览器实机走查，覆盖「新用户第一次进来」和「已有计划的日常使用」两条路径。
> 原则：只记录**影响用户理解或操作**的问题；不为了好看重做前端（PM 明确要求）。

---

## 1. 结论

**核心闭环没有阻断性体验问题，空状态是这一轮做得最扎实的部分。**
真正值得改的是两处「信息表达」问题（BUG-004/005）和一处测试资产缺口（BUG-003），
都属于 D 组，不影响发布判断。

## 2. 走查路径与结论

| # | 场景 | 观察 | 结论 |
|---|---|---|---|
| 1 | 新用户首次进入「我的旅行」 | 「还没有行程」+ 一句示例「在 AI 助手里说一句『帮我规划成都三天』」+ 两个入口按钮（去聊一个行程 / 去 AI 助手） | ✅ 引导闭环，不需要猜下一步 |

| 5 | 说一句话出计划 | 摘要 + 结构化卡片（标题/目的地/天数/待核实/前 2 天预览/展开全部/查看详情） | ✅ 卡片自解释，不看 Markdown 也懂（AC-10） |
| 6 | 卡片上的「待核实」 | 「部分信息待核实（行程安排 · 预算）：天气、票价与路况尚未接入实时数据」 | ✅ 已改（BUG-004）：卡片不报内部数，详情页可展开分类 |
| 7 | 详情页操作区 | 按状态给不同按钮（编辑/确认行程、调整行程/开始行程/取消行程） | ✅ 状态与按钮一一对应，不会给不该点的按钮 |
| 8 | 通知铃铛 | 内联 SVG 铃铛，未读时提亮 + 红点数字（>99 显示 99+） | ✅ 已改（BUG-005） |

## 3. 建议改进项（按性价比排序）

### 3.1 「待核实」的表达方式（P2，✅ 已做，2026-11-23）

**现状（改前）**：卡片首屏就有「74 个字段待核实」。
**问题**：这是内部计量单位。用户读到的是「这软件什么都不知道」，而不是「哪些数字需要你自己确认一下」。
**建议**：
- 卡片上改为分类提示：`天气 / 票价 / 路况 未接入实时数据`，数字收进详情页；
- 详情页保留精确计数，并支持展开逐项查看（现在只有数字，没有清单）。

**实际做法**：三处分开处理，数字只留在详情页。

| 位置 | 改后文案 |
|---|---|
| 对话里的计划卡片 | `部分信息待核实：行程安排 · 预算等尚未接入实时天气、票价与路况` |
| 我的旅行列表 | `部分信息待核实`（hover 提示「打开详情看具体是哪几类」） |
| 计划详情页 | `共 48 处信息待核实` + 原因 + 可展开的 `行程安排 42 处 · 宽窄巷子… 等 12 项` |

分类由 `src/utils/planFacts.ts` 从计划结构派生（`verified=false` 的 FactField 归四类），
**不重算权威总数**——数字仍以服务端 `unverifiedFieldCount` 为准。回归测试 16 项。

### 3.2 铃铛换内联图标（P3，✅ 已做，2026-11-23）

emoji 在不同系统上字形差异大，浅色底上偏暗。换成与「服务正常」胶囊同权重的 SVG 图标即可。
附带好处：可以用 `currentColor` 跟主题走。

**实际做法**：18px 描边 SVG，默认 `#5b6572`（与胶囊同灰阶），有未读时提亮为品牌色；
按钮固定 26×26，红点不再随 emoji 字形基线抖动。

### 3.3 通知列表「加载更多」（P2，数据多了再做）

现在固定取最近 20 条，超出只显示「仅显示最近 20 条」。MVP 阶段一个用户的通知量很小，
等真实使用中出现翻页需求再加，现在加等于做没人用的功能。

### 3.4 计划卡片的第二行信息密度（P3，✅ 已定，2026-11-23）

现在显示「目的地 · N 天」。可以补「人数 / 出发日」，但需要先解决「哪些字段经常为空」的问题——
mock 阶段这些字段几乎都空，看不出真实分布。**等真实模型跑过 20 次再决定**。

**决定：维持「目的地 · 天数 · 人数 · 出发日」的条件渲染，不加、不改。**

依据（真实模型 19 份计划回采）：`travelers` 有值 9/19（47%）、`startDate` 有值 10/19（53%），
且 null 状态与 `missingFields` **零矛盾**。也就是说这行有近一半的概率带上「N 人 / X 月 X 日出发」，
没有的时候自然省略，不会出现「0 人」「待定」这类占位噪音。
再补别的字段（预算、兴趣）会把这行拉长到读不完，价值不如风险大。

## 4. 明确不做的（避免过度设计）

| 想法 | 为什么不做 |
|---|---|
| 重做前端视觉体系 | PM 明确要求，且当前没有影响理解的视觉问题 |
| 通知支持「删除单条」 | 通知量小，标记已读足够；删除功能会引入「删了还想找回来」的新需求 |
| 列表页加无限滚动 | 现在 20 条一页，用户平均计划数远小于此 |
| 卡片内直接打勾 | 打勾需要当前「第几天」的上下文，卡片里做会与当日执行页产生第二套语义 |

## 5. 本轮已顺手修掉的体验问题（来自实现过程中的实机验证）

1. **铃铛不是按钮**：原本是 `<span>` 加点击事件，键盘不可达、读屏不识别 → 改为 `<button>` 并补 `aria-label`。
2. **通知项不是按钮**：同上，列表项改为 `<button>`，获得焦点态与键盘可达。
3. **点通知后弹层不收起**：跳转后弹层仍挂在页面上挡住内容 → `v-model:visible` 显式收起。
4. **红点滞后 30 秒**：点完操作抬头看铃铛是空的 → 写请求成功后广播 `app:mutation` 立即重算。
5. **轮询失败刷屏**：网络断了每 30 秒弹一次「网络异常」→ 轮询请求带 `skipErrorToast`。
