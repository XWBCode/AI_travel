> 前置已完成：M3-1 天气接入（验收关闭）、A 项连续故障验证、`CIRCUIT_OPEN` 跨层、stale 原因传递

## 0. 一句话

让模型在**排行程的时候**就知道那几天大概什么天气，从而把户外/室内、早晚强度安排得更合理；
拿不到天气时**完全退回今天的行为**，不降级、不阻塞、不留占位数字。

---

## 1. 目标用户场景与要解决的问题

### 1.1 现在是什么样

M3-1 把天气做成了**计划落库之后的附加展示**：用户打开计划详情页，看到"D1 11-24 成都 多云 11–16℃"。
天气和行程是**两块并列的信息**，互不影响：

- 行程第 2 天排了青城山徒步；
- 同一天天气预报是中雨；
- 用户得自己把这两件事联系起来。

`PlanController` 完全不引用天气（这一点在 A 项验证时被当作"核心链路解耦"的结构性证据），
所以今天**天气对生成结果零影响**。

### 1.2 M3-2 要解决什么

把"这两件事得用户自己联系"变成"系统在排的时候就考虑到了"。

具体到用户能感知的差别：

| 场景 | 今天 | M3-2 之后 |
|---|---|---|
| 11 月底成都 3 天，第 2 天预报中雨 | 第 2 天照样排青城山徒步，用户在详情页自己发现冲突 | 第 2 天优先排室内（博物馆/茶馆），户外项挪到第 1 或第 3 天；`aiNote` 说明"已参考预报" |
| 预报全天 35℃ | 照常排正午户外 | 正午安排室内/休息，户外挪到早晚 |
| 用户没说日期 | 正常生成 | **不变**（没有日期就没有天气可查） |

### 1.3 不解决的问题（明确非目标）

1. 不做"为了拿天气而追问日期"。对话流程不变。
2. 不做天气的实时刷新影响已生成计划。生成是一次性快照。
3. 不把天气写进计划契约（见 §4 决策点 D1）。
4. 不改 M3-1 已验收的天气链路（缓存/熔断/降级枚举/端点一行不动）。
5. 不做"雨天自动改期/退票"这类外部动作。

## 2. 一个必须先说清的现实：M3-2 的适用面比听起来窄

这是本设计最重要的一节。如果这一节判断错了，后面全是白做。

### 2.1 天气依赖"目的地 + 日期"，而这两者今天在生成**之前**已经有了

`backend-ai/app/plan/intent.py` 的 `analyze_messages()` 是**纯规则**（毫秒级、不调模型），
它的 `slots` 里已经有：

```
destination / destinations / startDate / endDate / days / originCity / travelers / budget / interests …
```

`/plan/intent` 端点已经把它返回给 Java 建草稿用（`slots` 字段）。
**所以"生成前拿不到城市和日期"这个担心不成立**，不需要为此增加一次 LLM 调用。

### 2.2 但 `startDate` 有相当比例是 null

`09-M3-1-天气接入设计.md` §4.3 记着实测：真实 20 条计划里 **10 条有 `startDate`，6 条小样本全为 null**。
用户常说"云南五天""下个月去成都"，规则能抽到天数，抽不到确定日期。

**没有日期 = 没有"哪天的天气" = 无法查。** 这不是实现问题，是语义问题：
拿"今天"顶替就是 09 文档里被否掉的 B 方案（看起来最像真数据的假信息）。

### 2.3 还有一层：预报窗口只有 10 天

即使有 `startDate`，出行日期超过 10 天也查不到（和风天气官方上限）。
十一月初规划十一月下旬的行程，是这类产品的典型用法，**这条会拦掉很大一部分**。

### 2.4 结论：M3-2 必须是"有则用、无则不提"

综合 §2.2 / §2.3，可用的比例大致是"有明确日期 且 日期在 10 天内"。
这个比例**不高**，而且会随用户习惯变化。

所以设计的基调定死：

> **天气是可选增强，不是生成的前置条件。** 拿不到 → 生成流程与今天**逐字相同**，
> 不增加提示、不增加延迟、不写任何"天气待核实"的占位。

这条如果反过来做（比如"没天气就降级生成质量"或"没天气就提示用户补日期"），
就等于用一个小众场景去拖累主路径。

> **需要 PM 确认的判断**：如果 PM 认为"M3-2 的价值必须覆盖大多数请求"，
> 那这个方案不满足，需要先做"日期追问交互"（本稿明确不做）。请在第 7 节 D2 拍板。

## 3. 功能范围

### 3.1 做

| 编号 | 内容 |
|---|---|
| F1 | 生成前用 `slots` 判断能否查天气：`destination` 非空、`startDate` 非空、且首日在预报窗口内 |
| F2 | 能查则查（多城并行、有总预算上限），把结果压成一张紧凑的"已核实天气表" |
| F3 | 把这张表作为**已核实事实**注入计划生成的 user 消息（不改 system prompt 的规则段） |
| F4 | system prompt 增加一段"如何使用天气表"的约束：只能用于安排决策，不得改写数值、不得扩展到表外日期、不得据此编造其他实时信息 |
| F5 | 计划 `aiNote` 追加一句"本计划生成时参考了 X 的天气预报（获取时间 …）" |
| F6 | 埋点：`weather_injected` / `weather_skipped(reason=…)`，含耗时与城市数 |
| F7 | 开关 `WEATHER_INJECT_ON_GENERATION`，**默认 false** |

### 3.2 不做

- 不新增计划契约字段（§4 D1）
- 不改 `fetch_forecast` / 缓存 / 熔断 / 降级枚举（PM 明确要求不顺手重构）
- 不改调整链路 `/plan/adjust`（§4 D3，建议留到 M3-3）
- 不改前端任何代码（本设计前端零改动）
- 不做日期追问、不做生成前的天气预览
- 不做"天气变了自动重排"

## 4. 需要 PM 拍板的决策点

| 编号 | 决策 | 选项 | 建议 | 理由 |
|---|---|---|---|---|
| **D1** | 天气要不要写进计划数据 | A 只进 prompt（计划里没有天气字段）<br>B 同时写进计划（`days[].weather` 之类） | **A** | B 要改**已冻结**的 v1 契约（`08` 要求破坏性变更升 1.1 并保留回滚），而 M3-1 已经把天气做成了独立端点。两处填同一件事，早晚不一致 |
| **D2** | 适用面窄是否可接受 | A 接受（有则用）<br>B 先做日期追问再谈 | **A** | B 改对话流程，是另一个切片的体量；且"追问用户日期"本身有打扰成本 |
| **D3** | 调整链路 `/plan/adjust` 是否同期注入 | A 不做<br>B 同期做 | **A（留 M3-3）** | 调整时计划已落库、`basic` 齐全，适用面比生成更大——正因为它更值得做，才更该单独验收，别混在一个切片里 |
| **D4** | 多城行程怎么办 | A 只查主目的地<br>B 查前 3 个城市并行 | **B** | `destinations` 本来就有多个；只查主城会给出"部分城市有天气"的误导。3 个是额度与预算的折中 |
| **D5** | 生成期天气查询要不要加缓存 | A 不加（靠熔断保护）<br>B 加 60s 进程内短缓存 | **B** | 用户连点"重新生成"会重复打上游；60s 短缓存成本极低。但**不动** M3-1 的 Java 缓存 |

## 5. 前后端交互与数据流

### 5.1 今天

```
Vue ──POST /api/chat/stream──▶ Java ──SSE──▶ Python
                                              ├─ analyze_messages(history) → intent.slots
                                              └─ run_generation → LLM → 校验 → 落库
Java 落库后，Vue 另外调 GET /api/plans/{id}/weather（M3-1，独立端点）
```

### 5.2 M3-2 之后（只在 `run_generation` 内部插一步）

```
Python
  ├─ analyze_messages(history) → slots（已有，零成本）
  ├─ [新] 判断能否查天气：slots.destination && slots.startDate && 首日在窗口内
  │        ├─ 能 → asyncio.gather(每城 fetch_forecast, timeout=2s)
  │        │        ├─ 有数据 → 构造"已核实天气表"块
  │        │        └─ 全失败/超时/熔断 → 视为"无天气"，不阻塞
  │        └─ 不能 → 直接跳过（记 weather_skipped 埋点）
  ├─ [改] build_plan_messages(history, weather_block) → user 消息前面加一段
  ├─ LLM → 校验 → done
  └─ [改] aiNote 追加"参考了天气预报"说明（仅当真的注入了）
```

**关键约束**：
- 天气查询发生在**第一次 LLM token 之前**，所以它对用户感知的影响是"首字延迟"。
  硬预算 **2 秒**（`asyncio.wait_for`），超时用已完成的部分；一个城市都没成就当没天气。
- 天气查询与 LLM 调用**不并行**：注入内容必须先有，才能进 prompt。
- 这一段**不写进 SSE 事件流**：前端不需要知道"正在查天气"。
  如果以后要显示，再单独加事件（本稿不做）。

### 5.3 为什么注入在 user 消息而不是 system prompt

- system prompt 的"规则段"由 `contracts/travel-plan/plan_rules_v1.json` 渲染，
  Python 提示词与 Java 校验器读同一份，CI 会拦"只改一侧"（见 `prompts.py` 的注释与 BUG-008/BUG-014 教训）。
  往里塞运行时数据会让这份文件不再是"纯规则"。
- 天气表是**本次请求的数据**，天然属于 user 消息（和 `build_adjust_messages` 里
  "【当前计划】/【用户要求】"分段同一路数）。
- 用户原话仍然单独成段、原样放入，不做字符串拼接（总纲 8.1 防注入）。

## 6. 接口、数据结构、页面

### 6.1 外部接口：**零变更**

| 接口 | 变更 |
|---|---|
| `POST /plan/generate`、`POST /plan/stream`、`POST /plan/adjust` | 请求/响应体**不变** |
| `GET /v1/weather` | 不变（只是多了一个内部调用方） |
| `GET /api/plans/{id}/weather` | 不变 |
| 计划契约 `travel_plan_v1.json` | **不变**（D1 选 A 时） |
| 前端页面 / 组件 | **不变** |

**这一点是刻意设计的**：M3-2 全部改动落在 Python 进程内部，
外部契约与前端零改动，所以它可以独立开关、独立回滚。

### 6.2 新增配置（Python）

| 键 | 默认 | 说明 |
|---|---|---|
| `WEATHER_INJECT_ON_GENERATION` | `false` | 总开关。**默认关**，与 `weather.provider` 默认 `none` 同一风格：外部依赖没显式打开就不默默用 |
| `WEATHER_INJECT_TIMEOUT_MS` | `2000` | 注入阶段的硬预算 |
| `WEATHER_INJECT_MAX_CITIES` | `3` | 多城上限 |
| `WEATHER_INJECT_CACHE_SECONDS` | `60` | 生成期短缓存（D5 选 B） |

### 6.3 内部数据结构

```python
@dataclass(frozen=True)
class WeatherBrief:
    """注入用的一张表。构造完即不可变，避免下游不小心把未核实字段混进来。"""
    cities: tuple[str, ...]
    fetched_at: str          # 工具真实获取时间（来自 ProviderResult）
    days: tuple[BriefDay, ...]   # 只含 verified=true 的字段
    attribution: str         # 署名义务，转述给 aiNote
    source: str

@dataclass(frozen=True)
class BriefDay:
    date: str
    city: str
    weather_text: str | None
    temp_range: str | None      # "11–16℃"，直接复用 M3-1 的 display 拼法
    precip_prob: str | None     # "降水概率 30%"
    wind: str | None
```

`WeatherBrief` 只能由 `fetch_forecast` 的结果构造：
`verified=false` 的字段一律丢弃，不做"缺就补 N/A"——补了就会变成一行看似完整的假数据。

### 6.4 注入块长什么样（示例）

```
【已核实的天气预报】
以下数据来自天气服务（和风天气），获取时间 2026-11-24T11:05:00+08:00，仅覆盖表中列出的日期。
你可以据此调整每日安排（例如把户外项放到天气更好的那天、雨天优先室内），
但**不得改写表中任何数值**，也不得为表中没有的日期编造天气。

| 日期 | 城市 | 天气 | 气温 | 降水概率 | 风 |
|---|---|---|---|---|---|
| 2026-11-24 | 成都 | 多云 | 11–16℃ | 30% | 2 级 |
| 2026-11-25 | 成都 | 中雨 | 10–14℃ | 80% | 3 级 |
| 2026-11-26 | 成都 | 阴 | 12–17℃ | 20% | 2 级 |
```

**注意"不得改写数值"这句必须出现**：模型看到一张表，最自然的动作是"复述进计划"。
而计划契约里没有天气字段，它只能在 `theme` / `note` / `aiNote` 这类自由文本里写，
一旦写错数字就是**新的编造来源**。这句话堵的就是这条。

## 7. 失败、降级、权限、边界

### 7.1 降级矩阵（全部沿用 M3-1 已验收的语义，不新增枚举）

| 场景 | 行为 | 用户能感知的差别 |
|---|---|---|
| `WEATHER_INJECT_ON_GENERATION=false` | 完全不查、不注入 | 与今天完全一致 |
| `slots.destination` 为空 | 跳过 | 无（这种请求本来也会走追问） |
| `slots.startDate` 为空 | 跳过，**零上游调用** | 无 |
| 首日超出 10 天窗口 | 跳过（`DATE_OUT_OF_RANGE` 语义） | 无 |
| 城市解析不出来（`CITY_UNKNOWN`） | 该城丢弃；全丢则跳过 | 无 |
| 上游 5xx / 超时 | 熔断器计数；本次视为无天气 | 无（但 `aiNote` 不写"参考了天气"） |
| 熔断器已打开（`CIRCUIT_OPEN`） | 直接视为无天气，**不重试** | 无 |
| 查询超过 2s 预算 | 用已完成的部分；一个都没成则跳过 | 首字最多慢 2s |
| 部分城市成功 | 只注入有数据的城市，块里写明覆盖范围 | 无 |

**统一原则**：任何降级都不产生"看起来像真实数据"的占位。
这条是 `03` §4 的原话，M3-2 没有例外。

### 7.2 权限与合规

| 项 | 处置 |
|---|---|
| 数据出境 | 只发"城市名 + 日期"给天气服务，不含 userId / 手机号 / 对话原文 |
| 署名 | `attribution` 从 `ProviderResult` 取，转述进 `aiNote`（详情页仍由 M3-1 那条路展示，不重复） |
| 日志 | 记 `traceId` / 城市数 / 耗时 / 结果枚举，**不记**对话原文与完整天气包 |
| 生产源 | 仍受 `WeatherProviderGuard` 硬约束：非 dev/test 用 open-meteo 直接起不来 |
| 商用授权 | M3-2 不改变 D-03 已定的商用路径 |

### 7.3 边界

- **预报不是事实**：`aiNote` 措辞用"预报"而不是"天气"，避免把 10 天预报说成确定信息。
- **只影响安排，不影响事实字段**：预算、门票、交通耗时一行不动。
- **不承诺一致**：生成时注入的天气快照与用户几分钟后在详情页看到的那份**可能不同**
  （TTL 60 分钟 + 上游更新）。这是已知不一致，本设计不试图消除——
  消除它要跨进程共享快照，属于 D1 选 B 才需要解决的问题。

## 8. 验收标准与测试方案

### 8.1 验收标准

| 编号 | 标准 | 判据（机检） |
|---|---|---|
| AC-1 | 能查且查到 → 注入生效 | 构造的 messages 含"【已核实的天气预报】"块，且列为 `verified=true` 的天 |
| AC-2 | 注入后 `aiNote` 提到参考了预报 | `aiNote` 含"预报"且含获取时间 |
| AC-3 | 不改契约 | 生成的计划 JSON 里**不出现** `weather` / `temperature` / `precipitation` 键（递归查） |
| AC-4 | 无日期不查 | 断言上游调用计数 = 0 |
| AC-5 | 超窗口不注入 | 上游调用 0 或结果被丢弃，最终无注入块 |
| AC-6 | 上游失败不阻塞生成 | 500/超时下生成成功率 100%，注入块缺席 |
| AC-7 | 熔断期不重试 | 熔断后连续 N 次生成，上游调用计数不增长 |
| AC-8 | 默认关闭 | 不配开关时，上游调用计数恒为 0 |
| AC-9 | 首字延迟增量受控 | 注入开启且上游超时，首字延迟增量 ≤ 2.5s |
| AC-10 | 前端零改动 | `git diff` 里 `frontend/` 无变更 |

### 8.2 测试方案

**单测（Python，无网络）**
- `build_weather_brief()` 纯函数：`ok` / 部分天 / 全失败 / 空 days / 只有 1 个城市成功 → 各自产出或返回 `None`
- `can_inject(slots)` 矩阵：destination×startDate×窗口边界（今天/第 10 天/第 11 天）
- 注入块渲染：只出现 `verified=true` 的字段；表外日期不出现

**端到端（复用 A 项已验证的故障设施）**
- 用 `scripts/fault_upstream.py` 的替身 + 一个"回声 provider"（把收到的 messages 落盘），
  断言注入块内容；再切 `http_500` / `timeout` / 熔断，断言降级。
- 复用 `run_fault_server.py`，不新增故障注入机制。

**回归**
- M3-1 的 231 项、Java 192 项、前端 48 项必须全绿且**零改动**
- 开关关闭时，生成链路的行为与改动前逐字一致（可用"同一输入两次生成的 messages 相同"断言）

## 9. 实施拆分

| 步 | 内容 | 可独立评审 | 可独立回滚 |
|---|---|---|---|
| S1 | `build_weather_brief()` / `can_inject()` / 注入块渲染 + 单测（**不接线**） | 是 | 是（纯新增文件） |
| S2 | 接线进 `run_generation`，加 4 个配置项与 2 个埋点，默认关闭 | 是 | 是（开关） |
| S3 | 端到端故障矩阵（AC-4~AC-9） | 是 | 是（脚本独立） |

## 12. 实施回填：实测数据与偏离（2026-11-24）

S1/S2/S3 已落地，这里只记**与设计稿不一致的地方**和**只有真跑才知道的数字**。

### 12.1 与设计稿的偏离（全部经过 PM 批复或在批复范围内）

| 项 | 设计稿 | 实际 | 原因 |
|---|---|---|---|
| 注入位置 | "user 消息前面加一段" | 放在**最后一条** user 消息最前面，用「【用户需求】」分段，用户原话逐字在后 | 新增一条 user 消息会让模型以为用户多说了句话；分段等同于 `build_adjust_messages` 的做法 |
| 超时实现 | `asyncio.wait_for` | `asyncio.wait(timeout=…)` + 取消 pending，并把被取消的城市补进 `uncovered_cities` | `wait_for(gather())` 超时会连已完成结果一起丢；且"沉默地不提这座城"比"说明它没数据"更危险 |
| `aiNote` 附注 | 模型/程序写 | **程序**用真实元数据拼，并在追加前按契约 `freeText` 自检（数字+单位、≤500 字） | 附注的全部意义是"我们确实用了哪一份数据"，不能让模型编；不合规时**不加**，而不是把合格计划判成不合格 |
| 跳过原因埋点 | `weather_skipped(reason=…)` | 另加 `detail=逐城原因`（如 `成都:CIRCUIT_OPEN`） | 只说 `UPSTREAM_ERROR` 会让"熔断（没出网）"与"真 500"在日志里同形 |
| 查询天数 | 只说了 `days` | 补 PM 四条规则：`days` 优先 → `endDate` 作上限（取更小）→ 都没有填满窗口 → 一律 ≤10 天 | PM 第三轮补充要求 |

### 12.2 实测数字（S3，见 `docs/acceptance/M3-2-S3-故障矩阵与首字延迟-验证报告.md`）

- **故障矩阵**：12 类场景 / 42 项断言，PASS 42 / FAIL 0 / SKIP 0。
  没有一种天气故障能让计划生成失败；`CITY_UNKNOWN` 与越窗场景的上游调用次数为 **0**。
- **首字延迟**（本机环回、回声 provider、每组预热 2 次）：`t_draft` 增量
  **+4.8ms（上游正常，天气耗时 P95 = 0ms）**、**+2014ms（上游 5s，≈2s 预算）**，
  都低于 AC-9 的 2500ms。
- **结构性事实**：`run_generation` 先 `yield intent` 再查天气，所以注入推迟的是
