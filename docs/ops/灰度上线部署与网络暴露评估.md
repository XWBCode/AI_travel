## 3. 网络暴露与访问边界评估

### 3.1 三条链路，风险完全不同

| 链路 | 端口 | 现状 | 风险 |
|---|---|---|---|
| 浏览器 → Java | 8080（生产应只暴露 nginx 443/8088） | 本机 8080 监听 `::`（全网卡） | 有登录与 `CurrentUser` 鉴权，属既有风险面 |
| Java → Python | 8000（内网调用） | 本机回环 | 正常路径 |
| **外部 → Python** | **8000** | **服务本身无任何鉴权** | **关键风险**：能连到 8000 的人可以直接调 `/v1/plan/adjust`、`/v1/plan/stream`，绕过 Java 的登录与计划归属校验，消耗模型额度 |

这不是 S5 引入的问题（S1~S4 之前就存在），但 S5 的 PM 要求里有一条
"只有可信 Java 服务能调用 Python 内部接口"——**今天这条在机制上不成立**，
只是靠"没人扫到 8000 端口"侥幸成立。

### 3.2 现在的三道缓解（以及各自的局限）

| 缓解 | 现状 | 局限 |
|---|---|---|
| 绑回环 | ~~只靠 `start-all.bat` 的 `--host 127.0.0.1`~~ → **已改为代码与 `config.yaml` 默认值即 `127.0.0.1`**（本次加固） | 仍可被 `AI_SERVICE_HOST=0.0.0.0` 显式打开，但那是**看得见的动作**，不再是默认 |
| nginx 只代理 Java | `deploy/nginx/r7.conf` 只有 8088→8080 | 没有把 8000 明确"拒绝"的规则，靠的是不配置 |
| 内部端点令牌 | `/v1/internal/*` 需 `X-Internal-Token`（S5 新增） | 只保护指标端点，不保护 `/v1/plan/*`；且**密钥未配置时放行**（已登记 TD-01） |

### 7.2 修改二：容器不发布 Python 8000 端口（核查结论：不适用）

核查过程与依据：

```
$ glob **/Dockerfile*        -> 无任何结果
$ cat docker-compose.yml     -> 只有 mysql / redis 两个 service，没有 python
$ grep -r "8000:8000"        -> 无结果
```

结论：**Python 服务从未容器化，不存在 `ports: 8000:8000` 这条发布规则**，
因此本项不是"删掉某一行"，而是"这条风险在当前部署形态下不存在"。
按 PM 的注意项（"容器内部监听地址与宿主机端口映射是两个不同问题"）说明：
- 容器内部监听地址：不适用（无容器）；
- 宿主机端口映射：不存在（compose 里没有 Python）。

**但核查时发现三处同类暴露，均不在本轮授权范围，已登记技术债（TD-03/TD-04）：**

| 端口 | 服务 | 监听地址 | 说明 |
|---|---|---|---|
| 3306 | MySQL（docker publish `3306:3306`） | `::`（全网卡） | 同网段可直接连库，风险高于 8000 |
| 6379 | Redis（docker publish `6379:6379`） | 未运行，规则同上 | 与 MySQL 同性质 |
| 8080 | Java 后端 | `::`（全网卡） | 有 JWT 鉴权，但生产应由 nginx 前置并回环 |

### 7.4 运行时核验：指标端点的鉴权与 fail-open（为登记技术债取实证）

用 `AI_INTERNAL_SECRET` 的有/无各起一个实例，实测：

| 场景 | 请求 | 实测结果 |
|---|---|---|
| 配了密钥，不带令牌 | `GET /v1/internal/metrics/weather-adjust` | **403** `{"code":40300,"message":"internal token required"}` |
| 配了密钥，带正确令牌 | 同上 + `X-Internal-Token: <secret>` | **200**，返回 `gray/outcome/upstream/latencyMs` |
| **未配密钥，不带令牌** | 同上 | **200 放行** ← 这就是 TD-01 的 fail-open 实证 |

> 顺带发现的运行态事实：本机在跑的 8000 进程（PID 246008）是**加入指标端点之前**的旧代码，
> 因此对 `/v1/internal/metrics/weather-adjust` 返回 404。这恰好印证 readiness 的 WARN 7——
> **"配置文件"和"跑着的进程"可以是两份不同的东西**，生产核验必须带 `--url` 对运行实例核。

### 7.5 readiness 增补：TD-01 的现场判据（按 PM 要求）

PM 在 TD-01 的决定里写了「readiness 必须增加这一项的明确检查」。检查项从 7 项扩到 9 项。

**新增第 8 项：密钥为空时 / 得放行？**

| 前置 | 探测 | 判定 |
|---|---|---|
| 密钥为空 | 不探测（代码路径已确定） | `FAIL` —— 密钥为空时必 fail-open |
| 密钥非空 + `--url` | 不带令牌请求指标端点 | 403 → `OK`；200 → `WARN`（dev）/ `FAIL`（prod） |
| 密钥非空 + 无 `--url` | — | `WARN` —— 未核验，不得用于生产 |

**顺带修掉一个误报（新增 7.2）：**

原来的第 7 项只看"带正确令牌能不能读到"，读到就打 `OK 服务侧密钥一致`。
但服务端若**根本没配密钥**，它不校验任何令牌——错令牌也照进 200，
于是"两端密钥一致"这句是假的，而灰度身份同样不可信。现在补一枪错令牌：

| 探测 | 判定 |
|---|---|
| 错令牌 → 403 | `OK 7.2 错令牌被拒绝`（服务端确实在校验） |
| 错令牌 → 200 | `FAIL 7.2 错令牌也被放行`（服务端没校验，第 7 项的"可读"不作数） |

**两种服务端配置的实测输出（同一份脚本、同一个 `--url`）：**

```
# 服务端已配密钥
[OK  ] 7. 指标端点可读（带令牌） —— gray.allowed=0，outcome={}
[OK  ] 7.2 错令牌被拒绝 —— HTTP 403：服务端确实在校验令牌
[OK  ] 8. 指标端点拒绝无令牌请求 —— 无令牌 → HTTP 403。注意：这只证明"配了密钥时会拒绝"，
        密钥为空时仍会放行（TD-01 未修，修法见技术债登记）
共 9 项：FAIL 0 / WARN 1 / OK 8

# 服务端未配密钥（本地配了一个不匹配的）
[OK  ] 7. 指标端点可读（带令牌）
[FAIL] 7.2 错令牌也被放行 —— 服务端根本没校验令牌：第 7 项的"可读"不能当作密钥一致
[WARN] 8. 指标端点仍是 fail-open（TD-01） —— 无令牌 → HTTP 200
共 9 项：FAIL 1 / WARN 4 / OK 4
```

> 第 8 项的 `OK` 判词刻意不写"TD-01 已关闭"：**配了密钥时拒绝 ≠ 密钥为空时也拒绝**。
> 这个区别就是整条技术债的核心，判词如果含糊，下一次就会有人拿它当已修复的证据。

> §2 里的"共 7 项"是当时的真实输出，保留不改；本次增补后的口径以本节为准。
