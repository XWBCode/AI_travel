## 5. 两个需要你拍板的问题

### 问题 1：计划要不要挂到会话上？（建议：要，现在加）

`t_travel_plan` 目前没有 `session_id` / `source_message_id`。

不加的后果：
- 聊天卡片点进详情，返回时回不到原会话；
- 用户问「这个计划是哪次聊天生成的」无法回答；
- 同一会话改了几版，无法按会话聚合。

成本：一个 `V4` 迁移加两个可空字段 + 落库时带上，约半小时。
**越晚加越贵**，建议 P1 一并做。

### 问题 2：生成要不要改成 SSE 流式？（建议：M1 不改）

05 文档写的是 `/v1/plan/stream` 流式下发 `plan_draft`，但 Java 侧 `/api/plans/generate` 是同步阻塞。

| 方案 | 改动 | 体验 |
|---|---|---|
| A 保持同步 | 小：P1 只做事件转发 | Mock 约 1 秒，真实模型 10–30 秒，期间聊天无反馈 |
| B 真正流式 | 大：Java 要边读边转发并处理半途失败 | 可显示「正在规划第 2 天…」 |

建议 M1 走 A，但在 P1 里加一个 `plan_progress` 心跳事件（前端显示「正在生成计划…」），避免长时间空白。等 P3 接真实模型、确认耗时后，再决定是否改 B。

### 7.1 追问改成「给明确选项」（P1-6 补做）

原先的顾虑是「chips 得先猜答案，猜错反而误导」。真正的问题不是要不要给选项，
而是**选项从哪来**：猜用户想说什么当然不行，但槽位是确定的（目的地、天数），
候选值可以穷举。所以做法是「按槽位给候选值」而不是「猜整句」。

- 后端 `PlanIntentService` 为每个追问字段配置候选值：
  - `destination` → 成都 / 西安 / 杭州 / 厦门 / 北京 / 三亚，`value` 为「去成都玩」
  - `days` → 2~5 天，`value` 为「玩3天」
- `value` 是**补答短语**而非裸值：前端提交的是「原话 + 补答」，走一遍正常的意图判定。
  裸值拼不出语法结构（「帮我规划三天，成都」抽不到目的地），短语可以。
- 多组追问逐组选择，全部选满才一次提交——只补一半就发，后端会再问一遍剩下那个。
- 已选按钮保持高亮、其余置灰，用户能回看自己选了什么。

验证（2026-11-12）：

- `mvn test` 26/26（新增 `PlanIntentServiceTest` 7 项）；前端 `npm run test` 全通过
- curl：「我想去成都」→ intent 带 `days` 的 4 个选项；「我想去成都，玩3天」直接出计划

1. **不开放行程条目与预算金额编辑。** 条目属于 M2 的行程调整；预算在 L0 下所有数值都是

### 7.4 P3 起步：接入真实模型（2026-11-12）

用企业内网关 `https://c4ai.ccccltd.cn/api/compatible/v1`（OpenAI 兼容）替换 Mock，
`LLM_PROVIDER=openai_compatible`。密钥只写在本机 `.env`（已 gitignore），文档与代码里不出现。

**选型实测**（同一 prompt：成都三天两人预算三千喜欢美食）

| 模型 | 耗时 | 结果 | 判断 |
|---|---|---|---|
| `jiaorong-instruct` | 33-41s | 契约通过 | **采用** |
| `jiaorong-deepseek-v4-flash` | 178s（8k 配额）/ 44s（2k 配额被推理吃光） | 前者通过、后者截断 | 推理型，`reasoning_content` 占配额，太慢 |
| `jiaorong-qwen3-235b-instruct` | 85s | 住宿 `areaName` 为 null，拒收 | 慢且不稳 |
| `jiaorong-glm-4.5` | — | 网关 500 | 该网关没有这个模型 |

**必须改的三处配置**（否则一定失败）

1. `LLM_MAX_TOKENS=8192`：计划 JSON 约 15k 字符，4096 会被截断（`TRUNCATED`）。
2. `LLM_TIMEOUT_SECONDS=240`，Java 单次生成上限 120s → **180s**，SSE emitter 180s → **240s**。
   顺序必须是「Python 超时 > Java 读超时 < emitter」，否则会出现"AI 还没超时、连接先被掐断"的假失败。
3. `LLM_JSON_MODE=true` 可用（网关支持 `response_format: json_object`）；不支持时置 false 即可。

**真实模型暴露出的两个契约问题（已修）**

- `unverifiedFieldCount` 让模型自己数必然数错（三次 60/58/63，实际 55-63），导致合法计划被整份拒绝。
  改为 AI 服务递归重算覆盖，自报值只记日志（冻结决议 S-5 修订，见 05 §2.2 注与 08 §8）。
- 提示词没列全枚举：模型把购物写成 `SHOPPING`（枚举里只有 `OTHER`）、把 `accommodation.areaName` 写成 null。

### 7.6 M2-2 完成：版本回滚（2026-11-12）

版本快照从 M1 起就在写，但一直没有入口——编辑错了恢复不了，等于「有版本表却没有版本能力」。
这一块把它补成闭环。

**接口**（05 §5.6）

```
POST /api/plans/{id}/versions/{versionNo}/rollback
→ { plan, restoredFrom, version, clearedProgress }
```

直接返回回滚后的详情：前端不用「回滚成功再拉一次」，两次请求之间页面会短暂显示旧内容，
看起来像回滚没生效。

**语义：只替换内容，不回退时间线**

| 项 | 回滚 | 理由 |
|---|---|---|
| 标题 / 基础信息 / 天 / 行程项 / 交通段 / 住宿 / 预算 / 风险 / aiNote | 是 | 这些是「行程内容」 |
| `version` | 否，继续 +1 | 历史只向前写；回滚本身也是一个版本 |
| `status` | 否 | v2 的草稿回滚到 v0 之后仍是草稿 |
| 确认/开始/完成时间、来源会话 | 否 | 事实记录，不可编辑 |

允许 `DRAFT` / `CONFIRMED` / `IN_PROGRESS`；`COMPLETED` / `CANCELLED` 拒绝（`30103`）——
否则「这次旅行最终是什么样」会随一次回滚改变。

**三个必须做的副作用**

1. **回滚前补写当前内容快照**：否则这次回滚不可撤销，而「回滚错了想回去」是最常见的第二次操作。
   实测进行中计划回滚时会触发（`start` 只加 version 不写快照，v2 没有快照可回）。
2. **清空进度**：行程项重建后 `itemId` 全变，不清会出现「进度条说完成了 2 项、列表里一项都没打勾」。
   清了几条通过 `clearedProgress` 下发，前端明确告诉用户，不悄悄归零。
3. **回滚后的版本写快照**，`change_summary = 回滚到 v{n}`。

**两个踩到的真问题**

- **逻辑删除会撞唯一键**：`uk_plan_day(plan_id, day_index, deleted)` 把 `deleted` 放进了索引，
  逻辑删除后同一计划同一天只能删一次，第二次回滚直接 `Duplicate entry`。
  改用 `PlanRollbackMapper` 物理删除，5 条 `DELETE`，行程项靠 `JOIN t_travel_day` 删。
  回滚语义是「整体替换」，留 `deleted=1` 的历史行没有收益。
- **`clearedProgress` 被全局 Long→String 误伤**：字段声明成 `Long` 时，全局序列化器
  把它输出成 `"2"`，前端 `cleared > 0` 恒为 false，提示永远不出现。
  改成 `Integer`（数量不是 ID），并在 VO 上写了注释，避免下次有人「顺手改成 Long」。

**顺带修的一个缺口**

原来只在确认/编辑时写快照，`v0` 永远没有快照——版本列表里最初那一版点不得。
现在**生成时就写 `v0`（AI 生成初稿）**，用户最想回到的往往正是 AI 刚生成、还没被自己改过的样子。

**前端**

- 版本历史每行右侧「回滚」按钮（当前版本显示「当前」、终态显示只读提示）
- 确认弹窗说清三件事：回到哪一版、历史会不会丢、已打的勾怎么办（0 条时不提进度，免得像出事了）
- 规则抽成 `utils/rollback.ts` 纯函数：`canRollback` / `canRollbackTo` / `rollbackConfirmText` / `rollbackSuccessText` / `versionLabel`

**验证（2026-11-12）**

- 后端 `mvn test` **57/57**（新增 `PlanRollbackTest` 9 项：内容恢复、连续回滚两次不撞唯一键、
  回滚前快照可回退、清进度并报数、状态不变、终态拒绝、无效目标、越权）

### 7.8 M2-4 完成：AI 调整建议（2026-11-23）

**真正的问题不是「让模型改行程」，是「怎么改才不破坏用户已有的数据」。**

版本快照是整计划级 JSON，回滚语义是「整份替换 + 重建子表」，`itemId` 全变、进度清零。
那是回滚该有的样子，但同一套机制用在日常调整上是灾难：用户在东京勾完上午三个景点，
说了句「下午那个不去了」，确认之后所有 `itemId` 都变了，**勾全部消失**。

**拍板结果（对应 08 §8 的 S-7）：四个边界**

| 维度 | 取值 | 为什么 |
|---|---|---|
| 可改范围 | 行程项级 + 天内重排 | 天数/日期/预算会触发子表重建、日期重算、进度清理，风险等级不同；混进一条建议后用户无法拆分接受 |
| 差异表达 | 按 `itemId` 的增量 ops | 整份替换会换掉全部 `itemId`，已打的勾跟着消失 |
| 确认粒度 | 整体接受 / 整体拒绝 | 子集 ops 之间有依赖（删了再重排、移动与重排交叉），逐条接受要写依赖求解 |
| 版本锚定 | `base_version` 不符即作废 | 否则 AI 的建议会静默覆盖用户等待期间的手改，且不报错 |

**实现要点**

1. `before` 一律由服务端回填，模型只给 `after`——让模型抄原值，等于让它在差异展示里说第二遍谎。
2. 事实字段（时长/开放时间/票价）不给改：没有数据可填，放开等于给编造开后门。
3. 重排必须先把整天序号移到负区间再写回：`uk_day_item(day_id, item_order, deleted)` 是真唯一键。
4. 删项走物理删除并连带清进度：逻辑删除会让同一位置只能删一次，且会留下孤儿进度行。
5. 应用后整体复检时间关系：单条 op 各自合法，合起来可能是「开始 08:00 / 结束 07:30」。
6. `EXPIRED` 惰性判定，不养定时任务；但**标记过期必须在事务之外**，否则随业务异常一起回滚。

**顺带修掉的两个 bug**

- **网关「200 + 错误 JSON」被误报成「模型返回空内容」。** Key 失效时上游返回的是
  HTTP 200 带 `{"code":400,"message":"invalid apikey: sk-..."}`，调用侧按 SSE 逐行读，
  读到零个事件，最终报「模型返回空内容」。现在识别 Content-Type 与流内错误块，
  报出「网关错误码 400：invalid apikey: sk-***」——并且错误体里的密钥做了脱敏，
  上游确实会把 key 原样回显在 message 里。
- **过期标记被自身的事务回滚。** 原本在 `@Transactional` 的 confirm 里标 `EXPIRED` 再抛异常，
  Spring 把这次更新一起回滚，用户下次点进来还是 `PENDING`，永远点不动。改成事务外判版本、就地标过期。

**验证证据**

- 后端 `mvn test` **92/92**（新增 `AdjustmentOpsTest` 13 项 + `PlanAdjustmentTest` 9 项）
- `verify_plan_adjustment.py` 端到端 **22 项**全通过（生成建议 → 确认前计划不动 → 增量生效 →
  已打的勾仍在 → 打勾不影响建议有效性 → 内容变更后 30108 → EXPIRED → 拒绝不产生版本 → 越权 → 草稿拒绝）

  确认 → 版本 v6→v7、待核实 +3、弹窗关闭、已打的勾仍在 → 放弃 → 版本不变

### 7.9 M2-5 完成：站内通知（2026-11-23）

**这一块最容易做成「为了 R-30 而 R-30」的东西：** 单用户应用里，通知的对象永远是自己。
所以先定判据，再写代码。

**判据只有一条：这件事有没有让计划本身发生变化。**

| 事件 | 进不进 | 为什么 |
|---|---|---|
| 确认 / 开始 / 完成 / 取消 | 进 | 计划级状态迁移，一轮行程各一次 |
| 确认一条调整建议 | 进（`ref_id` 指向建议） | 版本前进，计划内容真的变了 |
| 勾选行程项 | 不进 | 不产生版本，计划本身没变；且每天十几次，会把真正的三两件事淹掉 |
| 生成调整建议 | 不进 | 计划没变，只是多了个待办，而且用户此刻正盯着确认弹窗 |

这条判据同时解释了「为什么不是每个事件都通知」，也给出了协作阶段的迁移路径：
接入多人后，勾选对同伴是有信息量的，按 `actor ≠ recipient` 生成即可，表结构不用改。

**拍板结果（对应 08 §8 的 S-8）**

- 表名 `t_notification`（不是早期 ER 图里的 `t_user_notification`）：全库没有 `user_` 前缀的先例，一致优先。
- `read_at DATETIME` 而非 `is_read TINYINT`：布尔表达不了「什么时候读的」，而 `NULL` 与「1970 年读过」本就是两件事。
- `title/body/ref_id` 而非 `payload JSON`：文案由后端按事件生成固定中文，存 JSON 等于把渲染逻辑推给前端，
  还得为每种 `type` 写解析器——多一处必然走偏的重复。
- 列表响应自带 `unreadCount`（没复用 `PageResult`）：红点和列表必须同源，否则会出现「红点 3 条、列表 2 条」。
- 「全部已读」独立成 `POST /read-all`：「传空 ids」在参数缺失时会静默清空红点，一个拼错的请求就能造成。

**两个实现约束**

1. **通知跟着业务事务提交，不加 `REQUIRES_NEW`，但写失败只打日志。** 计划回滚了通知必须一起消失
   （否则用户看到「已确认」而计划还是草稿）；反过来，一条展示数据插不进去也不该让「确认计划」失败。
   这两件事看似矛盾，其实是同一个取舍的两面：**跟同一个事务 + 吞掉异常**。
2. **通知写在状态判定之后。** 草稿直接点「完成」被状态机拒掉时，不能留下一条「旅行已结束」。

**踩到的坑：计数不是 ID，不吃 ID 的序列化待遇**

全局 Jackson 为保雪花精度把 `Long` 一律序列化成字符串。三个返回未读数的接口原本是 `Result<Long>`，
前端收到的是 `"1"`，`unread === 0` 永远为 false——该禁用的「全部已读」不禁用、该消失的红点不消失。
改成 `Integer` 后恢复正常。端到端脚本第一次跑就红在这里，属于「不连真库看不出来」那一类。

**顺带补的交互**

- 红点不等 30 秒轮询：`http` 拦截器在任何写请求成功后广播 `app:mutation`，铃铛立即重算。
  否则用户点完「标记完成」抬头看铃铛，30 秒内都是空的，看起来像没生效。
- 点开某条通知后弹层自动收起（`v-model:visible`），跳转后弹层还挂着会挡住内容。
- 轮询请求带 `skipErrorToast`：失败时顶栏健康灯已经在说服务状态，每 30 秒弹一次「网络异常」只会让人以为系统崩了。

- 后端 `mvn test` **103/103**（新增 `NotificationTest` 8 项 + `NotificationResilienceTest` 3 项）
- `verify_notification.py` 端到端 **33 项**全通过（空列表 → 非法迁移不留痕 → 确认/开始/完成/取消各一条 →
  只看未读只改列表不改红点 → 幂等标记 → 全部已读不清数据 → 越权不可见、标记返回 403、不存在返回 30111 → 分页夹紧 → ID 字符串）

### 7.7 M2-3 完成：当日执行页（2026-11-12）

**先说清这一块真正的问题**：不是「页面怎么画」，而是「今天等于第几天」。
详情页是文档视角（第 1 天、第 2 天），执行页是时间视角（R-21）；而 `day_index` 是相对序号，
唯一的时间锚是 `start_date`，契约又允许它为空（日期与天数二选一）。没有锚点时，这个映射无解。

**拍板结果：方案 A —— 开始旅行时锚定。** 候选三方案对比：

| 方案 | 做法 | 为什么不选 / 为什么选 |
|---|---|---|
| A 锚定（选用） | 开始旅行时确认出发日，为空则取当天，回填 `start_date`/`end_date` 与全部 `day_date` | 一次点击解决；「我今天出发」符合直觉；老计划也能用；改日期写入版本快照，可回滚 |
| B 强制补日期 | 出发日期为空就不许开始 | 数据最干净，但挡住「已经在路上、今天是第 3 天」的用户 |
| C 降级不显示 | 只按天编号浏览 | 不改数据，但 R-21 要的就是当前日期视图，等于没做 |

**实现要点**

1. `POST /{id}/start` 增加可选 `startDate`；锚定后**只改日期**，不重排天序号、不重建行程项。
2. `GET /{id}/today?date=` 返回 `phase`（`TODAY`/`BEFORE`/`AFTER`/`UNANCHORED`）+ 当天卡片 + 整趟进度。
   **没有锚点就返回 UNANCHORED，绝不猜第 1 天**——猜错等于把人送去错的景点。
3. `date` 由前端传本机日期：跨时区时服务器时间会差一天，这种 bug 只在深夜复现。
4. 终态（`COMPLETED`/`CANCELLED`）不提供「今天」，返回 `30103`。
5. 前端：「今日 / 全部日程」切换，只有算得出今天才给「今日」；跨零点每 60s 与 `focus` 时重算。

**顺带修掉一个旧 bug**：`syncCalendar` 改小天数删除尾部整天时，只清了 item / segment / accommodation，
**没清 `t_travel_progress`**。行程项没了但进度行还在，按 `plan_id` 直接 count 会让「完成数」超过总项数。
现在删天时连带按 `itemId` 清理进度，并有用例钉住。
