### 7.5 readiness 增补：TD-01 的现场判据（按 PM 要求）

PM 在 TD-01 的决定里写了「readiness 必须增加这一项的明确检查」。检查项从 7 项扩到 9 项。

**新增第 8 项：密钥为空时 / 得放行？**

| 前置 | 探测 | 判定 |
|---|---|---|
| 密钥为空 | 不探测（代码路径已确定） | `FAIL` —— 密钥为空时必 fail-open |
| 密钥非空 + `--url` | 不带令牌请求指标端点 | 403 → `OK`；200 → `WARN`（dev）/ `FAIL`（prod） |
| 密钥非空 + 无 `--url` | — | `WARN` —— 未核验，不得用于生产 |

**顺带修掉一个误报（新增 7.2）：**

原来的第 7 项只看"带正确令牌能不能读到"，读到就打 `OK 服务侧密钥一致`。
但服务端若**根本没配密钥**，它不校验任何令牌——错令牌也照进 200，
于是"两端密钥一致"这句是假的，而灰度身份同样不可信。现在补一枪错令牌：

| 探测 | 判定 |
|---|---|
| 错令牌 → 403 | `OK 7.2 错令牌被拒绝`（服务端确实在校验） |
| 错令牌 → 200 | `FAIL 7.2 错令牌也被放行`（服务端没校验，第 7 项的"可读"不作数） |

**两种服务端配置的实测输出（同一份脚本、同一个 `--url`）：**

```
# 服务端已配密钥
[OK  ] 7. 指标端点可读（带令牌） —— gray.allowed=0，outcome={}
[OK  ] 7.2 错令牌被拒绝 —— HTTP 403：服务端确实在校验令牌
[OK  ] 8. 指标端点拒绝无令牌请求 —— 无令牌 → HTTP 403。注意：这只证明"配了密钥时会拒绝"，
        密钥为空时仍会放行（TD-01 未修，修法见技术债登记）
共 9 项：FAIL 0 / WARN 1 / OK 8

# 服务端未配密钥（本地配了一个不匹配的）
[OK  ] 7. 指标端点可读（带令牌）
[FAIL] 7.2 错令牌也被放行 —— 服务端根本没校验令牌：第 7 项的"可读"不能当作密钥一致
[WARN] 8. 指标端点仍是 fail-open（TD-01） —— 无令牌 → HTTP 200
共 9 项：FAIL 1 / WARN 4 / OK 4
```

> 第 8 项的 `OK` 判词刻意不写"TD-01 已关闭"：**配了密钥时拒绝 ≠ 密钥为空时也拒绝**。
> 这个区别就是整条技术债的核心，判词如果含糊，下一次就会有人拿它当已修复的证据。

> §2 里的"共 7 项"是当时的真实输出，保留不改；本次增补后的口径以本节为准。


### 7.6 MySQL 3306 收窄至回环（2026-11-24 执行，TD-03 关闭）

**先纠正一个归因**：本节早先写的「docker compose 把 3306/6379 publish 到全网卡」是**按文件推断**。
运行态核对的结论是：**本机没有 Docker**（无 `C:/Program Files\Docker`、无 `docker` 命令、
无 `com.docker.service`），3306 由**原生 Windows 服务 `MySQL80`** 提供；Redis **本机没有实体**。

所以真正的修复面是 `my.ini`，不是 `docker-compose.yml`。

### 7.8 TD-02 关闭：`/v1/*` 加接口级鉴权（2026-11-24）

**为什么必须做**：本节 §3.1 写得很清楚——8000 端口上所有业务接口原本没有任何鉴权，
唯一防线是"只绑回环"。那是**网络边界**，不是访问控制。端口转发、误配 `0.0.0.0`、
容器 publish，任意一条成立就等于全开。PM 的原则是"生产不能依赖启动脚本作为唯一防线"。

**改了什么**：
- `backend-ai/app/tools/service_guard.py`（新增）：`is_protected()` + `decide()`。
- `backend-ai/app/main.py`：`guard_internal_calls` 中间件；放行 `OPTIONS` 预检；
  启动日志打印当前鉴权模式（"这台机器到底有没有鉴权"要能一眼看到）。
- `backend-java/.../AiServiceClient.java`：`withInternalToken(builder)`，
  chat/stream、plan/generate、plan/adjust、plan/intent、weather **5 处全覆盖**。
- 测试：`test_service_guard.py` 33 项 + `AiServiceInternalTokenHeaderTest` 5 项（真 HTTP 抓头）。

**四档判定**：

| 条件 | 结果 |
|---|---|
| 配了密钥 + 令牌正确 | 放行 |
| 配了密钥 + 令牌缺失/错误 | 403 `40300` |
| 未配密钥 + `APP_ENV=prod` | 403 `40301` |
| 未配密钥 + 非 prod + 回环来源 | 放行（dev 便利） |
| 未配密钥 + 非 prod + 非回环来源 | 403 `40302` |

**决定性实测**（8007 实例：`--host 0.0.0.0` + 未配密钥 + `APP_ENV=dev`，模拟"有人图省事绑了全网卡"）：

| 来源 | 结果 |
|---|---|
| `127.0.0.1:8007/v1/plan/intent` | **200**（回环放行） |
| `192.168.1.4:8007/v1/plan/intent` | **403 `{"code":40302,"message":"internal token not configured: non-loopback caller rejected"}`** |

这条是 TD-02 的核心价值：**即使把端口暴露到全网卡，外部来源仍然进不来**。
这是第一次让"只有可信 Java 能调 Python"从部署约定变成代码事实。

**配了密钥时的三态实测**（8006 实例，`AI_INTERNAL_SECRET=td02-runtime-secret`）：

| 请求 | 结果 |
|---|---|
| 无令牌 | 403 `40300` |
| 错令牌 | 403 `40300` |
| 正确令牌 | **200** + 正常 `data`（scene/needPlan/missingFields…） |
| `/v1/health` | **200**（豁免，不受闸门影响） |

**回归**：Python **420 passed**（原 387 + 33）；Java **202 tests / 0 fail / 65 skipped**（+5）；
端到端 `verify_plan_edit.py` **17/17**。

**踩到的真实故障（运维必读）**：Java 把密钥**明文**放进 `X-Internal-Token`，
密钥里只要有一个非 ASCII 字符（中文就行），`HttpRequest.Builder.header()` 抛
`IllegalArgumentException: invalid header value`，整条链**崩**而不是降级。
触发它的是既有的 `AiServiceIdentityHeaderTest`——它一直用中文密钥，
但那只用来算 HMAC（输出 hex）不传明文，所以从没暴露。
现在 `withInternalToken` 先判断头安全性：非 ASCII 不发头 + 打一条 ERROR。
**所以：`AI_INTERNAL_SECRET` 必须用可见 ASCII 字符**（`openssl rand -hex 32` 天然满足）。

**对业务的影响**：本机现状（未配密钥 + 回环）走"放行"分支，行为不变。
生产配了密钥后 Java 自动带头，链路不变。**唯一会变的是"外部直连 8000"从"能用"变成"403"**，
这正是目的。
