## 2. 运行验证清单（M3-2 的遗留项，不属代码缺陷）

> PM 原话：「这些是运行验证和观测事项，不要求现在回头修改 M3-2。」
> 三条都不是「等功能补完」，而是**只有真实环境才能回答**的问题。

### V-1 真实 QWeather 生成链路冒烟

| 项 | 内容 |
|---|---|
| 为什么没做 | S3 的故障矩阵用的是**进程内替身**（`open_meteo.fetch` + 回声 provider）。它能证明"我们这一侧对故障的反应正确"，**不能**证明"和风天气真实返回的数据能被正确归一化后进 prompt" |
| 触发条件 | 拿到 QWeather 凭据（`QWEATHER_API_HOST` / `DEVELOPER_ID` / `PROJECT_ID` / `KEY_ID` / 私钥）且 `WEATHER_PROVIDER=qweather` |
| 做法 | 打开注入开关，跑一次真实生成（日期在 10 天窗口内），核对：prompt 里的天气表与 `GET /v1/weather` 同城同日结果一致；`aiNote` 的获取时间与响应一致；计划里仍无天气字段 |
| 判据 | 三处一致 + 计划里 `weather/temperature/precipitation` 零命中 + 上游只调 1 次/城 |
| 阻塞 | 无凭据（D-03 已定案源，但凭据不在仓库） |

### V-2 生产态运行验证

| 项 | 内容 |
|---|---|
| 覆盖 | ① 多实例下的**进程内缓存与熔断语义**（每个实例各有一份，冷启动/滚动发布时行为会短暂不一致）② 真实 **429** 与配额打满 ③ **跨日缓存边界**（23:00 缓存、次日 00:10 失效） |
| 触发条件 | 有多实例环境（≥2 个 Python 实例 + 反代）或真实凭据 |
| 判据 | ① 任一实例熔断不影响其他实例，且滚动发布后不出现"半数实例持续失败"；② 429 进硬熔断、不重试；③ 跨日不出现"整体错一天" |
| 已知设计取舍 | 缓存与熔断是进程内的（有意为之：M3-1 的 Java 缓存 + Python 熔断已验收，M3-2 不加分布式锁）。**多实例不一致是已知特性，不是缺陷** |

### V-3 延迟三指标监控

| 项 | 内容 |
|---|---|
| PM 要求 | 保留**天气查询耗时**、**行程内容首段输出耗时**、**整体生成耗时**三个指标，**不能只监控 SSE 第一个事件** |
| 为什么 | `run_generation` 先 `yield intent` 再查天气，所以"第一个事件"几乎不受注入影响，而"用户看到行程内容"会（最坏 +2s）。只盯第一个事件会把真实体验问题藏起来 |
| 现有可得数据 | 日志已具备：`weather_injected/weather_skipped` 带 `elapsedMs`；`done` 事件带 `latencyMs`。缺的是**服务端侧的"首段内容"时刻**——目前只有客户端能测 |
| 落地建议 | 在 `plan_draft` 事件前记一条 `plan_first_content trace=… elapsedMs=…`（Python 侧一处日志，不改契约、不改事件）。**属新代码，需 PM 批准后做**，本清单一并登记 |
