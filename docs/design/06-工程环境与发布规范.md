# 06 · 工程环境与发布规范

> 状态：草案，待 D-08 / D-09 确认 ｜ 上位文档：总纲 V1.0 第 8、9.4、9.5 章
> 对应上次审阅的 G-8（合规缺位）与 G-9（无环境 / CI / 迁移 / 回滚）。

## 1. 环境划分（D-08）

| 环境 | 用途 | 数据库 | 模型 | 数据来源 |
|---|---|---|---|---|
| `dev` | 本机开发、日常联调 | 本机 MySQL（`ai_travel_dev`） | `mock` 或真实 key（个人） | 允许 Mock，必须显式标注 |
| `test` | 自动化测试、评审演示 | 独立库 / 独立 schema | 真实模型的低成本规格 | 固定测试数据集 + 受控 Mock |
| `prod` | 正式运行 | 独立实例 | 正式 key 与额度 | 仅真实数据源，禁止任何 Mock |

**MVP 建议（D-08）**：先建 `dev` + `prod` 配置档案，`test` 随首个自动化测试套件一起引入。理由是单人开发阶段维护三套环境的收益不高，但**配置隔离必须从第一天就做对**，否则后面拆分很痛。

落地方式：

- Spring Boot 用 `application-{env}.yml`，通过 `SPRING_PROFILES_ACTIVE` 切换；**`application.yml` 只放公共项与默认值，不放环境特定值**。
- Python 侧沿用现有「`config.yaml` 默认值 + 环境变量覆盖」机制（已实现）。
- 前端通过 Vite 的 `.env.development` / `.env.production` 切换 API 前缀，禁止在代码里硬编码 `localhost:8080`。
- **U**：三环境的数据库不得共用同一实例同一 schema；`prod` 的连接信息不得出现在 `dev` 配置里。

> 现有 `application.yml` 中所有敏感项已用 `${ENV:default}` 形式（如 `MYSQL_PASSWORD`、`JWT_SECRET`），这个做法正确，继续保持。唯一要注意的是开发环境默认值不得带进 prod——上线检查清单会逐项核对。

## 2. 配置与密钥管理

| 项 | 规则 |
|---|---|
| `.env` | 本地文件，`.gitignore` 已排除（**已实现**） |
| `.env.example` | 只放键名与占位值，**不得出现真实 key**（已实现） |
| API Key | 只在服务端环境变量读取；不进代码、不进 Git、不进前端、不进日志（总纲 4.6、8.4） |
| `JWT_SECRET` | 每个环境独立随机值，长度 ≥ 32 字节（现有 `JwtTokenProvider` 启动时会校验） |
| 数据库口令 | 每个环境独立；prod 口令定期轮换 |
| 密钥泄漏处置 | 立即轮换 → 排查 Git 历史 → 记录事件 → 评估影响范围 |

**U**：日志中禁止输出密码、完整 token、API Key；用户 ID 适当脱敏（总纲 8.4）。现有 `TraceIdFilter` 与日志格式已支持 `traceId` 关联，M1 需补上模型名、token 用量、工具调用摘要字段。

## 3. 数据库迁移

- 采用 **Flyway**（或团队确认的等价方案），脚本放 `sql/migration/V{版本}__{描述}.sql`。
- **U**：任何表结构变更必须先提交 SQL 脚本、更新 04 号文档的 ER 图与字段说明，再执行（总纲 9.4、5.2）。
- **U**：禁止在生产库手工 `ALTER`；每个迁移脚本需配套回滚脚本或明确标注「不可逆」及原因。
- **U**：迁移在应用启动时自动执行，执行结果写入 `flyway_schema_history` 并纳入监控。
- 现有 `sql/01_schema.sql` 作为基线脚本保留，M1 起新增表走 `V2__plan_tables.sql`。

## 4. CI / CD 与质量门禁

MVP 阶段的建议流水线（工具选型待 D-08 一并确认，GitHub Actions / CNB / 工蜂均可）：

```
push / PR
  ↓
[并行] Java: mvn test + package
[并行] Python: ruff/flake8 + pytest + uvicorn 启动冒烟
[并行] Frontend: vue-tsc --noEmit + pnpm build
  ↓
[门禁] 三端全绿才允许合并到 main
  ↓
[部署] 手动触发 → 迁移 → 滚动发布 → 健康检查 → 观察期
```

**质量门禁（任一不通过即阻断合并）**：

| 检查 | 命令 | 当前状态 |
|---|---|---|
| Java 编译 | `mvn -q -B -DskipTests package` | ✅ 已验证通过 |
| Java 单测 | `mvn -q -B test` | ✅ 1/1 通过（用例待扩充） |
| 前端类型检查 + 构建 | `pnpm build` | ✅ 已验证通过 |
| Python 启动冒烟 | `uvicorn` 启动 + `/v1/health` | ✅ 已验证通过 |
| Python 单测 | `pytest` | ⬜ 待补 |
| 密钥扫描 | gitleaks / 等价 | ⬜ 待接入 |
| Schema 契约校验 | 对 `TravelPlan` v1 样例做校验 | ⬜ 待 D-06 冻结后补 |

> 总纲 9.5：「没有实际执行的测试，不得声称测试通过」。CI 报告必须保留原始输出，不接受人工填写的结论。

## 5. 测试策略

| 层 | 范围 | 要求 |
|---|---|---|
| 单元测试 | 状态机流转、`FactField` 约束、Schema 校验、预算计算 | 每个关键业务方法至少 1 个 |
| 接口测试 | 02 第 5 节全部 REST 接口 | 正常 + 权限边界 + 异常路径 |
| 契约测试 | AI 输出样例 → Schema 校验 | 50 组含畸形输出（AC-07） |
| 降级测试 | 外部源不可用 / 超时 / 脏数据 | AC-14、AC-15 |
| 回归测试 | 每次发布前跑核心闭环 | 登录→生成→确认→开始→勾选→完成 |

**每个任务的测试说明**按总纲 9.5 七项填写：编译、单测、接口测试、数据库验证、异常、权限边界、未解决问题。`docs/PHASE1-REPORT.md` 已有模板，后续任务沿用。

## 6. 发布与回滚

### 6.1 发布前检查清单

- [ ] 三端 CI 全绿，测试报告已归档
- [ ] 迁移脚本已评审，回滚方案已确认
- [ ] `prod` 配置项逐项核对：无 dev 默认值、无 Mock、无硬编码 key
- [ ] `LLM_PROVIDER` 非 `mock`；若为 mock，只允许在明确标注的内部演示环境
- [ ] 外部数据源商用授权与署名义务已核实（见 03 第 7 节）
- [ ] 隐私政策与用户协议已上线（社区 / 定位功能启用前必须有）
- [ ] 监控与告警可用：健康检查、错误率、AI 耗时、外部源成功率
- [ ] 回滚脚本已演练或至少验证过语法
- [ ] 本次发布范围经项目负责人确认（排期 / 上线范围不由执行方决定）

### 6.2 回滚

| 变更类型 | 回滚方式 |
|---|---|
| 应用代码 | 回滚到上一个 Git tag / commit 重新部署 |
| 数据库迁移 | 执行配套 down 脚本；不可逆迁移需提前准备数据修复方案 |
| 计划 Schema 版本 | 保留 `schemaVersion`，旧数据按版本适配读取，禁止就地覆写 |
| 模型 / Provider 切换 | `.env` 改回上一个可用配置并重启（现有可插拔设计已支持） |
| 外部数据源下线 | 自动降级到 L0，实时字段回到「待核实」，不阻断主流程（见 03） |

**U**：回滚后必须验证核心闭环（登录→对话→计划详情），并留一条发布记录。

## 7. 合规与内容安全（D-09）

总纲第 8.1 节只写了技术安全，以下为补充。**M4+ 社区上线前必须全部落实**；MVP 阶段先做不依赖 UGC 的部分。

| 项 | 要求 | 阶段 |
|---|---|---|
| 用户协议 / 隐私政策 | 明确收集哪些数据、用途、留存期、删除方式 | MVP 上线前 |
| 账号注销与数据导出 | 提供删除账号及导出个人数据的路径 | MVP 上线前 |
| 位置信息 | 最小化收集、单独授权、可随时关闭；**不得仅凭 GPS 标记行程完成**（总纲 2.2.4） | 启用定位前 |
| UGC 内容审核 | 明确人工 / 机审 / 先审后发策略；管理员审核入口（总纲 2.1 已列权限） | 社区上线前，D-09 |
| AI 生成内容标识 | AI 生成的计划与文章明确标注来源，避免用户误认为人工核实过 | M1 起 |
| 未成年人 | 注册年龄门槛或监护人同意路径 | 社区上线前 |
| 社区文章进 RAG | 只检索有权限访问的内容，删除/下架同步删向量，保留来源，不得把私人计划自动入库（总纲 2.3） | M4+ |
| 第三方数据署名 | 如使用 CC BY 4.0 数据，页面可见位置标注来源 | L1 启用时 |

**U**：AI 生成的计划转为公开文章前，必须由用户显式确认（总纲 2.3），系统不得自动发布。

> 这一节涉及法务与业务判断，**执行方不代为决定**（D-09，C 级，项目负责人确认）。本文件只列出必须在什么时点之前解决。

## 8. 可观测性落点

总纲 8.4 列了要记录什么，本文件补上"记在哪、怎么关联"：

| 信息 | 落点 |
|---|---|
| `traceId` | `TraceIdFilter` 生成 → MDC → 响应头 `X-Trace-Id` → 透传 Python → 埋点（已实现） |
| 请求耗时、异常 | Java 全局异常 + 访问日志 |
| 模型名、token、延迟 | `t_chat_message` + `t_ai_generation_log` |
| Agent 节点 / 工具调用摘要 | `t_ai_generation_log`（M1 补字段） |
| 外部 API 耗时与结果 | 专用日志 + `external_source_fallback` 埋点 |
| 业务指标 | `plan_generated` / `plan_confirmed` / `travel_started` 等（见 02 第 11 节） |

**U**：所有日志与埋点必须能通过 `traceId` 串起「前端请求 → Java → Python → 模型 → 落库」完整链路。
