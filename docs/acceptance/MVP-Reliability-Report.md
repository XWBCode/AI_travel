# MVP 可靠性报告（幂等 / 并发 / 异常 / 性能）

> 基线：`main` @ `2e27428`（修复后 `06b2b55`）
> 口径：可靠性 = **在异常和重复面前，数据还对不对**。所以每条都要有落库证据，不看接口返回 200。

---

## 1. 结论

| 维度 | 结论 | 依据 |
|---|---|---|
| 幂等性 | **部分达标** | 状态迁移、打勾、通知已读都幂等；`POST /plans/generate` 无幂等键（BUG-007） |
| 并发安全 | **达标** | 50 并发「完成旅行」只有 1 次成功；重排不撞唯一键；双标签页改草稿有版本冲突 |
| 异常处理 | **达标** | 网关 200 带错误体、SSE 中断、状态机非法、越权都有明确码与落库行为 |
| 性能 | **mock 达标，真实模型未知** | 首字 P95 38ms（mock）；真实模型 30–45s 属已知，未做压测 |

## 2. 幂等性

| 操作 | 重复执行会怎样 | 靠什么 | 证据 |
|---|---|---|---|
| 开始 / 完成 / 取消旅行 | 第二次 30103，状态与版本不变 | 状态机 + `WHERE status=? AND version=?` | AC-13：50 并发 1 成功、49 次 30103、版本 +1、通知 1 条 |
| 勾选行程项 | 重复勾选不翻倍，取消再勾仍成功 | `uk_plan_progress(user,item)` + 幂等写 | `PlanProgressTest` 5 项 |
| 标记通知已读 | 不报错、**不刷新首次已读时间** | `read_at is null` 条件更新 | `NotificationTest` 8 项 |
| 确认调整建议 | 第二次 30107（已处理） | 状态 `PENDING` 前置校验 | `PlanAdjustmentTest` 9 项 |
| 回滚到同版本 | 版本号递增一次，内容幂等 | 版本表唯一键 `uk_plan_version` | `PlanRollbackTest` 9 项 |
| **生成计划** | **重复执行会生成多份计划** | **无** | 实测：3 个并发相同请求 → 3 份计划（见 BUG-007） |

### BUG-007（P2）`clientRequestId` 幂等键未实现

05 §5「统一约定」写着「写操作支持 `clientRequestId` 幂等键，重复提交返回首次结果」，
全仓库搜不到这个字段——**契约承诺过，实现没做**。

AC-13 仍然通过，因为它的测量方法是「重复提交开始/完成不产生重复记录」，这一点由状态机保证了。
但幂等键要解决的是另一类问题：**同一个请求被重放**（网关重试、浏览器超时重试、用户连点两下）。
真实模型一次生成要 30–45 秒，超时重试的概率不低，后果是：

- 用户多出一份内容几乎相同的计划；
- 多花一次模型额度（真实模型按次计费）；
- 会话里多一条 `plan_saved`，卡片重复出现。

实测证据（mock，3 并发相同请求）：

```
并发同一请求 3 次 → 计划数: 3
planIds: 2124783387568963585, 2124783387568963596, 2124783387631878174
```

**建议方案**（下一阶段做，涉及 `V8` 迁移，本轮不动核心）：

1. `POST /plans/generate`、`POST /{id}/adjustments` 接受 `clientRequestId`；
2. `t_travel_plan` 加 `client_request_id` + 唯一索引 `(user_id, client_request_id)`；
3. 命中重复时返回首次结果（`planId` 不变），而不是报错——重试方要的是「结果」，不是「你知道我重试了」。

## 3. 并发安全

| 场景 | 保护 | 证据 |
|---|---|---|
| 两个标签页同时改草稿 | `PATCH` 带 `baseVersion`，`WHERE status='DRAFT' AND version=?` | `PlanUpdateCommandTest` 14 项；版本冲突 30104 |
| 同时确认同一计划 | 状态条件更新，只有一个 `rows=1` | `PlanPersistenceTest` 7 项 |
| 调整建议与手改打架 | `base_version` 锚定，不符即 `EXPIRED` + 30108 | `PlanAdjustmentTest.staleBaseVersionExpires` |
| 同一天连续重排 | 先把整天序号移到负区间再写回 | `reorderTwiceDoesNotHitUniqueKey` |
| 删项后重排 | 物理删除 + 序号重排，不留空洞 | `removeClearsItsProgress` |
| 50 并发完成旅行 | 状态机 + 版本双条件 | AC-13（1/50 成功） |

**一个刻意的设计**：打勾**不**让 `version` 前进。这样「用户在等建议时勾了几个」不会把建议判过期；
反过来，任何**内容**变更（另一次调整、回滚、锚定出发日）都会让建议失效。

## 4. 异常处理

| 异常 | 表现 | 落库行为 |
|---|---|---|
| 模型网关返回 200 + 错误体 | 识别 `Content-Type` 与流内错误块，报「网关错误码 400：invalid apikey: sk-***」 | 助手消息 `FAILED`，内容为已产出的部分 |
| 网关超时 / 5xx | `50201` | 同上 |
| SSE 中途断开（用户关页面） | 流静默结束，无异常抛出 | `CANCELED`（计划分支：附摘要并说明「计划已生成并保存」）——这是 BUG-001 修复后的行为 |
| 计划校验不通过 | `plan_rejected` + 原因 | 业务表 0 条（AC-07），助手消息 `FAILED` |
| 状态机非法迁移 | `30103`，中文说明 | 无副作用（AC-09） |
| 越权 | `20003`，不区分「不存在」与「不是你的」 | 无副作用（AC-12） |
| 通知写失败 | 只打 warn | **不影响业务提交**（`NotificationResilienceTest` 3 项） |

**一条经验**：所有「异常」都必须有落库结论——`SUCCESS` / `FAILED` / `CANCELED` 三态之一。
出现第四种（什么都不写）就会变成「内容凭空消失」，BUG-001 就是这么来的。
现在 `runPlan` 的每条出口都有对应状态，并有 3 项测试钉住。

## 5. 性能

### 5.1 已测

| 指标 | 值 | 备注 |
|---|---|---|
| 流式首字延迟（mock） | P50 30ms / P95 38ms（n=30） | 只证明链路无额外延迟 |
| 生成计划（mock，端到端） | < 1s | — |
| 50 并发状态迁移 | 全部返回，无 500 | 连接池 10，未见排队超时 |

### 5.2 未测（如实标注）

- 真实模型下的端到端耗时分布与并发承载；
- 单计划页的查询次数（`PlanAssembler` 一次装配会查 6~7 张表，属于可接受范围，但没有 quantify）；
- 大量历史数据下的分页与版本列表性能。

### 5.3 判断

`03` 文档的降级策略与 `PaginationInnerInterceptor` 已在位，但**没有慢查询监控**。
在 50 并发的规模上线性扩展没有问题，做缓存或索引优化现在属于「没有测量就优化」，
按 PM 的要求（先测量再优化）暂不做。
