## 1. 为什么要有这套文档

总纲 V1.0 的业务边界、技术路线和研发红线写得扎实，但作为"最高层级规范"，它刻意停在原则层。11 月 1 日的审阅列出了 9 个会真正卡住研发的缺口：

| 编号 | 缺口 | 严重度 | 本包对应文档 |
|---|---|---|---|
| G-1 | 范围过大，Phase 0–6 不构成 MVP，无排期与人力 | P0 | 01 |
| G-2 | 验收标准全是「用户可以…」，不可测 | P0 | 02 |
| G-3 | 天气 / 地图 / POI / 交通数据源全部未定 | P0 | 03 |
| G-4 | 关键实体缺失（景点、预算、交通段、住宿），版本粒度未定 | P0 | 04 |
| G-5 | 通知系统没有对应开发阶段 | P1 | 01 |
| G-6 | AI 结构化输出无 Schema、无校验、无降级 | P1 | 05 |
| G-7 | 无限流、成本预算、超时与步数上限的具体数值 | P1 | 05 |
| G-8 | 合规与内容审核缺位（UGC、位置、公开页） | P1 | 06 |
| G-9 | 无三环境、无 CI/CD、无数据库迁移与回滚 | P1 | 06 |

本包逐一补齐，**只做细化，不与总纲冲突**。凡与总纲表述不一致之处，以总纲为准；若确需调整总纲，走 C 级决策（总纲第 11 章）。

## 2. 当前最重要的一个设计约束

用户当前环境：**本机 MySQL 已就绪；大模型 API key 与天气 / 地图数据源尚未取得**。

这直接决定 Phase 2 能不能开工。本包给出的答案是 **L0 / L1 分层**（详见 03）：

> **L0（无外部工具）**：AI 基于自身知识与用户输入生成结构化行程，但所有实时性字段（天气、车次、票价、开放时间、景点间耗时）必须标记为「未核实」，禁止输出具体数值，前端显示「待核实」标签。
>
> **L1（工具就绪后）**：通过 Tool 注入真实数据，携带 `source` 与 `fetchedAt`，前端展示来源与更新时间。

这样既不违反总纲 2.2.4「没有实时数据时不允许 AI 编造」，也不必等商务采购完成才能写代码。**这是本包最核心的设计判断，请优先评审。**

## 5. 评审建议路径

1. 先评 **D-01 / D-02**（范围与核心约束），这两项不定，后面文档都可能返工。
2. 再评 **D-03 / D-04 / D-09**（外部依赖与合规），涉及商务与法务，周期最长，宜尽早启动。
3. 最后评 **D-05 ~ D-08**（技术细节），可在开工前的技术评审会上一次性过。
