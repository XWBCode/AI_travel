## 3. P0 缺陷：Java ↔ Python SSE 契约不一致

### 3.1 现象

`backend-java/.../AiServiceClient.java:106` 按**数据体里的 `type` 字段**分发事件：

```java
String type = node.path("type").asText("");   // data: {"content":"..."} 里没有 type
switch (type) { case "delta" -> ... }          // 永远走 default，被忽略
```

但 Python 侧（`backend-ai/app/routers/chat.py`）把事件名放在 **SSE 的 `event:` 行**，数据体里只有 `content`。本轮实测原始输出：

```
event: delta
data: {"content": "[MOCK]"}

event: delta
data: {"content": " 当前为本地"}
```

而 Java 的 `readSse()` 会 `continue` 掉所有非 `data:` 开头的行，所以 `event:` 行被直接丢弃。

### 3.2 后果

- `onDelta` / `onDone` **永不触发** → 前端只收到 `meta`，正文一片空白；
- 助手消息不落库，SSE 连接吊到 180s 超时；
- `PHASE1-REPORT` 里「Java→Python 全链路 未测试」这一条，实际是把一个确定性故障漏在了基线里。

### 3.3 修复方案（建议）

1. `AiServiceClient.readSse()` 改为按 SSE 规范先读 `event:` 行、再读 `data:` 行，用事件名分发（与前端 `stream.ts`、README 契约、Python 端三方对齐）；
2. 补「SSE 解析」纯函数单测：喂固定文本（含 `event: delta`、`done`、`error`、跨行 `data:`），断言回调序列；
3. 加兜底：流正常结束但从未收到 `done`/`error` 时，落库标记 `FAILED` 并下发 `error`，不再静默吊到超时。

### 11.3 关键决策

1. **意图用规则不用模型**。判意图跑在每次对话上，用模型成本高、延迟大且不可解释。规则抽不到的槽位进 `missingFields` 追问，不会乱猜。
2. **Mock 只产出"泛化活动"**（如「老城历史街区漫步」），不点名真实景点。否则 Mock 数据会被当成真实推荐，违反总纲 9.3。
3. **`unverifiedFieldCount` 由结构自动统计**，不写常量——WP1 的样例就出过「声明 25、实际 24」的偏差。
4. **不自动重试、不自动修复**。05 文档 §3 的硬要求：自动补全等于替模型编造，会让 AC-07 形同虚设。
5. **`json_mode` 做成可开关**（`LLM_JSON_MODE`）。部分自建/代理服务不认 `response_format` 会直接 400。

### 11.4 踩到的坑

1. 正则分支里的裸 `?`（`|？|?|`）会让整个模式编译失败（`nothing to repeat`），必须写成 `\?`。因为模式是模块级缓存的，一处写错全盘不可用——22 个用例一次性全红。
2. 目的地正则最初用 `从?\s*城市\s*去\s*(城市)`，导致「我想去成都」把「我想」当成出发地、目的地抽成「成都玩三天」。改为：出发地只认「从X…」与「X到Y」，目的地用 lookahead 卡住动词与标点。

### 12.3 关键决策

1. **结构校验复用冻结契约，不在 Java 另写一套**。引入 `com.networknt:json-schema-validator`，pom 把 `contracts/travel-plan/` 复制进 `classpath:schemas`。两套规则必然漂移，而漂移的表现是「Python 拒了、Java 收了」这种最难查的错。
2. **AI 调用与事务严格分离**。`PlanStoreService` 方法全部 `@Transactional` 且不碰网络；`PlanService.generate` 先完成 HTTP 调用、校验，再进事务。否则一次 3 秒的模型请求会占住连接池（上限 10）。
3. **生成留痕用 `REQUIRES_NEW`**。校验失败要回滚业务写入，但「模型原始输出」必须留下，否则线上被拒时无从复查。
4. **状态迁移只认服务端动作**，不接受客户端传目标状态；更新带 `status + version` 双条件，避免并发下两个请求都成功。
5. **`unverifiedFieldCount` 以递归重算为准**，模型自报值只用于 S-5 比对。

### 12.4 踩到的坑（都是测试抓出来的）

1. **合规样例本身违反 S-3**：`destinations = [成都, 乐山]`，但第 3 天城市是 `都江堰`。Schema 只校验结构，发现不了；已补为 `[成都, 乐山, 都江堰]`。这正说明语义校验不能省。
2. **S-4 按字面实现会误拒合法计划**：`preferences.transport` 为 null 但未列入 `missingFields` 被判违规。而 Q-03 的 `transportSource = USER_DEFAULT` 已经表达「未指定、按默认」。已收敛为 basic 的 6 个字段，理由记入 08 §4.1。
3. **测试配置是死配置**：仓库原有 `application-test.yml` 指向 H2 + `schema-h2.sql`，但既没有 H2 依赖也没有该脚本。改为真实 MySQL 测试库 `ai_travel_test`——建表脚本用了 JSON 列、`ON UPDATE CURRENT_TIMESTAMP`、`ENGINE=InnoDB`，H2 兼容模式「跑得过」不代表生产能跑。
4. **surefire 只认命名**：`*IT` 结尾的类 `mvn test` 不会执行。集成测试改名为 `PlanPersistenceTest`，靠 `@EnabledIfEnvironmentVariable` 控制是否跳过。
