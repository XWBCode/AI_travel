## 2. 落地了什么

### 2.1 Python：判定与身份

`app/tools/inject_gate.py`（新增，纯函数 + 一处文件检查）：

- `sign()` / `verify_identity()`：`HMAC-SHA256(secret, "<userId>|<traceId>")`。
  签名绑定 `traceId`，跨请求搬运无效。
- `decide()`：判定顺序固定为 总开关 → 数据源 → 急停 → 白名单/身份。
- `kill_switch_active()`：`Path.exists()`，`stat` 成本可忽略，无需重启。
- 拒绝原因**新造字面量**（`INJECT_DISABLED` / `PROVIDER_DISABLED` / `GRAY_KILLED` /
  `GRAY_NO_WHITELIST` / `IDENTITY_UNTRUSTED` / `NOT_IN_WHITELIST`），不复用 M3-1 的 `SKIP_*`：
  那些枚举的意思是"天气查不到"，而这里绝大多数是"根本不该查"，混在一起日志就分不开。

接入点只有一个：`run_adjust` 在**调 `prepare_adjust_weather_block` 之前**判。
不放行就构造一个 `InjectResult(block=None, reason=...)`，于是 `weather_adjust` 一行未改。

### 2.2 Java：两处

- `AiServiceProperties` + `application.yml`：新增 `internal-secret`（`${AI_INTERNAL_SECRET:}`，默认空）。
- `AiServiceClient.adjustPlan(planView, instruction, traceId, userId)`：配了密钥且拿到 `userId`
  时发 `X-User-Id` + `X-Identity-Sig`；签不出来**不发**（宁可灰度不生效，不发假身份）。
- `PlanAdjustmentService.proposeOnce` 把已有的 `userId` 传下去。

`userId` **不进入请求体**（`userIdNeverLeaksIntoBody`），身份只走头。

### 2.3 观测

`app/tools/adjust_metrics.py`（新增）+ `GET /v1/internal/metrics/weather-adjust`：

- `gray.allowed` / `gray.denied{reason}`
- `outcome`: `injected` / `no_weather` / `circuit_open` / `value_gate` / `gray_denied` / `failed`
- `upstream.calls` / `upstream.cities` / `cacheSavedRate`（派生值，已在文档里标明）
- `latencyMs.weather` / `latencyMs.total` 的 P50/P95（nearest-rank，最近 500 次）

## 4. 两条必须写清的取舍

### 4.1 只有显式 `prod` 才要求白名单

`APP_ENV` 默认是空串（没人声明）。如果"未声明"也算生产，S1~S4 的 **8 个已验收用例**
（它们跑在未声明 env 的状态下）会从"注入成功"变成"灰度拒绝"——那是**改动已验收行为**，
不是收紧灰度。

所以规则是：`APP_ENV ∈ {prod, production}` 且白名单为空 → 拒绝（`GRAY_NO_WHITELIST`）；
其余按实例级放行。**代价**：生产忘设 `APP_ENV` 时这道闸门不生效。
这与 S1 的数据源合规闸门是同一条边界，兜底都是上线检查清单。

### 4.2 延迟样本用显式 `timed=` 标记，不用"是否为 0"判断

第一版写的是"`weather_ms` 或 `total_ms` 非 0 就采样本"，跑 §10 时发现两个问题：

1. 本机替身下天气耗时**真的是 0ms**，有效样本被丢掉，`samples=0`；
2. `gray_denied` 的 0ms 是"没查"，如果一并采进去，会把 P50 拉低成一个好看的假数字。

改成显式标记：只有"真的尝试过查天气"的请求才进分位数。这条与 M3-2 的"用耗时判熔断"
是同一个教训——**不能用结果的数值反推过程**。
