# A · 连续上游故障 10 分钟 · 验证报告

> 日期：2026-11-24
> 场景设计：`docs/acceptance/A-连续故障10分钟-场景设计.md`（执行前定稿）
> 执行：`backend-ai/scripts/verify_weather_outage.py`（真实 HTTP + 真实缓存 + 真实熔断）
> 故障注入：`backend-ai/scripts/fault_upstream.py`（替换 provider 出网点，**产品代码零改动**）

---

## 1. 一句话结论

**上游连续失败 10 分钟，用户全程看到的是「有数据、标了旧、能继续用」，而不是空白或报错；上游调用从第 4 次请求起就停了，10 分钟里总共只打了 4 次。**

三场结果：

| 场次 | 结果 |
|---|---|
| 主场景（10 分钟持续 500，生产参数） | **20 PASS / 0 FAIL / 1 SKIP**，exit=0 |
| 空缓存 + 故障中首次访问 | **4 项全过**（200 / available=false / days=0 / 详情页 22–42ms） |
| 恢复场景（冷却压缩到 20s） | **7 PASS / 0 FAIL**，exit=0 |

唯一 SKIP 是「故障结束后立即恢复」——**这是设计预期，不是失败**：半开探测失败后冷却从 300s 翻倍到 600s，10 分钟窗口内本来就等不到恢复。详见 §5。

## 2. 主场景实测（10 分钟 / 生产参数）

参数：`failure_threshold=3`、`cooldown=300s`、Java 缓存 TTL 由 Python 的 `expiresAt` 决定（本场设为 1 分钟，见设计 §4.4 说明）。

### 2.1 基线

| 项 | 实测 |
|---|---|
| 首次取数 | 143ms，`source=QWEATHER`、`stale=false`、日期 11-24/25/26 |
| 二次取数（缓存命中） | **6ms**，上游调用数 1→1 |
| 缓存响应日期 | 与基线逐字一致 |

### 2.2 故障期（600 秒，Java 侧采样 20 次）

| 断言 | 实测 |
|---|---|
| 全程无 5xx，都拿到结构化响应 | 20/20 |
| 有效缓存期内照常返回新鲜数据 | 2 次（`stale=false`） |
| 缓存过期后降级为旧值 | **18 次（`available=true`、`stale=true`）** |
| 是否有任何一次变成"暂不可用" | **0 次**（有旧值就不该说没有） |
| 日期是否偏移 | **0 次偏移**（始终 11-24/25/26） |
| 最坏耗时 | **30ms**（Java 侧超时 5s，余量 166 倍） |

降级时用户看到的原文（接口实采）：

```
available = true
stale     = true
note      = 数据为上次成功获取的结果（本次刷新失败：UPSTREAM_ERROR）
dates     = 2026-11-24, 2026-11-25, 2026-11-26
```

页面上表现为：天气卡片**保留在原位**、数据照常显示、底部多一行
「数据为上次成功获取的结果，正在尝试更新」——没有塌缩、没有被抽走、没有变成空白。

### 2.3 熔断与资源保护（Python 侧采样 30 次）

上游调用时间线（来自注入替身的 JSONL 记录，不是推断）：

| 时刻 | 事件 | 累计上游调用 |
|---|---|---|
| T+0s | 第 1 次失败（soft） | 2 |
| T+20s | 第 2 次失败 | 3 |
| T+40s | 第 3 次失败 → **熔断打开** | 4 |
| T+60s … T+321s | 21 次请求，**全部被拦，0 次上游调用**（耗时 2–27ms） | 4 |
| **T+341s** | 冷却到点，**放行 1 次半开探测**，失败 | 5 |
| T+361s … T+581s | 12 次请求，**0 次上游调用**（冷却已翻倍到 600s） | 5 |

- **请求 30 次，上游只被调用 4 次**。这是「没有请求风暴」的唯一硬证据——
  耗时短不能证明这件事，一个安静的无限重试循环同样很快。
- 熔断打开后耗时从 ~50ms 降到 **2ms**：说明请求根本没出去，而不是"出去了但很快失败"。

## 3. 空缓存 + 故障中首次访问

重启 Java 清空进程内缓存，在上游仍 500 的情况下访问：

| 断言 | 实测 |
|---|---|
| 天气接口状态码 | **200**（不是 5xx） |
| `available` / `reason` / `days` | `false` / `UPSTREAM_ERROR` / 0 |
| 文案 | 「天气服务暂时不可用」 |
| 计划详情 `GET /api/plans/{id}` | **200，22–42ms** |
| 页面 | 天气卡片留在原位、只显示一行原因；行程正文照常渲染 |

**核心链路不受影响的真正原因不是"耗时短"，而是结构上就没关系**：
`PlanController` 完全不引用天气，天气是 `PlanWeatherController` 上的独立端点。
耗时数字只是这个结构的表现。这一条已用代码核对过，不是推测。

## 4. 恢复场景（冷却压缩到 20s）

| 断言 | 实测 |
|---|---|
| 6 次直连只产生 3 次上游调用，之后冻结 | 是（阈值 3） |
| 冷却到点后半开探测成功 | `ok=true`，50ms |
| 恢复时确实重新请求了上游 | 调用数 +1 |
| 恢复后日期正确 | 11-25/26/27（与请求窗口一致） |
| Java 恢复后写入缓存，二次请求不打上游 | 调用数不变，30ms |
| Java 侧同步恢复为新鲜数据 | `available=true`、`stale=false` |

**这一场的冷却参数是压缩过的（20s，生产 300s），只证明"恢复路径正确"，不证明生产时序。**

## 5. 最重要的一个发现：默认参数下，恢复可能比故障还慢

主场景给了一个反直觉的结果：**10 分钟故障结束后，电路并没有很快恢复**。

推演（与实测一致）：

```
T+40s   熔断打开，冷却 300s
T+341s  半开探测失败 → 冷却翻倍到 600s
T+941s  才允许下一次探测（已是故障结束后的 5.5 分钟）
```

也就是说：上游在第 10 分钟恢复，用户最晚要再等 **约 10 分钟** 才能看到新数据；
这段时间里他看到的是标注了"正在尝试更新"的旧值（不是错误，但确实是旧值）。

这是刻意的保护（官方明确写了持续错误请求可能冻结帐号），但**运维层面需要决策**：

- 要不要提供一个「手动重置熔断」入口（例如仅内网可调的运维接口）？
- 还是接受"最多 10 分钟的旧值"？

本轮按 PM 指令**不扩功能**，所以只记录、不实现。这一条写进 §7 待决策。

## 6. 断言本身错了 4 次（写下来，因为它比对的结果更值得记）

这场验证的第一版脚本有 4 条断言是错的，全部是**断言口径**问题，不是产品问题。
写出来是因为：如果不修正，它们会制造 3 个假红，其中第 1 条还会制造假绿。

| # | 错误断言 | 为什么错 | 后果 |
|---|---|---|---|
| 1 | 用「耗时 < 500ms」判断"熔断返回" | 注入的 500 是在内存里直接抛的，同样毫秒级。**真失败与熔断返回从外部完全同形** | 假红；且熔断若从未打开，它同样会 PASS → **假绿** |
| 2 | 探测次数 = "calls 大于熔断基线的样本数" | 探测是**增量事件**，只能数 calls 的跳变；那样数会把探测后的每次请求都算一次（实测数成 13 次） | 假红 2 条 |
| 3 | 拿 Java 计划窗口的日期去比 Python 直连返回的日期 | 两个请求的窗口本来就不同（计划 11-24 起 vs 明天起） | 假红 |
| 4 | 在 Python 直连上断言"二次请求走缓存" | **Python 侧根本没有缓存**，缓存只在 Java 进程内 | 假红 |

第 1 条最值得记住：它不只是"判错"，而是在**熔断根本没生效时也会通过**——
一个只会判对的断言没有价值，一个会判错对的断言比没有更糟。

第 1 条还顺带证实了设计文档 §6.1 预告的产品问题（见 §7.1）：
既然真失败与熔断返回 reason 相同、耗时相近，**运维和用户都分不出"上游挂了"还是"我们在保护自己"**。

## 7. 待决策 / 已知问题（不自行处理）

### 7.1 熔断返回与真实上游失败同码（产品问题，本轮不改）

熔断期间返回 `UPSTREAM_ERROR`，与上游真返回 500 的 reason 完全一样。
用户看到的都是「天气服务暂时不可用」，无法区分。

建议（需 PM 批准，属功能改动）：熔断期返回独立 reason（如 `CIRCUIT_OPEN`），
文案区分「上游异常」与「已暂停请求以保护服务」。改动面：Python 一处枚举 + Java 映射 + 前端文案。

### 7.2 恢复窗口需要人工兜底吗

见 §5。默认参数下故障结束后最长还要等 10 分钟。要不要提供手动重置入口，需 PM 决定。

### 7.3 本报告**不声称**的事

1. **不声称真实 429 / 403**：全部用替身注入的等价响应，没有骚扰真实账号（按 PM 要求）。
2. **不声称真实网络抖动**：注入的是固定 500 与即时失败，不是真实丢包/半开连接。
3. **不声称多实例语义**：熔断与缓存都是**进程内**状态，两台机器各自计数。扩到多实例后本报告结论不自动成立。
4. **不声称生产 TTL 下的完整时序**：主场景把缓存 TTL 压到 1 分钟（见设计 §4.4），
   否则 10 分钟窗口内 Java 永远命中缓存、`stale` 分支一次都触发不到。
   压缩只改变"多久进入该状态"，没有改变走哪条代码路径。
5. **不声称跨天行为**：没有跨过零点。

## 8. 复现方式

```bash
# 1) 启动可控上游（产品代码零改动，进程内替换出网点）
cd backend-ai
FAULT_STATE_FILE=../.tools/fault/state.json \
FAULT_LOG_FILE=../.tools/fault/calls.jsonl \
WEATHER_PROVIDER=qweather WEATHER_CACHE_TTL_MINUTES=1 \
python scripts/run_fault_server.py --port 8100

# 2) Java 指向它
cd ../backend-java
AI_SERVICE_URL=http://127.0.0.1:8100 WEATHER_PROVIDER=qweather mvn spring-boot:run

# 3) 主场景（10 分钟）/ 恢复场景
cd ../backend-ai
python scripts/verify_weather_outage.py outage 600
python scripts/verify_weather_outage.py recovery   # 需把替身冷却设为 20s

# 4) 切换故障：改 .tools/fault/state.json 的 mode（ok | http_500 | timeout | http_403）
```

采样已落盘到 `.tools/fault/series.json`（Java/Python 两条时间线 + 健康检查 + 调用计数），
断言口径若再变，可用同一份采样重算，不必重跑 10 分钟。
