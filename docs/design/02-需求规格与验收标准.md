# 02 · 需求规格与验收标准（MVP）

> 状态：草案，待技术负责人评审 ｜ 遵循 EARS 原则 ｜ 上位文档：总纲 V1.0 第 2、12 章
> 本文件覆盖 M1（计划生成）与 M2（旅行执行），M0 已交付部分不重复。

## 1. 写法约定

EARS 五类句式，本文件统一用中文表达并标注类型，避免歧义：

| 类型 | 句式 | 用途 |
|---|---|---|
| **U** Ubiquitous | 「系统应始终……」 | 无条件的全局约束 |
| **E** Event-driven | 「当……时，系统应……」 | 事件触发的行为 |
| **X** Unwanted | 「若……，则系统应……」 | 异常 / 故障处理 |
| **S** State-driven | 「在……状态下，系统应……」 | 特定状态下的行为 |
| **O** Optional | 「在具备……能力时，系统应……」 | 可选功能（L1 增强层） |

每条需求有稳定编号 `R-xx`，验收标准编号 `AC-xx`，二者双向可追溯。

## 2. 功能需求：AI 对话（M0 已实现，补规格）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| R-01 | U | 系统应始终将用户消息与 AI 消息持久化到 MySQL，不得以 Redis 缓存替代持久化职责。 |
| R-02 | U | 系统应始终保证每个会话归属唯一用户，跨用户访问会话或消息应被拒绝。 |
| R-03 | E | 当用户发送消息且 `sessionId` 为空时，系统应创建独立会话并在流开始的 `meta` 事件中返回新 `sessionId`。 |
| R-04 | E | 当 AI 服务逐段返回内容时，系统应通过 SSE `delta` 事件实时推送给前端，不得等待全部生成完成后一次性下发。 |
| R-05 | X | 若 AI 服务超时、断连或返回错误，则系统应把已生成的部分内容照常落库、标记 `FAILED`，并通过 `error` 事件告知前端，不得静默丢弃或返回成功。 |
| R-06 | E | 当用户点击「停止生成」时，系统应中断 SSE 连接，已生成内容按 `CANCELED` 落库，且不得继续向模型计费。 |
| R-07 | S | 在生成进行中状态下，系统应禁用发送按钮并展示「停止生成」，禁止同一会话并发发起第二次生成。 |
| R-08 | U | 系统应始终对单条消息长度、单次上下文轮数与总字符数设上限，超限时应截断历史而非拒绝请求。 |

## 3. 功能需求：旅行需求识别与计划生成（M1 核心）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| R-10 | E | 当用户以自然语言提出旅行需求时，系统应识别出发地、目的地、出行日期、天数、人数、预算、兴趣偏好、交通偏好、住宿偏好与特殊要求，缺失字段标记为 `unknown`，不得默认为 0 或空字符串冒充已填写。 |
| R-11 | E | 当关键字段（目的地、天数）缺失时，系统应一次性最多追问 2 个问题；用户明确允许使用默认值时，系统应记录该默认值来源为 `USER_DEFAULT`。 |
| R-12 | U | 系统应始终以结构化对象保存旅行计划，Markdown 仅作为展示层输出，不得作为数据库唯一数据结构。 |
| R-13 | U | 系统应始终对 AI 返回的结构化结果执行 Schema 校验，校验通过方可写入业务表。 |
| R-14 | X | 若 AI 返回内容不符合 Schema 或包含实时性字段的具体数值而对应工具未返回数据，则系统应拒绝落库、保留原始响应用于排查，并向用户展示「生成失败，请重试」，不得把不可信内容写入正式计划。 |
| R-15 | U | 系统应始终保证 **AI 生成计划不等于用户确认计划**；计划初始状态为 `DRAFT`，只有用户显式操作才能变更为 `CONFIRMED`。 |
| R-16 | E | 当用户修改草稿计划时，系统应保存修改并保留修改前的版本记录，前端展示变更字段差异。 |
| R-17 | U | 系统应始终在计划卡片中标注数据来源与核实状态；未接入工具时，天气、车次、票价、开放时间、景点间耗时一律显示「待核实」，不得展示为确定信息。 |
| R-18 | X | 若用户要求 AI 提供天气、车次、票价等实时信息但对应工具不可用，则系统应明确回答「该信息需要实时查询，当前无法确认」，不得以模型知识编造具体数值。 |

## 4. 功能需求：旅行执行（M2 核心）

| 编号 | 类型 | 需求描述 |
|---|---|---|
| R-20 | E | 当用户对 `CONFIRMED` 计划点击「开始旅行」时，系统应将状态变更为 `IN_PROGRESS` 并初始化每日行程进度为未完成。 |
| R-21 | S | 在 `IN_PROGRESS` 状态下，系统应展示当前日期对应的行程卡片、当日景点列表与整体完成进度。 |
| R-22 | E | 当用户勾选某个行程项完成时，系统应记录完成时间与操作人，并更新进度；不得由系统基于位置或时间自动标记完成。 |
| R-23 | E | 当用户提出行程调整（如「今天太累，下午不去了」）时，系统应基于当前计划生成**调整建议**并展示修改前后差异，等待用户确认。 |
| R-24 | U | 系统应始终保证：AI 不得未经用户确认直接修改 `CONFIRMED` 或 `IN_PROGRESS` 状态的正式计划。 |
| R-25 | E | 当用户确认调整方案时，系统应由 Java 业务服务执行变更、生成新版本记录并推送站内通知。 |
| R-26 | E | 当用户点击「完成旅行」时，系统应将状态变更为 `COMPLETED`，记录结束时间，并允许后续转为社区文章（M4+）。 |
| R-27 | X | 若用户尝试对 `DRAFT` 计划执行「开始旅行」或对 `COMPLETED` 计划重复操作，则系统应拒绝并返回明确的业务错误码，不得静默成功。 |
| R-28 | S | 在 `CANCELLED` 状态下，系统应只读展示计划，禁止任何修改与开始操作。 |

## 5. 功能需求：通知与增强层

| 编号 | 类型 | 需求描述 |
|---|---|---|
| R-30 | E | 当计划状态变更、行程项完成或产生调整建议待确认时，系统应生成站内通知并关联到相关用户。 |
| R-31 | O | 在具备天气工具时，系统应按城市与日期获取天气预报，并在行程卡片展示数值、来源与更新时间。 |
| R-32 | X | 若外部数据源返回错误或超时，则系统应保留上一次成功数据并标注「数据更新于 X 前」，无历史数据时显示「暂不可用」，不得展示空白或编造值。 |
| R-33 | O | 在具备地图工具时，系统应可校验景点间距离与耗时；未具备时，系统应只做同城分组并提示「景点间耗时未核实」。 |

## 6. 可量化验收标准

> 所有指标为**建议默认值**，需 D-07 确认后生效；测量方法必须写明，否则不接受「测试通过」的结论。

| 编号 | 验收项 | 指标 | 测量方法 |
|---|---|---|---|
| AC-01 | 历史消息持久化 | 刷新页面后会话与消息恢复率 = 100% | 注册→发 3 轮→刷新→比对消息 ID 与内容 |
| AC-02 | 会话隔离 | 用户 A 访问用户 B 的 sessionId 返回 403 的比例 = 100% | 双账号交叉请求 20 次 |
| AC-03 | 流式首字延迟 | P95 ≤ 3s（mock 模式 ≤ 500ms；真实模型待 D-07 另定） | 记录 `meta`→首个 `delta` 的时间差，30 次采样 |
| AC-04 | 生成中断完整性 | 断连后已产出内容落库率 = 100%，且 `status=FAILED` | 中途 abort，查 `t_chat_message` |
| AC-05 | 需求字段识别 | 给定 20 条含明确字段的语料，必需字段（目的地/天数）识别准确率 ≥ 95% | 标注语料集批量回归 |
| AC-06 | 缺失字段处理 | 未知字段被存为 `unknown` 而非 0/空串的比例 = 100% | 构造缺字段输入，查库 |
| AC-07 | 计划 Schema | AI 输出通过 Schema 校验率 ≥ 98%；未通过时落库数 = 0 | 注入 50 组含畸形输出的响应 |
| AC-08 | 实时字段不编造 | L0 模式下天气/票价/车次/耗时字段出现具体数值的次数 = 0 | 扫描 50 份生成计划的 `FactField.verified` 标记与文本 |
| AC-09 | 确认状态机 | 未经用户操作计划自动变为 `CONFIRMED` 的次数 = 0 | 全链路状态日志审计 |
| AC-10 | 结构化存储 | 计划详情可从结构化字段完整还原，不依赖 Markdown 文本 = 100% | 关闭 Markdown 渲染后比对字段 |
| AC-11 | 调整需确认 | AI 直接写正式计划的次数 = 0 | 代码审计 + 状态变更日志 |
| AC-12 | 越权防护 | 越权读写计划/进度/通知返回 403 的比例 = 100% | 权限边界用例集 |
| AC-13 | 幂等性 | 重复提交「开始旅行」「完成旅行」不产生重复记录 = 100% | 并发重复请求 50 次 |
| AC-14 | 异常可见 | 外部源不可用时前端展示降级提示的比例 = 100% | 断网 / 返回 5xx 模拟 |
| AC-15 | 来源标注 | L1 模式下每个天气数值都带 `source` 与 `fetchedAt` = 100% | 接口响应字段校验 |

## 7. 边界场景清单

| 场景 | 期望行为 |
|---|---|
| 用户只说「想去玩」 | 追问目的地与天数，最多 2 个问题，不生成计划 |
| 天数 = 1 / 天数 > 30 | 提示范围外并建议调整，仍允许用户坚持（不擅自截断） |
| 预算填 0 或负数 | 参数校验拒绝，返回明确错误码 |
| 出行日期在过去 | 提示日期无效，不生成计划 |
| 目的地为境外 | L0 正常生成，实时字段保持待核实；提示签证等信息以官方为准 |
| 同一会话连续生成两次计划 | 生成新草稿版本，不覆盖已确认计划 |
| 计划已开始后用户改出发日期 | 走调整建议 + 确认流程，不直接改 |
| 消息超长 / 含特殊字符 / Markdown 注入 | 长度截断 + 转义渲染，禁止 XSS |
| 刷新页面时正在流式生成 | 已落库部分可见，流不自动恢复，提示「生成已中断」 |
| 多端同时登录同一账号 | 允许，各端独立会话；写操作以服务端状态为准 |

## 8. 异常状态与错误码

| 异常 | 业务码 | HTTP | 前端行为 |
|---|---|---|---|
| 未登录 / token 过期 | 20001 / 20002 | 401 | 清除 token，跳登录 |
| 越权访问 | 20003 | 403 | 提示无权访问，返回上一页 |
| 计划/会话不存在 | 30101 / 30201 | 404 | 提示资源不存在 |
| AI 服务不可用 | 50201 | 502 | 保留已生成内容，提示重试 |
| 外部数据源失败 | 50202 | 200（降级） | 展示「暂不可用 / 数据更新于 X 前」 |
| Schema 校验失败 | 10002 | 200 | 提示生成失败，不落库 |
| 状态机非法流转 | 30102（新增建议） | 200 | 提示当前状态不允许该操作 |
| 触发限流 | 10429 | 429 | 提示稍后重试，展示剩余等待时间 |

## 9. 权限规则

- **U**：所有涉及私有数据的接口必须校验「登录态 + 资源归属」两项，缺一不可。
- **U**：AI 工具调用正式业务数据时，必须由 Java 业务接口执行权限校验，Python 不得直连 MySQL（总纲 4.3）。
- **U**：`PRIVATE` 计划仅创建者可见；`LINK_ONLY` / `PUBLIC` 属 M4+ 范围，MVP 不开放。
- **U**：日志中禁止出现密码、完整 token、API Key；用户 ID 适当脱敏（总纲 8.4）。
- **U**：Prompt Injection 不得突破权限边界；用户输入一律作为 `user` 角色消息传入，不拼进 system prompt（已在 `backend-ai/app/llm/prompts.py` 实现）。

## 10. 数据口径

| 指标 | 定义 | 口径说明 |
|---|---|---|
| 计划完成进度 | 已完成行程项数 / 计划总行程项数 | 分母按 `CONFIRMED` 时快照计算，调整后单独记录版本 |
| 生成耗时 | `meta` 发出 → `done` 发出的时间差 | 含网络传输，不含前端渲染 |
| 首字延迟 | `meta` 发出 → 首个 `delta` 的时间差 | 反映模型与链路响应 |
| 会话数 | `deleted=0` 的 `t_chat_session` 计数 | 逻辑删除不计入 |
| 活跃用户 | 当日内有 `t_chat_message` 写入的去重用户数 | 以 `create_time` 归属日 |
| Token 用量 | `prompt_tokens + completion_tokens` | 模型未返回时记 null，不得填 0 |

## 11. 埋点需求

| 事件名 | 触发时机 | 关键属性 |
|---|---|---|
| `chat_send` | 用户发送消息 | sessionId、traceId、消息长度、是否新会话 |
| `chat_first_delta` | 首个 delta 到达 | 首字延迟、provider、model |
| `chat_done` / `chat_failed` | 流结束 | 耗时、字符数、token、错误码 |
| `plan_generated` | Schema 校验通过并落库 | planId、天数、行程项数、未核实字段数 |
| `plan_schema_rejected` | 校验失败 | 失败原因分类、traceId |
| `plan_confirmed` | 用户确认 | planId、从生成到确认的间隔、修改次数 |
| `travel_started` / `travel_completed` | 状态流转 | planId、状态、时间 |
| `progress_item_checked` | 勾完成 | planId、itemId、完成时间 |
| `adjustment_suggested` / `adjustment_confirmed` | 调整建议与确认 | planId、差异字段数 |
| `external_source_fallback` | 外部源降级 | 来源、失败类型、是否有历史缓存 |

> 埋点统一携带 `traceId`，与后端日志关联（总纲 8.4）。所有埋点字段先入设计文档，再由研发实现，禁止随手加字段。
