## 2. 实验设计：为什么不把 `proxy_read_timeout` 调大

最容易做的「修复」是把反代超时从 60s 调到 600s，然后发一条心跳，报告「连接不再断」。
那样做**永远无法证明心跳有用**——连接可能只是因为超时够长而活着。所以本实验刻意反过来：

| | 对照组 | 实验组 |
|---|---|---|
| nginx 配置 | `proxy_read_timeout 60s`（默认值） | 完全**同一份**配置文件 |
| 后端代码 | 同一份 | 同一份 |
| 模型 / 输入 | 同一句「成都三天」 | 同一句「成都三天」 |
| 唯一变量 | `app.ai.sse-heartbeat-enabled=false` | `=true` |

预期与实测：

| | 预期 | 实测 |
|---|---|---|
| 对照组 | 第 60 秒被反代掐断 | **60.017s** 断开，nginx error log：`upstream timed out ... while reading upstream` |
| 实验组 | 每 15s 一次心跳，活到生成结束 | **113.251s** 正常完成，7 次心跳，最长静默 15.009s |

对照组客户端在 60s 内只收到 **373 字节**（`meta` + `intent` + `plan_progress`），
实验组收到完整事件流并落库。同一个 60s 门槛，两种命运，变量只有一个——这就是因果。

## 4. 第二阶段：SSE 心跳

新增 `SseHeartbeat`（单线程调度，15s 一次），在 `ChatController` 的 emitter 生命周期内 start/stop。

| 设计点 | 选择 | 理由 |
|---|---|---|
| 心跳形态 | SSE 注释行 `:ping` | 浏览器原生 EventSource 与我们的前端解析器（只认 `event:`/`data:`，没有 data 就丢弃）都不把它当事件，**不改变任何业务语义，也不需要前端配合**；且不产生模型调用 |
| 间隔 | 15s | 反代默认 60s 空闲超时的 1/4，留 3 次容错；一次 GC 停顿不至于判死 |
| 并发安全 | 调度线程与业务线程都会 send | Spring 的 `ResponseBodyEmitter#send` 内部对同一实例串行化，不会写坏响应体；顺序上心跳只是插在业务事件之间 |
| 客户端断开 | send 抛异常 → 立刻摘掉任务 | 连接没了还在发，等于拖着一个永不结束的定时任务 |
| 生命周期 | `onTimeout` / `onError` / `onCompletion` / 业务 `finally` 四处都 stop | 少一处就会泄漏一个定时任务（已用单测钉住） |
| 开关 | `app.ai.sse-heartbeat-enabled`，默认 true | 存在的唯一目的是「对照组」。生产没有关掉它的理由，关掉时启动会打 WARN |

单测 `SseHeartbeatTest`（5 项）：间隔到了必发且载荷是注释行、客户端断开自动停、开关关闭一条不发、
`stop()` 幂等、**默认值本身是安全的**（开启 + 15s 且断言「间隔不得 ≥ 反代默认空闲超时」）。
前端解析器对无 data 的块直接丢弃——这条规则原来埋在 `dispatch` 里只能靠肉眼保证，现已抽成纯函数 `frontend/src/api/sse-frame.ts` 并用 8 项断言钉住（见 §7）。

| ② Nginx 代理链路正常 | 探针作为**独立的 HTTP 客户端**经 8088 收到的 7 次 `:ping` 与完整事件流；access log 的字节数 | 不能证明是**浏览器**收的（探针不是浏览器） |
| ③ 浏览器实际接收正常 | Edge 里跑真实前端（5173 → 8088 → 8080），页面最后渲染出计划卡片；nginx access 里那条带 `Edg/158` UA 的 `200 7702` | 不能证明业务数据正确（那要看 ④） |
| ④ 业务任务正常完成 | `plan_saved` 事件 + `t_travel_plan` 落库 + `t_ai_generation_log` PASS | 不能证明链路没断过（断过也可能补写成功——对照组就是） |

这里不把「服务端 send 成功」当成「浏览器收到」，两者在本次实验中分别有独立证据。

## 6. 限制、未测项与遗留

### 6.1 未测：接近业务上限（330s SSE / 300s AI）的请求

要造出一次「接近 330s」的请求，只能让真实模型跑 5 分钟以上（或者把超时改小造假，那就变成测配置而不是测链路）。
本次已经用真实生成覆盖到 **164s**（8 并发里最长的一条），远超过 60s 这个真正的风险点；
再往上的时间窗由 BUG-012 的断言（`sseTimeout > max(plan, read)`）在单测层面兜住，
并由 §5.7 的「模型超时」用例覆盖了「等待被提前终止」这条出口。
**结论：这一项记 NA，不记 PASS**——没测就是没测。

### 6.2 这个反代环境不是生产环境

没有 TLS、没有 gzip、没有多层代理、没有真实域名与 CDN。本次验证的是「60s 空闲掐断」这个机制，
以及心跳对它的作用。生产挂反代时仍需：
- 反代侧显式关掉 SSE 响应缓冲（`X-Accel-Buffering: no` 或 `proxy_buffering off`）；
- `proxy_read_timeout` 与「心跳间隔」「SSE 上限」三者一起核对，不能各写各的；
- 负载均衡（多实例）时，`SseEmitter` 是**单机内存对象**，不做会话粘滞就会把流打到另一台机器上——这是 R7 之后的新风险，见 §6.3。

### 6.3 新增风险：心率任务与多实例

`SseHeartbeat` 的任务表在 JVM 内存里。单机没问题（本次验证的就是单机）。
一旦多实例 + 无粘滞，浏览器重连可能落到另一台实例上，那台的 emitter 是空的——
表现为「重连后收不到任何事件」。这不是缺陷，是**部署前提**，已记入可靠性报告风险表。

### 6.4 一个顺带发现（不修，只记录）

三次「客户端没拿到结果」的请求，后端都各写了一份 DRAFT 计划（22:40:08 / 22:45:08 / 22:46:05）。
用户视角是「失败了」，进「我的旅行」却能看到三份计划。这是 BUG-012 描述过的同一类现象，
在**正常路径上已经被心跳消除**（§5.3 实验组）；只有客户端真的断开时才会留下，
而那种情况下「计划保留」比「静默丢弃」更符合用户利益（他确实想要这份计划）。
所以这里不改行为，只在报告里写清楚：**「用户看到失败」不等于「没有产生数据」**。
