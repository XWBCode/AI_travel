## 3. 网络暴露与访问边界评估

### 3.1 三条链路，风险完全不同

| 链路 | 端口 | 现状 | 风险 |
|---|---|---|---|
| 浏览器 → Java | 8080（生产应只暴露 nginx 443/8088） | 本机直连 8080 | 有登录与 `CurrentUser` 鉴权，属既有风险面 |
| Java → Python | 8000（内网调用） | 本机回环 | 正常路径 |
| **外部 → Python** | **8000** | **服务本身无任何鉴权** | **关键风险**：能连到 8000 的人可以直接调 `/v1/plan/adjust`、`/v1/plan/stream`，绕过 Java 的登录与计划归属校验，消耗模型额度 |

这不是 S5 引入的问题（S1~S4 之前就存在），但 S5 的 PM 要求里有一条
"只有可信 Java 服务能调用 Python 内部接口"——**今天这条在机制上不成立**，
只是靠"没人扫到 8000 端口"侥幸成立。

### 3.2 现在的三道缓解（以及各自的局限）

| 缓解 | 现状 | 局限 |
|---|---|---|
| 绑回环 | `start-all.bat` 用 `--host 127.0.0.1` | 只要有人图省事用默认 `host=0.0.0.0` 起，就全开。配置默认值仍是 `0.0.0.0` |
| nginx 只代理 Java | `deploy/nginx/r7.conf` 只有 8088→8080 | 没有把 8000 明确"拒绝"的规则，靠的是不配置 |
| 内部端点令牌 | `/v1/internal/*` 需 `X-Internal-Token`（S5 新增） | 只保护指标端点，不保护 `/v1/plan/*` |

### 3.3 建议（按性价比排序，均未实施，需批准）

1. **把 `Settings.host` 默认值从 `0.0.0.0` 改成 `127.0.0.1`**，需要对外监听时必须显式设
   `AI_SERVICE_HOST`。一次改动，把"默认安全"变成代码事实，而不是靠启动脚本自觉。
2. **生产部署用容器网络**：Python 不 publish 端口，只与 Java 同网络；或 `expose` 而非 `ports`。
3. **给 `/v1/plan/*` 加内部令牌**（复用同一个 `X-Internal-Token`）：Java 调用时带上，
   Python 拒绝无令牌请求。这是把"只有可信 Java 能调"从部署约定变成代码约束的**唯一**办法。
   代价：两端都要改（Java 两处、Python 中间件一处），属于新范围，需要单独立项。

> 第 3 条不做的话，灰度本身仍然安全（身份伪造不了），但"AI 服务可被匿名调用"这个更大的口子一直在。

## 4. 上生产：部署步骤（开关保持 false）

1. 建独立实例（或明确"本机即唯一实例"，见 §5）
2. 部署本分支代码，**`WEATHER_INJECT_ON_ADJUST=false`**
3. 配 `AI_INTERNAL_SECRET`（`openssl rand -hex 32`），**两端同值**，不入库、不进日志
4. 配 `APP_ENV=prod`（或 `SPRING_PROFILES_ACTIVE=prod`）
5. 配 `AI_SERVICE_HOST=127.0.0.1`（或容器内网 IP），确认外部扫不到 8000
6. 配 `WEATHER_INJECT_ADJUST_KILL_FILE` 指向运维可写路径
7. 配 `WEATHER_INJECT_ADJUST_USERS=2124886847173947393`（首批仅此一个）
8. 起服务，跑 `check_gray_readiness.py --url http://<host>:8000`
9. 结果贴给 PM，等 G1 授权
10. 授权后设 `true` 并重启，按 ops 文档 §4「开启」四条验证（白名单账号 +1、非白名单 +0、无数值转述、p95 正常）

## 5. 需要 PM 决定的一件事

**生产环境到底存不存在？** 两条路，代价不同：

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 搭独立实例 | 真正的生产部署，独立网络边界 | 需要服务器/DNS/证书/部署流水线，工作量远大于 S5 |
| B. 认定本机即唯一实例 | 写进文档：本机就是"生产"，核验 = 本机核验 + 人工确认 | 无法声称"独立环境验证过"；一旦对外开放端口，风险立即变成真实 |

在此之前，我不会开启 G1，也不会把本机核验包装成生产核验。
