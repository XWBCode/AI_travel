## 1. 结论（一句话）

采 **和风天气新版 Weather API（`/weather/v1/daily/{lat}/{lon}`）+ JWT（EdDSA）认证**，
**不用** API KEY 认证、**不用** GeoAPI 取城市坐标、**不缓存** GeoAPI 数据；
对外的 `PlanWeatherVO` 契约**一字不改**，只重写 Python 侧的 provider 与归一化层。

### 2.1 官方文档内部不一致（记录，不掩盖）

- **API KEY 受限的生效日期**：`authentication` 页写 **2027-01-01**，`project-and-key` 页写 **2027-02-01**。

  第三方文章广泛流传的「1000 次/天 / 60 次每分钟 / 30 次每秒」在官方文档里**查不到**，不作为依据。

## 3. 与现状（Open-Meteo）的差异清单

这些差异决定改动面，也是"只重写 provider"不等于"改个 URL"的原因。

| 维度 | Open-Meteo（现状） | QWeather 新版（目标） | 影响 |
|---|---|---|---|
| 端点 | `api.open-meteo.com/v1/forecast`（固定域名，无鉴权） | `{专属host}/weather/v1/daily/{lat}/{lon}` | **host 必须可配置**，不能硬编码 |
| 认证 | 无 | JWT（EdDSA 签名，`exp` ≤ 24h） | 新增依赖 `PyJWT` + `cryptography`；需缓存 token（建议 15 分钟轮换） |
| 地理编码 | 实测不可达 → 已自带坐标表 | **GeoAPI 禁止缓存/存储**（F10） | 继续用自带坐标表，**恰好合规**；不得为了省事去缓存 GeoAPI |
| 预报窗口 | 16 天 | **最多 10 天** | 前端「超出预报范围」阈值 16 → **10**，Python 常量同步 |
| 按天切分 | `timezone=Asia/Shanghai` | `localTime=true` 返回当地日期时间 | 必须开 `localTime`，否则按 UTC 切天会错一天 |
| 温度 | `temperature_2m_max/min/mean`（℃，裸数字） | `temperatureMax/Min/Avg`：`{value, unit}`（**带单位对象**） | 归一化时要去 `value`，且**不得信任 unit**（校验为 `°C`） |
| 降水概率 | `precipitation_probability_max`：**0–100 整数** | `precipitation.probability`：**0–1 小数** | **× 100 并四舍五入**，这里是典型的"看起来对但对不上"的坑 |
| 降水量 | 未取 | `precipitation.amount{value,unit}`（mm） | 可增加，但契约字段不变 → 只影响 display 拼法 |
| 风 | `wind_speed_10m_max`（km/h），本地换算蒲福级 | `wind.speed{value,unit}`（m/s）+ **`wind.scale` 直接给蒲福风级** | 直接用 `scale`，**不要再自己换算**（否则两套风级口径打架） |
| 天气现象 | WMO 数字码 → 中文（我们维护了 28 条映射） | `daytime.condition.text` **直接是中文**（如「小雨」）+ `code` | 删掉 WMO 映射表；但**要用白天/夜间两个 text**，见 §4.3 |
| 归因 | `attribution` 字符串 | `metadata.attributions` 数组（必须共同显示）+ 固定文案要求 | 前端文案从 Open-Meteo 换成和风，且要带超链 |
| 缓存建议 | 我们定 30 分钟 | 官方推荐 1–6 小时，且要求处理跨天 | 见 §4.4（这一条我建议改） |

## 4. 需要决定的点（我给出建议，等 PM 拍板）

### 4.1 认证方式：JWT（建议） vs API KEY

| 方案 | 优点 | 缺点 |
|---|---|---|
| **JWT / EdDSA（建议）** | 官方推荐；密钥不在请求里传输；不受 2027 年 API KEY 限流影响 | 新增两个依赖（`PyJWT`、`cryptography`）；要实现 token 生成与轮换；私钥必须妥善保管 |
| API KEY | 零新依赖，一行 `X-QW-Api-Key` 即可 | 2027 起被限流（官方两处日期不一致）；SDK 5+ 已不支持；密钥随每个请求传输 |

**建议 JWT**。理由不是"更安全"这种空话，而是：**API KEY 有一条明确的、日期的、不由我们控制的失效路径**，
而 JWT 没有。选它等于把未来的一次被迫迁移提前做掉。

### 4.2 是否保留 Open-Meteo 实现

**建议保留，但只作为 `provider=open-meteo` 的开发/降级选项**，理由：
1. CI 与本地单测**没有 QWeather 凭据**，需要一个不需要 key 的真实上游路径来跑联调；
2. 前端与 Java 层不变，多一个 provider 就是多一层"契约确实与数据源解耦"的证明；
3. 代价很小：`weather.py` 里已经是「调上游 → 归一化」两段，加一个 provider 只是多一个归一化函数。

**不保留也可以**，但那样 `provider` 开关就只剩 `none` 和 `qweather` 两态，CI 里的天气联调会全部退化成 mock——我不推荐。

### 4.3 白天 / 夜间两套天气现象取哪个

QWeather 给 `daytime.condition.text` 与 `nighttime.condition.text`，粒度比 Open-Meteo 细。
**建议：取白天的 `text`**，理由：这是"这天出门大概什么天气"的最常用判断；
夜间天气另行附加在 `display` 后缀（如「小雨转晴」）会超出 64 字符限制的风险，本切片**不加**，只取白天。
如果要显示「小雨转晴」，需要 PM 明确，因为那会改前端展示密度。

### 4.4 缓存时长：30 分钟 → 60 分钟（建议改）

现设计稿写 30 分钟（当时照 `03` §6 的"30–60 分钟"取下界）。官方逐天预报**推荐 1–6 小时**。
**建议 60 分钟**，并额外处理官方点名的跨天问题：

- 缓存到期时间取 `min(now + 60min, 次日 00:10)`；
- 缓存 key 已含 `startDate`，但**用户看的"今天"会跨天**，所以 key 里再加入「请求时的自然日」，
  避免 23:50 缓存的"明天起 3 天"在次日 00:10 之后仍被当成最新。

这一条比"省配额"重要：错误的表现是**用户看到错一天的天气**，而不是少一次请求。

### 4.5 配额与熔断

- 免费额度：**50,000 次/月**（不是每月"重置的 5 万次/天"）。按 60 分钟缓存 + 单飞合并估算：

| 场景 | 日请求量估算 | 月请求量 | 是否在免费额度内 |
|---|---|---|---|
| 100 日活，人均看 3 次计划（缓存命中率高） | ≈ 100–300 | 3,000–9,000 | 是 |
| 1,000 日活，同上 | ≈ 1,000–3,000 | 30,000–90,000 | **可能超**（超出部分 0.0007 元/次，90,000 次约 28 元/月） |

- **必须加熔断**（官方明确的帐号冻结风险，F11）：连续 N 次失败（401/403/429）→ 停止请求一个冷却窗口，
  期间全部走 `available=false`，而不是"继续重试"。指数退避 + 随机抖动，`c` 上限 10。

### 4.6 归因与前端改动

- 文案从 `Weather data by Open-Meteo.com (CC BY 4.0)` 换成 **「天气服务由和风天气驱动」+ 超链 `https://www.qweather.com`**。
- 契约层 `attribution` 字段保留（类型不变），Java 原样透传 `metadata.attributions` 与固定文案；
  **第三方原始字段（如 `metadata.tag`、`astro`、`uvIndexMax`）不出现在对外响应里**（PM 明确要求）。

## 5. 契约不变的具体含义（PM 要求第 3 条）

对外 `GET /api/plans/{planId}/weather` 的响应结构**一个字段都不加、不改**：

```jsonc
// 不变：available / reason / message / source / attribution / fetchedAt / expiresAt / note / stale / days[]
// days[] 不变：dayIndex / date / city / resolvedCity / weather / temperature / precipitation / wind
// 四个 FactField 不变：value / display / source / verified / fetchedAt / expiresAt / note
// source 枚举不变：OPEN_METEO | QWEATHER（新增取值的枚举扩展，不是结构变更）
```

三条硬边界：

1. `source` 从 `OPEN_METEO` 变成 `QWEATHER`。已核对全仓库引用点（共 4 处）：
   前端 **0 处**（`utils/weather.ts` 只读 `attribution` 与 `fetchedAt`，不认 source）；
   Python 2 处（本就要改）；Java 1 处是 `text(root, "source", "OPEN_METEO")` 的**兜底默认值**，
   建议顺手改成 `"NONE"`——默认值写死某个 provider 名，在换源后就会变成一句假话；
2. `reason` 枚举不变（`UPSTREAM_TIMEOUT` / `UPSTREAM_ERROR` 继续承载 429/403 等上游异常）；
3. 新增的 provider 差异**全部关在 `app/tools/weather.py` 里**，Java 与 Vue 不改一行。

## 9. PM 批准结论（2026-11-23）

四项全部采纳建议，不再保留待定项：

| # | 事项 | 最终决定 |
|---|---|---|
| 1 | 认证方式 | **JWT（EdDSA）** |
| 2 | Open-Meteo | **保留**，仅用于 CI / 本地无凭据联调 |
| 3 | 缓存 TTL | **60 分钟 + 跨天失效**（`min(now+60min, 次日 00:10)`，key 加请求自然日） |
| 4 | 天气现象 | **只取白天**（不加「昼转夜」后缀） |

实施约束（PM 逐条给出，均已落地）：

1. API Host 必须可配置，不得硬编码（专属域名，用错 403 INVALID HOST）。
2. `weather.provider` 默认仍为 `none`，不能因为保留 Open-Meteo 就默认启用。
3. 缓存 TTL 与跨天失效见上表；缓存 key 加请求自然日，避免跨天读旧数据。
4. 预报窗口统一为未来 **10 天**，前后端校验口径一致。
5. 归一化：降水概率 ×100 四舍五入；风级直接用 `wind.scale`；QWeather 路径不需要 WMO 映射表。
6. 必须实现熔断，持续错误时停止请求，不允许无限重试。
7. 归因：前端固定展示「天气服务由和风天气驱动」并链接 `https://www.qweather.com`。
8. Java `source` 兜底默认值从 `OPEN_METEO` 改为 `NONE`。

验收原则（PM 原话）：**不改变现有天气响应契约，不影响计划生成，不允许天气故障拖垮计划详情页。**

执行顺序：① 凭据准备 → ② QWeather Provider 与统一归一化层 → ③ 双 Provider 契约测试 →
④ Java / Vue 改动 → ⑤ 真实 API、JWT、熔断、跨天缓存、10 天边界与降级验证。

> **⑤ 尚未完成**：和风天气账号注册需要本人邮箱/手机号与公钥上传，属于账号主体操作，
> 不由开发侧代办。当前状态见 `docs/acceptance/D-03-QWeather-接入报告.md`。

## 10. 实施记录：与本文档原方案的 4 处差异

写下来是为了让"实际做了什么"和"当初批准了什么"可以被对照，而不是事后找补。

### 10.1 响应根是 `days`，且每天没有 `date` 字段（核验资料时没抓到）

官方示例里根是 `metadata` + **`days`**（我原先按旧版 API 记成了 `daily`），
且每一项**没有 date**，唯一时间锚是 `forecastStartTime`（UTC，如 `2024-08-10T22:00Z`）。

影响：日期只能"算"出来。做法是**双轨校验**——先按 `forecastStartTime` 转 +08:00 取日期，
再和"今天 + 序号"交叉比对；一致就用序号（连续、无空洞），不一致就记 warning 并以上游为准。
理由：这一协议没有官方文档承诺"第一天一定是今天"，也没有 `date` 字段，
安静地错一天在界面上完全看不出来。真实凭据联调时脚本会单独检查这一项。

### 10.2 WMO 映射表没有删除，而是移进了 Open-Meteo provider

PM 第 5 条要求"删除 WMO 映射表"。实际处置：**QWeather 路径不再依赖它**（直接用
`daytime.condition.text`），但 Open-Meteo 仍然需要它——而 PM 第 2 条又要求保留 Open-Meteo。
两条要求同时成立时，唯一不矛盾的做法是把它**限制在 Open-Meteo provider 内部**。
结果等价：QWeather 链路上不再有任何码表参与，主归一化层零依赖。

### 10.3 新增 `token_provider` / `clock` 注入点

`weather_jwt.QWeatherTokenProvider` 的时钟与 token 可注入。这不是为测试而测试：
Ed25519 是**确定性签名**，同一秒内同一 payload 会签出完全相同的 token，
"401 后有没有真的重签"这件事只能靠注入才能断言（拿真实 token 比字符串会误判）。

### 10.4 熔断的 `hard` 分级

文档里只写了"必须熔断"。实际按官方错误码分了级，因为两类错误的处置完全相反：

| 类型 | 触发 | 处置 |
|---|---|---|
| hard | 401（重试一次仍失败）/ 403 / 429 / 400 / 404 / 405 / 凭据缺失 | **一次都不重试**，熔断直接进最长冷却 |
| soft | 5xx / 超时 / 结构异常 | 连续 N 次（默认 3）才熔断，冷却 300s，半开失败翻倍至 1800s 封顶 |

理由：403 里包含 NO CREDIT / INVALID HOST / ACCOUNT SUSPENSION，429 是 QPM 超限，
全是"再请求一万次也不会变好、只会加速冻结"的错。而对 401 仍保留**一次**重试——
它可能只是 token 过期或服务器时钟偏差，那是真能自愈的。
