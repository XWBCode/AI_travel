## TD-01 指标端点在密钥缺失时 fail-open

**现象**：`GET /v1/internal/metrics/weather-adjust` 只在"配置了 `AI_INTERNAL_SECRET`"时才校验
`X-Internal-Token`；密钥为空时**直接放行**，返回完整观测数据。

**实测证据**（两实例对比，详见 `灰度上线部署与网络暴露评估.md` §7.4）：

| 场景 | 结果 |
|---|---|
| 配了密钥 + 无令牌 | `403 {"code":40300,"message":"internal token required"}` |
| 配了密钥 + 正确令牌 | `200` + 指标 JSON |
| **未配密钥 + 无令牌** | **`200` 放行** ← 问题所在 |

**为什么当初这么做**：S1~S4 期间没有任何密钥体系，端点若强制要令牌会让存量环境全部 403；
为了不破坏既有调用，选了口径"配了才校验"。

**PM 的裁决**：
> 本轮允许先完成默认回环和容器端口收窄。暂时不要求修改所有 `/v1/plan/*` 接口。
> 但指标端点的 fail-open 必须单独登记为安全技术债。
> 后续生产部署前，必须保证指标端点在密钥缺失时返回 403，而不是放行。

**修复方式**（已定位，约 1 行）：把"密钥非空才校验"改为"密钥为空即 403"，
即 `if not secret: raise 403`。改动点 `backend-ai/app/routers/plan.py` 的
`weather_adjust_metrics` 处理分支。**需要单独立项批准**——它会改变
"未配密钥环境"的返回值，属于行为变更，不是纯加固。

**关闭判据**：密钥为空时该端点返回 403；配了密钥时不带令牌仍返回 403；配了密钥带正确令牌返回 200。

## TD-02 `/v1/plan/*` 无接口级鉴权

**现象**：Python AI 服务的 `/v1/plan/generate`、`/v1/plan/stream`、`/v1/plan/adjust`、
`/v1/plan/intent`、`/v1/weather` 全部**没有任何鉴权**。谁能连上 8000，谁就能直接调用，
绕过 Java 侧的登录态与"计划归属"校验，直接消耗模型额度。

**当前为什么还算安全**：只靠"8000 只绑回环"（本轮已把这条从启动脚本提升为代码默认）。
这是网络边界，不是访问控制——**边界一旦被绕过（端口转发、误配 0.0.0.0、容器 publish），
就等于全开**。

**PM 的裁决**：本轮「暂时不要求修改所有 `/v1/plan/*` 接口」；
"未来生产环境不能依赖 `start-all.bat` 作为唯一安全防线"。

**修复方式**：复用 `X-Internal-Token`（与 `/v1/internal/*` 同一套密钥），
作用到 `/v1/*` 的中间件；Java 端 `AiServiceClient` 的五处请求统一带头。
代价：Python 中间件 1 处 + Java 1 处（集中加头），属于新范围，需单独立项。

**关闭判据**：不带令牌访问 `/v1/plan/adjust` 返回 403；Java 正常链路端到端仍通；
S1~S5 行为不变。

## TD-03 MySQL 3306 / Redis 6379 发布到全网卡

**现象**：`docker-compose.yml` 里 `ports: - "3306:3306"` / `- "6379:6379"` 没有绑回环前缀，
实测 3306 监听在 `::`（所有网卡），同网段任何主机都能直接连数据库。

**为什么本轮没改**：不在 PM 的允许清单内（只批准了 Python 默认 host 与容器 Python 端口两项），
且属于"改基础设施配置"，影响面需要单独评估。

**风险对比**：这条比 8000 端口更严重——数据库一旦可连，前面的接口鉴权全部失去意义。

**修复方式**：改成 `"127.0.0.1:3306:3306"` / `"127.0.0.1:6379:6379"`（只绑宿主机回环），
或生产环境改用容器内网、不 publish。Redis 若已设密码需同时确认 `requirepass`。

**关闭判据**：`Get-NetTCPConnection -State Listen -LocalPort 3306` 显示 `127.0.0.1` 而非 `::`。

## TD-04 Java 8080 监听全网卡

**现象**：实测 Java 后端监听 `::`（所有网卡），不是回环。

**为什么本轮没改**：不在允许清单内；且生产形态下 8080 本就该由 nginx 前置，
是否绑回环取决于 nginx 与 Java 是否同机，需要部署方案定了再定。

**修复方式**：`server.address: 127.0.0.1`（同机 nginx）或保持全网卡但由安全组限制只允许 nginx 访问。

**关闭判据**：非 nginx 来源无法直连 8080。

## 观察项（不构成技术债，但值得记住）

- **`AI_SERVICE_URL` 用 `localhost` 时先解析 `::1`**：Python 只绑 IPv4 回环，JDK `HttpClient`
  实测 5/5 成功、首次 47ms、复用后 1ms，**不构成故障**，因此本轮不改配置（改了属于范围外）。
  若将来出现"偶发连接失败"，第一嫌疑就是这里，改成 `http://127.0.0.1:8000` 即可。
- **运行中的进程可能比代码旧**：本次核查时本机 8000 进程对指标端点返回 404，
  因为它是加端点之前启动的。任何"改了没生效"的疑问，先确认进程启动时间。
