# 旧值（stale）场景：把刷新失败原因传到界面 —— 实施与验证报告

> 任务来源：PM 2026-11-24 第二次决定。原话：
> 「用户看到旧天气数据时，仍然无法判断它为什么没有更新。普通失败和熔断虽然已经区分，
> 但在 `stale=true` 场景下，这个区别没有传递到用户界面。故障状态表达还没有真正闭环。」
>
> PM 给的边界：只批准一个小修复。**不改缓存策略、不改熔断机制、不加手动重置入口、不扩大到其他页面。**

---

## 1. 问题

上一轮把 `CIRCUIT_OPEN` 与 `UPSTREAM_ERROR` 分开了，但只在"没有天气"这条路上生效。
`stale=true`（有旧值、本次刷新失败）这条路上，`reason` 一直是 **null**：

```
PlanWeatherVO { available: true, stale: true, reason: null,
                note: "数据为上次成功获取的结果（本次刷新失败：CIRCUIT_OPEN）" }
```

原因只存在于 `note` 的括号里，是个英文枚举；而前端 `cityNote()` 在 stale 时会把整条 `note` 藏掉
（因为它本来是用来显示城市别名的）。结果：**用户只看到「数据为上次成功获取的结果」，不知道为什么不更新。**

---

## 2. 改动（3 处，都很小）

### 2.1 Java：把原因放进结构化字段

`PlanWeatherService.staleOf()` 增加一行 `vo.setReason(fresh.getReason())`。

- **刻意不设 `message`**：stale 场景那句人话由前端 `WEATHER_STALE_REASON_TEXT` 统一管理，
  Java 再写一份就变成两个文案来源（PM 明确要求"不在 Java 增加翻译表"）。
- **`note` 一个字没动**：它仍然记着「本次刷新失败：<枚举>」，供排障用，但不参与展示。
  不动它的理由很实际——`cityNote()` 靠 `note` 里是否含"上次成功获取"来决定要不要隐藏，
  改文案会顺手把这个判据弄坏，收益却是零。

`PlanWeatherVO.reason` 的注释补了两种含义（available=false / stale=true），
`types.ts` 同步。

### 2.2 Vue：一张表 + 一个函数

`src/utils/weather.ts`：

```ts
export const WEATHER_STALE_REASON_TEXT: Record<string, string> = {
  UPSTREAM_ERROR: '天气服务暂时不可用，正在保留上次数据',
  CIRCUIT_OPEN: '天气服务连续异常，已暂停刷新，稍后会自动恢复',
}
```

只写"语气需要变"的两条，其余继续用 `WEATHER_REASON_TEXT` 兜底——不复制一份完整枚举，
两处各写一遍早晚会不一致。

`staleText()` 顺手改了一处旧文案：`数据为上次成功获取的结果，正在尝试更新`
→ `数据为上次成功获取的结果`。因为熔断期间我们**根本没有出网**，
"正在尝试更新"是一句假话。刷新为什么失败由新增的 `staleReasonText()` 单独说。

`staleReasonText()` 读的是结构化 `reason`，**不从 `note` 抠英文枚举**（PM 要求的第 5 条）。

### 2.3 组件：多一行

`WeatherStrip.vue` 在页脚加一个 `weather-stale` 段落，沿用琥珀色——它是"提醒"，不是报错。

## 3. 验证

### 3.1 三端单测

| 端 | 结果 | 新增 |
|---|---|---|
| Python | 231 passed | 0（本切片不动 Python：`CIRCUIT_OPEN` 上一轮已经在源头分好了） |
| Java | **192 run / 0 fail / 65 skipped** | +2 |
| 前端 | **48 项全 PASS** | +8 |

前端新增 8 条里，有两条是**防回退**的：

```js
check('原因只认结构化 reason，不从 note 里抠英文枚举', staleReasonText({
  ...OK, stale: true, reason: null,
  note: '数据为上次成功获取的结果（本次刷新失败：CIRCUIT_OPEN）',
}), '')
check('note 里写什么都不影响文案', staleReasonText({
  ...OK, stale: true, reason: 'CIRCUIT_OPEN',
  note: '本次刷新失败：UPSTREAM_ERROR',
}), '本次刷新失败：天气服务连续异常，已暂停刷新，稍后会自动恢复')
```

写它们的原因：`note` 里那个英文枚举就摆在那里，是最近的一条捷径。
半年后有人图省事去 `note.split('：')[1]`，这两条会立刻红。

### 3.2 端到端（真实进程，13 项断言全 PASS）

脚本：`backend-ai/scripts/verify_stale_reason_chain.py`（约 80 秒，其中 70 秒在等缓存过期）

拓扑：`Java:8081 → Python:8100（上游替身，模式可从 ok 切到 500）`，两端 TTL 都压到 1 分钟。

| 阶段 | 断言 | 实测 |
|---|---|---|
| 0 | 预热拿到真数据并缓存 | `available=true`、3 天、`expiresAt` 1 分钟后 |
| 1.1 | 旧值仍在：`available=true` + `stale=true` | ✓ |
| 1.2 | 旧数据没被清空 | 逐日 3 条 |
| 1.3 | 原因进了结构化 `reason` | `UPSTREAM_ERROR` |
| 1.4 | 这次刷新确实出网 | 上游调用 1 → 2 |
| 2.1–2.2 | 第 2、3 次刷新仍归因上游 | `UPSTREAM_ERROR` |
| **2.3** | **熔断后旧值场景 `reason` 变成 `CIRCUIT_OPEN`** | `available=true, stale=true, reason=CIRCUIT_OPEN`，3 天数据仍在 |
| 2.4 | 熔断期间没有出网 | 上游调用 4 → 4 |
| 2.5 | 两种失败的原因不同 | `UPSTREAM_ERROR` vs `CIRCUIT_OPEN` |
| 3.1 | 故障期无请求风暴 | 4 次刷新只产生 3 次上游调用（阈值 3） |

**为什么必须真等 70 秒**：Java 的缓存过期时间来自 Python 给的 `expiresAt`（TTL 只有一个来源）。
想造 stale 只有两条路——改代码绕过去（假证据），或者真等它过期。选后者。

### 3.3 Vue 层：同一页面，两个原因各拍一张

| 上游状态 | 页面显示 |
|---|---|
| 熔断已打开 | 三天数据正常显示 · `天气服务由和风天气驱动 · 更新于 1 分钟前` · **数据为上次成功获取的结果** · **本次刷新失败：天气服务连续异常，已暂停刷新，稍后会自动恢复** |
| 熔断已关闭、上游仍 500 | 同上，最后一句变成 **本次刷新失败：天气服务暂时不可用，正在保留上次数据** |

两张图里旧数据都在、`stale` 提示都在，**只有失败原因不同**——这正是 PM 要的"闭环"。

## 4. 过程中踩到的坑

### 4.1 `tab_goto` 同一 URL 只是 hash 导航，不会重新请求

第一张 stale 截图拍出来是旧的降级态。原因是浏览器当前 URL 本来就是
`#/plans/<id>`，`goto` 只改了 hash，**没有重新加载**，页面还是上一次渲染的结果。
必须显式 reload。

教训：验证展示层时，"导航到某 URL"不等于"重新取了一次数据"。
尤其 SPA + hash 路由，同 URL 导航是空操作。

### 4.2 断言口径又错了一次（第 5 次了）

第一版写「5 次请求只产生 ≤3 次上游调用」，实测 4 次 → 假红。
原因是把**预热那 1 次正常取数**算进了"故障期的重试"。
改成把预热与故障期分开计数后：故障期 4 次刷新 = 3 次上游调用（阈值 3），另有预热 1 次。

这是同一个毛病的第五次：**分母没想清楚就开始比大小**。
A 项报告 §6 记过 4 条同类错误，这次是第 5 条。写进本节，是因为它一定会再犯。

## 5. 本次**不声称**的事

1. **不声称多实例语义**：缓存与熔断都是进程内状态。
2. **不声称生产 TTL 下的时序**：本次把 TTL 压到 1 分钟才等得起，生产是 60 分钟。
3. **不声称 `note` 已清理**：note 里仍然是英文枚举，只是不再参与展示。要不要清理需另行决定。
4. **不声称真实 429/403**：全部用替身注入。
5. **不声称其他页面**：PM 明确"不扩大到其他页面"，本次只改计划详情页的天气条。

## 6. M3-2 的前置条件是否已满足

PM 上一轮的话是「我不希望在天气故障状态表达还不够清晰时，把天气进一步引入模型生成链路」，
并把"stale 场景的原因传递"点名为前置条件。

现在四条路径都能被区分：

| 场景 | 用户看到 |
|---|---|
| 没有天气（无城市/无日期/超窗口） | 各自一句可操作的提示 |
| 上游真失败、无旧值 | 「天气服务暂时不可用」 |
| 上游真失败、有旧值 | 「数据为上次成功获取的结果」+「本次刷新失败：天气服务暂时不可用，正在保留上次数据」 |
| 熔断、无旧值 | 「天气服务连续异常，已暂停刷新，稍后会自动恢复」 |
| 熔断、有旧值 | 「数据为上次成功获取的结果」+「本次刷新失败：天气服务连续异常，已暂停刷新，稍后会自动恢复」 |

是否批准 M3-2，由 PM 决定。
