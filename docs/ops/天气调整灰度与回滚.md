# 调整期天气：灰度开关、观测与回滚

> 适用范围：`/plan/adjust` 的天气上下文注入（M3-3 · S1~S5）
> 当前默认状态：**全站关闭**（`WEATHER_INJECT_ON_ADJUST=false`）
> 本文是上线前必须逐条走完的清单，也是出事时的第一份操作手册。

---

## 1. 三颗开关，缺一不生效

注入要多查一次上游天气，代价是用户多等最多 1200ms。所以它不是"打开一个功能"，
而是"同时满足三个条件才查一次"。少一个条件就不查，且**日志会写明是哪一条**。

| # | 开关 | 在哪 | 默认 | 作用 |
|---|---|---|---|---|
| 1 | `WEATHER_INJECT_ON_ADJUST` | 两端环境变量 | `false` | 进程级总开关。false 时连判断都不做 |
| 2 | `WEATHER_INJECT_ADJUST_USERS` | 仅 Python | 空 | 内部账号白名单（`t_user.id`，逗号分隔） |
| 3 | `WEATHER_INJECT_ADJUST_KILL_FILE` | 仅 Python | 空 | 运行时急停：文件存在即停，**不用重启** |
| — | `AI_INTERNAL_SECRET` | 两端**同值** | 空 | 身份签名密钥。空 → 身份不可信 → 一律不放行 |

判定顺序（顺序本身是可观测的契约，排障时按这个顺序看日志）：

```
总开关关        → INJECT_DISABLED      （去改配置）
数据源未启用    → PROVIDER_DISABLED    （去看 WEATHER_PROVIDER）
急停文件存在    → GRAY_KILLED          （有人在急停，去看文件）
prod 且白名单空 → GRAY_NO_WHITELIST    （去配名单）
身份缺失/伪造   → IDENTITY_UNTRUSTED   （去看 Java 有没有发头、密钥是否同值）
可信但不在名单  → NOT_IN_WHITELIST     （去加名单）
全部通过        → GRAY_ALLOWED         （这时才会出网）
```

**为什么先判总开关再判身份**：如果顺序反过来，"功能没开"会被报成"身份不可信"，
排障的人会跑去查网关，而真正要做的只是改一个环境变量。

## 2. 身份为什么不是"一个请求头"

Java 调 Python 时带两个头：

```
X-User-Id: 1001
X-Identity-Sig: hmac_sha256(AI_INTERNAL_SECRET, "1001|<traceId>")   # 小写十六进制
```

- 签名绑定 `traceId`，把 A 请求的签名搬到 B 请求上无效（重放被拒）。
- 密钥只在两端环境里，不进仓库、不进前端、不进日志。
- Java 侧拿不到密钥或签不出来时**不发头**——宁可灰度不生效，也不发一个假身份。
- Python 侧密钥为空时**一律判为不可信**，即使头齐全。

> 跨语言一致性由两边的用例钉死：`AiServiceIdentityHeaderTest`（Java，真 HTTP 抓头）
> 与 `test_inject_gate.py::test_signature_matches_java_constant`（Python）用的是**同一个
> 字面量哈希**。任何一边改了编码/大小写/分隔符，两个用例会立刻红，而不是"灰度悄悄不生效"。

## 3. 观测：四类结果必须分得开

端点（内网，只读，无用户内容）：

```bash
curl -s -H "X-Internal-Token: $AI_INTERNAL_SECRET" \
  http://127.0.0.1:8000/v1/internal/metrics/weather-adjust | jq
```

```json
{
  "gray":    {"allowed": 128, "denied": {"NOT_IN_WHITELIST": 900, "IDENTITY_UNTRUSTED": 3}},
  "outcome": {"injected": 120, "no_weather": 7, "circuit_open": 1,
              "value_gate": 2, "gray_denied": 900},
  "upstream":{"calls": 96, "cities": 210, "cacheSavedRate": 0.5429},
  "latencyMs":{"weather": {"p50": 3, "p95": 210, "samples": 128},
               "total":   {"p50": 4300, "p95": 9100, "samples": 128}}
}
```

对应 PM 点名的七个指标：

| 指标 | 取法 |
|---|---|
| 天气调整触发次数 | `gray.allowed` |
| 上游请求次数 | `upstream.calls` |
| 缓存命中率 | `upstream.cacheSavedRate`（= 1 − calls/cities，**派生值**，不是直接计数） |
| 天气调整成功率 | `outcome.injected / (injected + no_weather + circuit_open)` |
| 天气调整耗时 P50/P95 | `latencyMs.weather` |
| 熔断次数 | `outcome.circuit_open` |
| 数值闸门拦截次数 | `outcome.value_gate` |

两条口径必须守住，否则数字会骗人：

1. **`circuit_open` 与 `no_weather` 分开**：熔断是"我们主动不出网"，真 500 是"出网了但对面挂了"。
   合成一个错误率，就看不出上游到底有没有被打。
2. **`gray_denied` 不计入延迟分位数**：它的 0ms 是"没查"，不是"很快"。混进去会把 P50 拉低。
   代码里用显式的 `timed=` 标记，**不用"数值是否为 0"来判断**——本机替身下 0ms 是有效样本。

灰度用户与非灰度用户的对照，直接看同一时间窗内 `gray.allowed` 与
`denied.NOT_IN_WHITELIST` 的比值，以及 `upstream.calls` 是否只随 `allowed` 增长。

## 4. 上线检查清单

### 一条命令代替人肉看配置

```bash
cd backend-ai
APP_ENV=prod WEATHER_PROVIDER=qweather \
AI_INTERNAL_SECRET=*** WEATHER_INJECT_ADJUST_USERS=1001 \
  ./.venv/Scripts/python.exe scripts/check_gray_readiness.py --url http://127.0.0.1:8000
```

`--url` 会顺带核对"跑着的服务"与这份配置是否一致（密钥同值、指标端点可用）。
退出码 1 = 不能开 G1，输出里直接写"先修哪几项"。九项检查：`APP_ENV` / 数据源 /
总开关 / 密钥 / 白名单 / 急停路径可写 / 服务侧可读（含 7.1/7.2 两条子判定） /
**指标端点是否裸奔** / **业务接口是否要令牌**。

> 第 7.2 与第 8 项是 PM 验收后追加的：只验"对的令牌能进"会漏掉"服务端压根不校验"这种情况，
> 所以再拿一个错令牌试一次；同时单独判一次"不带令牌能不能读"。
>
> **2026-11-24 更新**：TD-01 已修（fail-closed），所以第 8 项的判词也随之改了，按响应 `code` 分流：
> - `403` + `40301` → `WARN 端点已 fail-closed，但服务端没配密钥`（端点不裸奔，但这个实例不能开灰度）
> - `403` + `40300` → `OK 指标端点已 fail-closed（TD-01 关闭）`
> - `200` → `FAIL`(prod) / `WARN`(dev)，仍是 fail-open
>
> 另外第 7 项加了前置分流：本地密钥为空时直接 `WARN 跳过服务侧核对`。
> 否则"我自己没配"会因为同样返回 403 而被误报成"服务端配了别的值"。
>
> **2026-11-24 又加第 9 项**（TD-02）：拿 `/v1/plan/intent` 当探针，无令牌打一枪。
> `403` = 业务接口已要求令牌（理想）；`200` 且本地配了密钥 = 闸门没生效（`FAIL`）；
> `200` 且本地没配密钥 = dev 回环放行（`WARN`，知情即可）。

**它查不出来的**：和风凭据是否有效（用 D-03 的联调脚本）、上游额度与账单、
名单里的人是否真的该在里面（那是 PM 的判断）。

## 5. 回滚（三级，越靠前越快）

| 级别 | 动作 | 生效时间 | 影响面 | 何时用 |
|---|---|---|---|---|
| L1 急停 | `touch $WEATHER_INJECT_ADJUST_KILL_FILE` | **下一次请求** | 只停注入，进程不动 | 观测到异常，先止血 |
| L2 关总开关 | `WEATHER_INJECT_ON_ADJUST=false` + 重启 | 重启后 | 与上线前完全一致 | 需要彻底回到旧行为 |
| L3 回滚代码 | `git revert` S5 提交并重新部署 | 一次发布 | 含身份头一起撤掉 | 身份/密钥机制本身有问题 |

L1 与 L2 之后都要验证一次"旧行为回来了"：

- 白名单账号再调整一次，Prompt 里**不该**出现「【已核实的天气预报】」
- `gray.denied.GRAY_KILLED`（L1）或 `gray.denied.INJECT_DISABLED`（L2）+1
- 调整仍返回合法建议（`code=0` 且有 ops）

数据库无需回滚：整个功能不写任何表，也不改响应结构。

## 6. 已知边界（写在前面，免得被当成 bug）

1. **`APP_ENV` 未声明时白名单闸门不生效**：只有显式 `prod` 才要求白名单。
   这与数据源合规闸门是同一条边界，兜底都是本清单第 4 节。
2. **急停是"单实例"的**：多实例部署时，每个实例读自己那份文件路径。要全站急停，
   要么把文件放在共享卷，要么用 L2。
3. **密钥轮换会让灰度短暂失效**：两端不同值的窗口内，所有人都是 `IDENTITY_UNTRUSTED`。
   轮换请两端同时改、同时重启。
4. **`cacheSavedRate` 是派生值**：它由 `1 - calls/cities` 算出，包含"坐标未知/熔断"这些
   本地就不出网的城市，所以会略高于"真正的缓存命中率"。要看真值得看日志里的 `upstream=0` 行。
5. **指标端点要求 `X-Internal-Token`**（配了密钥时）：无令牌返回 403。
   指标本身不敏感，但"这个服务对公网无鉴权"不该因为一个只读端点变成默认事实。
6. **`value_gate` 只统计"注入过天气且被数值闸门拒绝"**：它走的是既有的
   `AdjustError`（10003）路径，用户看到的是"建议里抄了天气数值，请换一种说法重试"。
   它与"建议结构不合法"（`failed`）分开计数，因为后者与天气无关。
