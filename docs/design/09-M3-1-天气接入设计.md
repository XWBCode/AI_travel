## 1. 为什么先做「展示」而不是「生成时注入」

M3 的完整愿景是「AI 知道天气并据此给建议」。如果第一步就改生成链路，会有三个立刻出现的麻烦：

| 若从生成链路切入 | 后果 |
|---|---|
| 生成时调天气 | 一次生成 +1 个外部依赖，外部 3s 超时会把 130s 的成功率再拉低一档 |
| 天气进模型上下文 | 提示词要改、校验规则要改（`source=TOOL` 的 FactField 有值），等于同时动 3 个已验收的部件 |
| 天气失败怎么办 | 生成链路上的降级路径要重新设计一遍，R7 刚验完的链路又要重测 |

反过来，**「生成之后按需展示」** 有四个好处：生成链路零风险、天气失败只影响一个小卡片、
可以独立验收（AC 只针对这个接口）、后续把天气喂给模型时数据层已经就绪。

所以切片一 = 只读的天气展示。模型什么时候用天气，是切片二的事。

## 2. 架构与归属

```
前端 PlanDetailView
   └─ GET /api/plans/{planId}/weather        （Java：编排 + 缓存 + 降级 + 鉴权）
        └─ GET /v1/weather?city=&start=&days=  （Python AI 服务：外部调用 + 归一化）
             └─ api.open-meteo.com/v1/forecast （外部数据源）
             └─ city_coords.json              （本地城市坐标表）
```

归属原则沿用现有分层：

| 环节 | 归属 | 理由 |
|---|---|---|
| 外部 API 调用 | **Python AI 服务** | 「工具」是 AI 服务的能力，Java 不直连第三方（与 `03` §2 一致）；也便于以后做成模型可调用的 tool |
| 鉴权、缓存、降级、错误码 | **Java** | 用户身份、计划归属、业务错误码都在 Java；缓存放在调用方才有意义 |
| 展示 | **Vue** | 只消费结构化 FactField，不判断「能不能显示」 |

## 3. 数据源与合规（这是本切片最大的约束）

| 项 | 结论 |
|---|---|
| 首选（开发 / 内部演示） | **Open-Meteo 免费端点**：无需 key，实测 `api.open-meteo.com/v1/forecast` 可用（1.3s 返回） |
| 合规红线 | 免费端点**明确禁止商业使用**，数据 CC BY 4.0 **必须署名**。→ 响应里强制带 `attribution` 字段，前端必须展示「数据来源 Open-Meteo」 |
| 生产 | **不能直接上线免费端点**。等 `D-03`（和风天气 / 高德）定案后切换，本切片只留一个 `provider` 开关 |
| 配置 | `weather.provider: none \| open-meteo`，**默认 `none`**（生产配 prod 时保持关闭），开发/演示环境显式打开 |

### 3.1 一个实测发现：geocoding 端点在本机不可达

`geocoding-api.open-meteo.com` 实测返回 `code=000`（7.5s 后失败），而 `api.open-meteo.com` 正常。
也就是说**「城市名 → 经纬度」这一步不能依赖 Open-Meteo 的地理编码**，否则天气功能会挂在第一步，
而且失败原因很隐蔽（不是 4xx，是连不上）。

**做法**：切片一自带 `backend-ai/app/tools/city_coords.json`（约 100 个常用城市 + 省会，含经纬度与时区），
先查表；表里没有才尝试 geocoding（失败即降级）。理由：

- 计划里的城市是**有限集合**（实测 20 条真实生成只出现 20 个城市），一张表就够；
- 查表是确定性的，不受第三方可用性影响，也不会因为网络抖动变成随机失败；
- 省 / 大区名（如 `云南`）在表里映射到省会，并在 `note` 里写明「按昆明代表云南」，不假装精确。

## 4. 接口契约（提案）

### 4.1 对外：Java

```
GET /api/plans/{planId}/weather        需要登录，且计划必须属于当前用户
```

**200（可用）**

```json
{
  "available": true,
  "source": "OPEN_METEO",
  "attribution": "Weather data by Open-Meteo.com (CC BY 4.0)",
  "fetchedAt": "2026-11-23T22:40:00+08:00",
  "expiresAt": "2026-11-23T23:10:00+08:00",
  "note": null,
  "days": [
    {
      "dayIndex": 1,
      "date": "2026-11-24",
      "city": "成都",
      "temperature": {
        "value": null, "display": "12–16℃", "source": "TOOL", "verified": true,
        "fetchedAt": "2026-11-23T22:40:00+08:00", "expiresAt": "2026-11-23T23:10:00+08:00",
        "note": ""
      },
      "precipitation": { "value": 6, "display": "降水概率 6%", "source": "TOOL", "verified": true, "...": "..." },
      "wind": { "value": null, "display": "微风", "source": "TOOL", "verified": true, "...": "..." }
    }
  ]
}
```

**200（不可用）** —— 注意：**降级不是错误**，不返回 5xx，前端照常渲染页面，只把天气区域换成提示

```json
{
  "available": false,
  "reason": "NO_START_DATE",
  "message": "这份计划还没有出发日期，选好日期后可以查看天气",
  "source": "NONE",
  "days": []
}
```

`reason` 取值：`NO_START_DATE` / `NO_CITY` / `DATE_OUT_OF_RANGE` / `CITY_UNKNOWN` / `PROVIDER_DISABLED` / `UPSTREAM_TIMEOUT` / `UPSTREAM_ERROR`。

> 为什么用 200 + `available=false` 而不是 4xx：这是「计划页的附属信息缺失」，不是请求错误。
> 用 4xx 会让前端把整页当失败处理，也会污染错误率监控。

### 4.2 内部：Python

```
GET /v1/weather?city=成都&start_date=2026-11-24&days=3
```
返回 `{ "ok": true, "source": "OPEN_METEO", "days": [...], "fetchedAt": ..., "expiresAt": ... }`
或 `{ "ok": false, "reason": "UPSTREAM_TIMEOUT" }`。
**内部接口同样用 200 表达可预期的失败**，只有参数非法才 422。

### 4.3 日期口径（PM 已拍板：C）

真实数据里 **`basic.startDate` 经常是 null**（20 条复验里 10 条有值，6 条小样本全为 null）。
没有出发日期就没有「哪天天气」可查。三个候选：

| 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| A | 无 `startDate` → `available=false, reason=NO_START_DATE`，前端提示「选好出发日期后可查看天气」 | 不猜、不误导 | 大部分计划第一次打开看不到天气 |
| B | 无 `startDate` → 按「今天起 N 天」查，显式标注「按今天起算」 | 总有东西可看 | 用户可能 12 月出行，看到的是今天的天气——**这就是「看起来像真数据的假信息」** |
| **C（PM 选定）** | A + 前端引导「补出发日期」 | 兼顾不误导与可用性 | 需要额外做一处引导交互 |

**PM 决定**：取 **C**。没有 `startDate` 时不请求天气、不展示默认日期天气，
显示「补充出发日期后可查看天气」，点击引导补填日期。

落地口径（写进代码注释，避免后面被"优化"掉）：

- **禁止**用"今天"或任何默认日期代替真实 `startDate`——这就是 B 被否掉的原因，属于编造数据。
- 引导补填走已有的计划编辑入口，本切片**不新增编辑接口**，只做一处文案 + 跳转。
- `reason=NO_START_DATE` 与「有日期但超出预报窗口的 `DATE_OUT_OF_RANGE`」必须是**两个不同提示**：
  前者用户能自己解决（补日期），后者只能等（临近再看）。混成一个提示会让人白找半天。

### 4.4 展示位置（PM 已拍板）

天气条位于**计划详情页顶部**：**基本信息（标题 / 城市 / 日期 / 预算）下方、行程列表上方**。

理由（PM 给的口径 + 我们的场景）：天气是"行前判断"信息，用户进详情页第一眼要能判断
"这几天合适吗"；放进每天行程内部则要求用户先逐天滚动，失去了概览价值。
`available=false` 时同位置显示一行提示，位置不变——**不要在降级时把这块从布局里抽掉**，
否则页面高度来回跳。

## 5. 降级矩阵（逐条对应 `03` §4）

| 场景 | Python | Java | 前端 |
|---|---|---|---|
| 配置 `provider=none` | — | 不调上游，直接 `PROVIDER_DISABLED` | 「天气功能未开启」（内部演示环境才可能出现） |
| 计划无 `startDate` | — | **不调上游**，直接 `NO_START_DATE` | 「补充出发日期后可查看天气」+ 引导补填（§4.3 C） |
| 城市不在坐标表且 geocoding 失败 | `CITY_UNKNOWN` | 透传 | 「该地点暂无天气数据」 |
| 出行日期超出预报窗口（>16 天） | `DATE_OUT_OF_RANGE` | 透传 | 「出发日期太远，临近再看」 |
| 上游超时（>3s） | `UPSTREAM_TIMEOUT` | 透传 + 记 warn | 「天气暂不可用」 |
| 上游 5xx / 脏数据 | `UPSTREAM_ERROR` | 透传 + 记 warn | 「天气暂不可用」 |
| 缓存命中 | — | 直接返回，`fetchedAt` 保留原始时间 | 显示「更新于 X 分钟前」 |
| 缓存过期但上游挂了 | — | **返回过期缓存** + `note="数据更新于 …"` | 展示旧值 + 灰字提示 |

最后一行是 `03` §4 的要求（过期展示旧值 + 标注），也是最容易被忽略的一格。

## 6. 缓存

| 项 | 方案 |
|---|---|
| 位置 | Java，进程内（`ConcurrentHashMap` + TTL，不引入 Caffeine 以外的依赖） |
| key | `planId` + `startDate` + `days`（计划改了日期就自动失效） |
| TTL | 30 分钟（`03` §6：城市天气预报 30–60 分钟） |
| 上限 | 1000 条 + LRU 淘汰，避免长期运行内存增长 |
| 过期策略 | 过期后**先返回旧值**并发起刷新，刷新失败仍返回旧值（`note` 标注） |

**已知限制**：进程内缓存 = 单机状态。多实例时每台各存一份，命中率下降但不会出错
（与 R7 §6.3 同一类问题，已登记，本切片不解决）。

## 7. 超时与并发

| 环节 | 超时 | 说明 |
|---|---|---|
| Python → Open-Meteo | connect 2s / read 3s | 外部 API 必须设超时（`03` §6 U 条） |
| Java → Python | 5s | 比 Python 内部总预算宽，留序列化与网络余量 |
| Java → 前端 | 同步 HTTP，不占 SSE 线程池 | 走普通 Tomcat 线程；**绝不复用 `ai-stream-*` 线程** |
| 并发 | 同一 planId 的并发请求合并成一次上游调用（`computeIfAbsent` 式单飞） | 防止用户狂点刷新打爆上游配额 |

## 9. 测试与验收标准（提案）

| 编号 | 验收项 | 判据 |
|---|---|---|
| W-1 | 有日期 + 已知城市 | 每天 3 个 FactField，`source=TOOL`、`verified=true`、带 `fetchedAt`/`expiresAt`，`display` 带单位 |
| W-2 | 上游超时 | 3s 内返回 200 + `available=false, reason=UPSTREAM_TIMEOUT`；计划页其余内容正常 |
| W-3 | 无出发日期 | `NO_START_DATE` + 可读文案，**不显示任何数值** |
| W-4 | 缓存 | 30 分钟内二次请求 **0 次**上游调用（用计数器断言，不靠日志目测） |
| W-5 | 过期回退 | 上游挂掉时返回旧值且 `note` 标注更新时间 |
| W-6 | 越权 | 别人的计划返回 403，不泄露任何天气数据 |
| W-7 | 生成链路无回归 | 同一条输入，生成耗时与成功率对照 §9 基线不劣化（跑 3 条即可） |
| W-8 | 合规 | 响应含 `attribution`；前端展示来源；`provider=none` 时全部降级 |

## 12. 一句话给 PM

切片一的全部价值是**「让『天气』这个字段第一次有了真值，而且失败时看得出来是失败」**。
它不改变生成链路，所以风险被限制在一个新接口 + 一个卡片里；它的产出（带 `source`/`fetchedAt` 的天气数据）
正好是切片二「AI 根据天气给建议」的输入。需要你先定 §4.3 的日期口径。
