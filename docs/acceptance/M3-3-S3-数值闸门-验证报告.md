## 1. 为什么闸门不放进 `validate_ops`

PM 的验收要求是"天气关闭、没有注入、天气查询失败时，原校验器行为保持不变"。有三种做法：

| 做法 | 能否证明"行为不变" | 结论 |
|---|---|---|
| 给 `validate_ops` 加 `weather_injected=False` 参数 | 只能靠测试证明分支没走错 | 否 |
| 在 `validate_ops` 内部读全局开关 | 隐式依赖，更难验 | 否 |
| **独立函数 + 调用点决定是否启用** | **`validate_ops` 一个字符没改，diff 可证** | **采用** |

所以闸门是 `weather_adjust.validate_weather_values(summary, ops)`，由 `run_adjust` 在
`weather.injected` 为真时调用。拦截逻辑与"要不要拦"彻底分开，后者只有一个判断点。

## 2. 检查范围

| 项 | 取值 | 依据 |
|---|---|---|
| 字段 | `summary` / `title` / `note` / `theme` | PM 批复的四个字段 |
| 不查 | `city`（地名含数字是正常形态）、`startTime` / `endTime`（HH:mm 本来就带数字）、`itemId` | 同上 |
| 覆盖位置 | op 顶层 `title`/`note`、`changes[].after`（field 属于上述三类）、`ADD_ITEM` 的 `title` | 实际会写自由文本的所有位置 |
| 命中处置 | 抛 `AdjustError`（`code=10003`，与其它"建议不合规"同类），消息带命中片段 | 沿用既有处置：本地拒绝 + 用户重说，不重试、不删文本、不静默放行 |

### 正则

```python
WEATHER_VALUE_PATTERN = re.compile(
    r"[0-9０-９]+\s*(?:%|％|℃|°C|°|摄氏度|度|级|毫米|mm|MM|厘米|cm|米/秒|m/s|米每秒)"
)
```

**刻意不复用 `contract.NUMERIC_UNIT_PATTERN`**：那个正则服务于已冻结契约的 `freeText` 校验，
给它加 `%` / `级` 会改变生成链路已验收的行为。这里只认天气语境会出现的单位，
不认"分钟/小时/元/公里"——那些是行程本身的单位，拦它们等于顺手改了调整规则。

## 4. 误伤边界（防"拦得太宽"）

| 文本 | 是否命中 | 说明 |
|---|---|---|
| `15:00 出发` | 不命中 | 时间不是天气单位 |
| `第2天再去` | 不命中 | 「天」不在单位表里 |
| `下午3点集合` | 不命中 | 「点」不在单位表里 |
| `4星级酒店` | 不命中 | 数字与「级」之间隔着「星」（正则要求相邻） |
| `两个人一起去` | 不命中 | 「个」不在单位表里 |
| `五星级` | 不命中 | 中文数字本就不在识别范围（见 §5） |

5 项均为单测断言（`test_injected_does_not_misfire_on_normal_text`）。

## 5. 已知限制（不假装挡住了）

**中文数字漏网**：「十几度」「三四级风」「三十来度」不命中。

不扩正则的理由：扩到中文数字会把「一起」「十分」「一点」这类正常表达一起误伤，
而调整链路上误伤的代价是**合法建议被拒、用户得重说一遍**，比漏网更糟。
补它的是 S4 的 AC-A10（抽样 20 条注入过天气的建议，人工确认无数值转述）与 AC-A12（闸门触发率统计）。

这条限制按 PM 要求**明确记录**，不宣称完全防止天气数值泄漏。
