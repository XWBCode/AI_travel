>
> **D-06 冻结记录**：Q-01~Q-14 的结论见 `08-TravelPlan-v1-冻结决议.md`；唯一实现来源是 `contracts/travel-plan/` 下的两份 JSON Schema。**第 2 节的 TypeScript 定义保留为评审期原稿，不再作为实现依据**——其中 `preferences.source`（改为四项）、`basic.destination` 单值（新增 `destinations[]`）、`TransportSegment` 结构（新增 `scope`）、`aiNote` 的 Markdown 约定（改为纯文本）、缺 `version` 五处已被决议取代，冲突时以 08 与 contracts 为准。

## 1. 契约归属与责任边界

| 环节 | 责任方 | 说明 |
|---|---|---|
| Schema 定义 | 本文件（评审冻结后为唯一来源） | 前后端与 AI 三方共同遵守 |
| AI 输出生成 | Python AI 服务 | 按 Schema 生成，只输出 JSON，不在同一响应里混 Markdown |
| Schema 校验 | **Java 业务服务** |  Python 不写业务库；Java 是落库前的最后一道闸 |
| 落库 | Java 业务服务 | 校验通过才写，失败写 `t_ai_generation_log` |
| 渲染 | Vue3 | 只消费结构化字段，Markdown 仅用于「AI 生成说明」等描述性文本 |

> **U**：Python 不得直接连接 MySQL 修改业务数据（总纲 3.3、4.3）。AI 输出的只是「提案」，是否成为正式数据由 Java 决定。
> **U**：AI 对话输出格式与业务数据格式是两个概念（总纲 4.5）；Markdown 不得作为数据库唯一数据结构。

## 2. `TravelPlan` v1 结构

以下定义用 TypeScript 表达（前端直接复用，后端按同结构建 DTO）。配套 JSON Schema 由 M1 开工时从本定义生成，放进 `backend-ai/app/schemas/travel_plan_v1.json`。

```ts
/** 所有实时性字段的包装，见 03 节 FactField 契约 */
interface FactField<T = unknown> {
  value: T | null
  display: string
  source: 'NONE' | 'MODEL_KNOWLEDGE' | 'USER' | 'TOOL' | 'CACHE'
  verified: boolean
  fetchedAt: string | null
  expiresAt: string | null
  note: string
}

type PlanStatus = 'DRAFT' | 'CONFIRMED' | 'IN_PROGRESS' | 'COMPLETED' | 'CANCELLED'

interface TravelPlan {
  schemaVersion: '1.0'
  planId: string | null          // 新建为 null，落库后由 Java 回填
  title: string
  status: PlanStatus             // AI 输出时只允许 DRAFT
  basic: {
    originCity: string | null
    destination: string | null
    startDate: string | null     // YYYY-MM-DD
    endDate: string | null
    days: number | null
    travelers: number | null
    missingFields: string[]      // 未识别字段，禁止填默认值冒充
  }
  preferences: {
    interests: string[]
    transport: string | null
    accommodation: string | null
    specialRequirements: string[]
    source: 'USER' | 'USER_DEFAULT' | 'MODEL_KNOWLEDGE'
  }
  days: TravelDay[]
  budget: {
    currency: 'CNY'
    total: FactField<number>
    items: BudgetItem[]
    note: string
  }
  risks: string[]                // 注意事项，非实时，可用模型知识
  aiNote: string                 // AI 生成说明（Markdown），仅展示用
  unverifiedFieldCount: number   // 便于埋点与 AC-08 校验
}

interface TravelDay {
  dayIndex: number
  date: string | null
  city: string
  theme: string | null
  items: TravelItem[]
  transportSegments: TransportSegment[]
  accommodation: Accommodation | null
}

interface TravelItem {
  itemOrder: number
  attractionId: string | null
  title: string
  startTime: string | null       // HH:mm，建议时间，非实时
  endTime: string | null
  duration: FactField<number>    // 分钟；L0 恒为 null
  openHours: FactField<string>
  ticketPrice: FactField<number>
  note: string
}

interface TransportSegment {
  fromItemOrder: number
  toItemOrder: number
  mode: string | null            // 步行/公交/包车等一般性建议
  duration: FactField<number>    // L0 恒为 null
  distance: FactField<number>    // L0 恒为 null
  advice: string                 // 不得含具体数字
}

interface BudgetItem {
  category: 'TRANSPORT' | 'ACCOMMODATION' | 'FOOD' | 'TICKET' | 'OTHER'
  label: string
  amount: FactField<number>
  note: string
}

interface Accommodation {
  areaName: string
  suggestion: string
  priceRange: FactField<string>
}
```

### 2.1 Schema 级硬约束

| 约束 | 违反时 |
|---|---|
| `status` 只能为 `DRAFT` | 拒绝落库，记 `SCHEMA_VIOLATION` |
| `FactField.verified=false` → `value` 必须为 `null` | 拒绝落库 |
| `source` 不在枚举内、`fetchedAt` 缺失但 `verified=true` | 拒绝落库 |
| `days.length === basic.days`（当 `days` 非空时） | 拒绝落库 |
| `dayIndex` 从 1 连续递增、`itemOrder` 日内唯一 | 拒绝落库 |
| `unverifiedFieldCount` 与实际统计不一致 | 拒绝落库（防模型自报不实） |
| `risks` / `aiNote` 中出现具体天气/车次/票价数值 | 文本规则拦截，拒绝落库 |
| `basic` 中未知字段为 `null` 且列入 `missingFields` | 违反则拒绝（AC-06） |

> 最后两条是**针对"模型绕过 FactField 把数字写进自由文本"**的兜底。只做字段级校验不够，必须对自由文本做正则扫描（温度/℃/元/车次/分钟等模式）。

## 3. 校验与降级流程

```
Python 生成 JSON
   ↓ SSE: plan_draft（携带完整 JSON，或分片 JSON Patch）
Java 接收 → 结构校验 → FactField 约束校验 → 自由文本扫描
   ├─ 通过 → 写 t_travel_plan / t_travel_day / ... (事务) → SSE: plan_saved
   └─ 失败 → 写 t_ai_generation_log(raw_response, fail_reason)
              → SSE: error {code:10002, message:"生成失败，请重试"}
              → 业务表写入数 = 0
```

| 情况 | 策略 |
|---|---|
| 首次校验失败 | **不自动重试**（避免无限循环与额外成本），提示用户重试；原始响应留痕 |
| 部分字段违规但主体可用 | **不做"自动修复"**，一律拒绝。自动补全等于替模型编造 |
| 模型返回 Markdown 而非 JSON | 拒绝，记录 `INVALID_FORMAT` |
| 模型返回截断的 JSON | 拒绝，记录 `TRUNCATED` |
| 连续 3 次校验失败 | 触发告警，暂停该模型的计划生成能力并通知技术负责人 |

**U**：任何情况下不得把未通过校验的内容写入正式计划表（R-14 / AC-07）。

## 4. SSE 事件协议

现有 `/api/chat/stream` 已实现 `meta / delta / done / error`（见 README），保持兼容。M1 新增计划生成相关事件：

| 事件 | data | 方向 | 说明 |
|---|---|---|---|
| `meta` | `{sessionId, userMessageId}` | 现有 | 流开始 |
| `delta` | `{content}` | 现有 | 对话增量文本；计划生成完成后也用它下发一句摘要 |
| `done` | `{messageId, model, latencyMs}` | 现有 | 对话结束 |
| `error` | `{code, message}` | 现有 | 失败 |
| **`intent`** | `{scene, needPlan, missingFields[], followUps[]}` | 新增 | 意图判定结果；`needPlan=false` 时 `followUps` 是**带候选值的中文问句**，前端可直接渲染成可点选按钮 |
| **`plan_progress`** | `{stage, message}` | 新增 | 生成中的阶段提示（真实模型可能十几秒，避免聊天框空白） |
| **`plan_draft`** | `{plan: TravelPlan}` | 新增 | 校验通过后的计划草稿（**已校验**，不是模型原始输出） |
| **`plan_saved`** | `{planId, version}` | 新增 | 落库成功；`planId` 为**字符串**（雪花 ID 超出 JS 安全整数） |
| **`plan_rejected`** | `{reason, message}` | 新增 | 校验失败 / 信息不足；紧跟一个 `error` 事件负责收尾 |

一轮对话只会走三条路之一（由 Java 侧 `ChatController` 路由）：

| 路径 | 事件序列 | 触发条件 |
|---|---|---|
| 普通闲聊 | `meta → delta… → done` | `scene=general` 或意图服务不可用 |
| 追问槽位 | `meta → intent → delta(追问文案) → done` | `needPlan=false` 且有 `followUps` |
| 生成计划 | `meta → intent → plan_progress → plan_draft → plan_saved → delta(摘要) → done` | `needPlan=true` |

`intent.followUps` 的元素结构（追问必须给明确候选，不能让用户猜格式）：

```json
{
  "field": "days",
  "question": "大概玩几天？",
  "options": [
    { "label": "3 天", "value": "玩3天" },
    { "label": "4 天", "value": "玩4天" }
  ]
}
```

- `field`：槽位名（`destination` / `days`），前端用它记录该组的选择。
- `label`：按钮文案，短。
- `value`：**补答短语**，不是裸值。前端提交「原话 + value」重新走意图判定，
  因此 `value` 必须自带语法信息——`帮我规划三天，成都` 抽不出目的地，
  `帮我规划三天，去成都玩` 才可以。
- 一组内单选；多组时逐组选择，全部选满后一次提交，避免补一半又被问一遍。

统一要求：

- **U**：所有事件携带 `traceId`，与日志、埋点、AI 生成留痕关联。
- **U**：每个流必须以 `done` / `error` 之一结束，不得无声中断。
- **U**：客户端断开时，后端仍应完成落库或标记 `FAILED/CANCELED`（现有实现已覆盖）。
- **U**：SSE 响应头必须带 `Cache-Control: no-cache` 与 `X-Accel-Buffering: no`（现有实现已覆盖）。

### 4.1 Python 侧实现（WP3 已完成）

AI 服务只暴露两个内部端点，仅由 Java 调用，不对前端直接开放：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/plan/intent` | 规则判定意图，普通 JSON 返回 `{scene, needPlan, missingFields, slots, followUps}`，不调模型 |
| POST | `/v1/plan/stream` | 生成计划，SSE 下发 `intent → plan_draft → done`；信息不足时只发 `intent → done{skipped: NEED_MORE_INFO}` |

补充约定：

- `intent` 与 `plan_draft` 都带 `traceId`，由服务统一注入，避免各分支漏写。
- `plan_draft.plan` 是**已通过契约校验**的内容；校验失败时下发 `plan_rejected{reason, errors[]}`，紧跟 `error{code:10002}`。
- 拒绝原因取值：`NEED_MORE_INFO`（信息不足未生成）/ `SCHEMA_VIOLATION` / `INVALID_FORMAT` / `TRUNCATED`。
- 生成侧不自动重试、不自动修复，与 §3 一致；原始响应由 Java 写 `t_ai_generation_log` 留痕。

### 4.2 Java 侧接线（M1 P1 已完成）

`/api/chat/stream` 在发出 `meta` 之后、进入模型调用之前，先同步调用 `/v1/plan/intent`（规则判定，毫秒级）决定走哪条路：

| 判定 | 动作 |
|---|---|
| `scene=general` / 意图服务不可用 | 原链路，行为与 M0 完全一致 |
| `scene=plan` 且 `needPlan=false` | 下发 `intent` + 把追问话术当 `delta`，落库一条助手消息（**不调模型**：追问项是确定性的，让模型润色只会引入不确定性） |
| `scene=plan` 且 `needPlan=true` | 复用 `PlanService.generate()`（校验+落库+留痕的完整单元），只做事件转发；成功后额外下发一句摘要 |

两条关键约束：

- **意图预判失败必须降级，不能阻断对话**：`AiServiceClient.analyzeIntent` 超时（5s）或报错时返回 `null`，调用方按闲聊处理并在日志留痕。
- **计划必须记来源**：`t_travel_plan` 自 V4 起有 `session_id` / `source_message_id`，由 `PlanStoreService.createFromDraft` 写入，用于「这个计划是哪句话生成的」与按会话聚合。

### 5.1 JSON 数值约定（2026-11-10 补充，已实现）

**主键一律以字符串下发。** 主键用雪花算法，19 位（约 2.1e18）已超出 JS 的
`Number.MAX_SAFE_INTEGER`（9007199254740991）。按数字下发时浏览器 `JSON.parse`
会四舍五入：

```
2119988130910269442  ->  2119988130910269400
```

前端再把这个值传回来就是「会话不存在」这类看不出因果的错误——这正是 2026-11-10
「第二条消息必然失败」的根因。实现方式：后端 `JacksonConfig` 将包装类型 `Long`
统一序列化为字符串；基本类型 `long`（如 `latencyMs`）保持数字。前端 `Id = string`，
禁止对 id 做 `Number()` 转换。

### 5.2 错误响应的 Content-Type（2026-11-10 补充，已实现）

`/api/chat/stream` 的请求头只有 `Accept: text/event-stream`。若异常响应交给内容协商
去挑转换器，会因为没有能写 `text/event-stream` 的转换器而抛 406，最终被容器兜成
**「500 + 空 body」**，前端只能显示「请求失败(500)」，真实原因（会话不存在、凭证
无效、参数非法）全部丢失。

因此 `GlobalExceptionHandler` 的所有错误响应都显式声明 `Content-Type: application/json`，
并遵循：

| 场景 | 状态码 | 说明 |
|---|---|---|
| 参数校验失败 | 400 | 不得回 200，否则 SSE 客户端会把它当成功流，留下空气泡 |
| 未登录 / 凭证无效 | 401 | 前端提示重新登录，不建议重试 |
| 越权访问他人资源 | 403 | |
| 资源不存在 | 404 | 如会话已被删除 |
| 限流 | 429 | 可重试 |
| 服务端异常 | 500 | 可重试，响应体必须带 `message` |

### 5.3 `PATCH /api/plans/{id}` 修改草稿（2026-11-12，已实现）

**可改范围**：标题、出发地、目的地、天数、人数、起止日期。
行程条目与预算金额不在本接口范围内——前者属于 M2 的行程调整，后者在 L0（无实时数据源）
下改了就是编造数字。

**请求体**（`application/json`，所有字段可选）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string(1-100) | 不能为空白 |
| `originCity` | string(≤64) \| null | `null` 表示清空 |
| `destination` | string(≤64) \| null | `null` 表示清空；多目的地计划禁止修改 |
| `days` | int(1-30) \| null | `null` 表示天数未知 |
| `travelers` | int(1-50) \| null | |
| `startDate` | `YYYY-MM-DD` \| null | |
| `endDate` | `YYYY-MM-DD` \| null | |
| `baseVersion` | int | 打开表单时看到的 `version`，用于乐观锁 |

三条语义约定：

1. **不传 = 不改，传 `null` = 清空。** 客户端删空输入框时必须显式传 `null`，
   否则会变成「点了保存但没生效」。
2. **未知字段直接报错**（`10001`），不做静默忽略——前端把 `titl` 拼错时应当立刻发现。
3. **天数与日期的归一化**（前端 `utils/planEdit.ts` 按同一套规则联动）：
   - 显式给天数且有出发日期 → 结束日期由天数推导；同时给了矛盾的结束日期则报错；
   - 只给日期 → 天数由区间反推；
   - 天数变化会同步 `t_travel_day`：变多补空白天，变少删尾部整天（含当日行程项）。

**服务端保证**：

| 保证 | 实现 |
|---|---|
| 只有 `DRAFT` 可改 | 状态机前置判断，否则 `30103` |
| 并发下只有一个成功 | `WHERE id=? AND status='DRAFT' AND version=?`，失败返回 `30104` |
| 改动可回溯 | 改前、改后各写一份 `t_plan_version` 快照（`version_no` 分别为旧值与新值） |
| 无变化不产生版本 | 请求体与当前值完全一致时直接返回详情，`version` 不变 |
| 天数变化后统计不失效 | 重算 `unverifiedFieldCount`（删掉的天里带着 FactField） |

响应体是修改后的完整计划（与 `GET /api/plans/{id}` 同构），前端可直接替换本地状态。


前端侧（`src/api/stream-error.ts`）按状态码兜底中文文案，并在 5xx / 429 时给出
「重试」按钮；只有后端明确返回的可读 message 才原样展示给用户。

## 6. 限流、超时与成本（D-07 建议默认值）

## 7. Prompt 输出约束（Python 侧）

`backend-ai/app/llm/prompts.py` 现有 system prompt 已包含「不得编造实时信息」「不得声称已修改正式行程」。M1 需追加：

1. 计划生成场景下**只输出 JSON**，且有 `scene=plan` 时切换到专用 prompt。
2. 所有实时性字段必须输出 `FactField` 结构，`verified` 固定 `false`、`value` 固定 `null`。
3. 未知字段输出 `null` 并列入 `missingFields`，不得填 0、"无"、空串。
4. 不得在 `risks` / `aiNote` / `advice` 等自由文本里夹带具体实时数值。
5. 用户输入一律作为 `user` 角色消息传入，不拼接进 system prompt（防注入，已实现）。
